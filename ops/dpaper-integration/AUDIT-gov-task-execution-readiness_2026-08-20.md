# 전 기관·부서 SP 업무 수행 가능성 전수조사 (2026-08-20)

> 계기: AGENCY-AC-COMMON_v1.5 공리 2(접수 이후 심사·보완·의견제출·결재)를
> 전 기관 공통으로 승격시킨 뒤, 주피터님 지시("상위 SP는 원칙을 담당하고,
> 하위 실제 기관과 부서 SP는 근거 법령과 규칙 등에 따라 실제로 업무를
> 수행해야 한다")에 따라 실제로 그 하위 SP들이 업무를 수행할 수 있는
> 상태인지 전수조사했다.
>
> **방법론상 한계(정직하게 고지)**: 1,115개 SP 파일 각각을 사람이 읽듯
> 내용 품질까지 검토하는 건 이 세션 범위에서 불가능하다 — 대신 "원칙은
> 상속했지만 실행 코드가 없어 어떤 요청도 처리 못 하는" 구조적 공백을
> 코드·문서 교차조회로 전수 검출했다. 개별 SP의 서류 목록·법령 조문이
> 정확한지(내용 정확성)는 이 조사 범위 밖이다 — 그건 실제로 문서를
> 등록하는 세션에서 웹검색으로 개별 확인해야 한다(REQUIRED_DOCUMENTS_
> REGISTRY 등록 관례 그대로).

## 2. §LEGAL-BASIS(근거 법령) 보유 현황 — "원칙" 축

**핵심 발견 ①**: `benefit-categories`(42개, 급여·수당류) 전체가
§LEGAL-BASIS 섹션 자체가 없다 — 다른 7개 분류가 전부 95%대 이상인 것과
대조적으로 이 카테고리만 통째로 누락됐다. 개별 파일이 우연히 다
빠뜨렸을 확률보다 이 카테고리의 템플릿 자체에 §LEGAL-BASIS가 없거나,
작성 시점이 다른 배치보다 앞서 이 규칙이 적용되기 전이었을 가능성이
크다 — 원인은 이번 조사에서 확인하지 못했다.

## 3. REQUIRED_DOCUMENTS_REGISTRY(실제 업무 수행 코드) 보유 현황 — "실행" 축

`GOV_TASK_SUBMIT_REQUEST`가 실제로 서류를 접수·심사하려면
`REQUIRED_DOCUMENTS_REGISTRY`(worker.js)에 그 기관의 `agency:task_key`가
등록돼 있어야 한다 — 없으면 공리 2를 상속했어도 이 기관은 어떤 GOV_TASK
요청이 와도 예외 없이 `TASK_SCHEMA_NOT_FOUND`로 거부한다(handleGovTaskSubmit,
worker.js 19044행).

| 소스 | 등록된 task_key 수 |
|---|---|
| `main`(병합 완료, 원래 있던 것) | 2 (`kcc:location_service_registration`, `court:personal_bankruptcy_filing`) |
| 이번 세션 작업 전체(§4 병합 포함, 병합 대기) | +13 (`seogwipo` 7개, `jejusi` 6개 — 서귀포·제주시 건설 계열, 중복 없음 확인됨) |
| **SP 파일 자체에 REQUIRED_DOCUMENTS_REGISTRY/task_key를 언급하는 파일** | **1개** (`SP-CITYDIV-SEOGWIPO-CONSTRUCTION-BUILDING`, 이번 세션 작업 대상) |

**핵심 발견 ②(가장 중요)**: 1,115개 SP 중 991개(89%)가 "허가"/"신청"/
"등록"/"신고"/"승인" 등 실제 처분·접수 업무를 명시하는데도, 이번 세션
작업분을 전부 병합해도 실제로 서류를 접수할 수 있는 기관은
**15개 task_key뿐**이다 — 필요 추정치 991개 대비 **1.5%**. 즉 공리
2(원칙)는 전 기관에 자동 상속됐지만, 그 원칙을 실제로 실행할 "하위
SP의 구체적 업무 수행 코드"는 거의 전무한 상태다 — 이번 세션 시작
시점 지적("상위는 원칙, 하위는 실제 수행")이 정확히 이 공백을 가리킨
것으로 보인다.

## 4. 발견된 위험 — 병합 대기 중인 두 브랜치의 키 충돌 (2026-08-20 해소됨)

`feat/dpaper-and-gov-task-review-protocol`(이번 세션)과
`feat/required-documents-registry-construction`(별도 세션)이 **서로
모른 채** 정확히 같은 두 키(`seogwipo:building_permit`,
`seogwipo:occupancy_inspection`)를 각자 다른 내용으로 등록했었다:

| 필드 | 이번 세션 버전 | 별도 세션 버전 |
|---|---|---|
| `legal_basis` | "건축법 제11조, 건축법 시행령 제9조, 건축법 시행규칙 별표 4"(조문 특정) | "건축법"(조문 없음) |
| 구조계산서 id | `structure_calc` | `structural_calc` |
| 시공사진 id | `construction_photos` | `construction_photo` |
| land_use_cert `max_age_days` | 90(보수적 추정치 명시) | null |

**해소 방식**: `git cherry-pick`으로 `feat/required-documents-registry-
construction`(57f235c9)을 이 브랜치에 병합하면서, 겹치는 두 키는 조문을
더 구체적으로 특정한 이번 세션 버전을 유지하고 나머지 11개(서귀포 5·
제주시 6, 겹치지 않는 키)는 그대로 합쳤다 — 정보 손실 없이 15개
task_key(`kcc`/`court` 포함) 전부 하나의 커밋 이력에 통합됐다.
worker.js의 REQUIRED_DOCUMENTS_REGISTRY에 중복 키 없음을 코드로
재확인했다. 결정 근거는 worker.js 해당 위치 주석에도 남겨뒀다. **단,
어느 쪽 legal_basis/문서 목록도 이번 병합에서 웹검색으로 재검증하지는
않았다** — "조문이 더 구체적인 쪽을 택했다"는 것과 "그 조문이 실제로
맞다"는 것은 다른 주장이다.


## 5. 기관 신원(access_cert 결재) 축 — 별도 병목

3항의 REQUIRED_DOCUMENTS_REGISTRY와 별개로, 접수된 GOV_TASK이 공리
2의 결재 단계(`/gov/task/officer-decision`)까지 가려면 그 기관이
`AGENCY_PUBKEY_REGISTRY`(dept-task-handler.js)에 실제 기관장 공개키를
등록해야 한다. 이 레지스트리는 **현재 완전히 비어있다** — 3항에서 몇
개 task_key가 등록되든, 등록된 기관의 공식 키가 하나도 없으므로 지금
이 순간 어느 기관도 §3(공무원 결재)까지 도달할 수 없다(§2 접수·심사·
보완까지는 가능, 최종 결재만 막힘). 이는 이 저장소 밖의 절차(기관
신원 오프라인 확인)가 선행돼야 하는 별도 항목으로, 이전
IMPLEMENTATION-GAPS 문서에 이미 기록돼 있다.

## 6. 종합 — 3단 병목 구조

```
공리 2(원칙, AGENCY-AC-COMMON)          ✅ 1,115개 기관 전부 자동 상속(2026-08-20)
        │
        ▼
REQUIRED_DOCUMENTS_REGISTRY(실행 코드)   ⚠️  991개 후보 중 15개만 등록(병합 대기, 1.5%)
        │
        ▼
AGENCY_PUBKEY_REGISTRY(기관 신원)        ❌  0개 — 어느 기관도 결재 단계 도달 불가
```

세 층 중 어느 하나라도 비어있으면 그 기관은 실제로 GOV_TASK을 처리하지
못한다. 지금은 세 층 다 동시에 비어있는 구간이 압도적으로 넓다 —
"원칙(공리 2)이 상속됐다"는 사실이 "업무를 수행할 수 있다"는 뜻이
아님을 이 조사가 수치로 확인했다.

## 7. 권고 (우선순위, 실행은 별도 세션 판단)

1. **키 충돌 해소(§4) — 완료** — 조문을 더 구체적으로 특정한 쪽을
   유지하고 나머지 11개를 합쳐 15개로 병합했다. 다만 어느 쪽
   `legal_basis`도 웹검색으로 재검증하지 않았으니, 실제 등록 전
   최종 확인은 여전히 필요하다.
2. **REQUIRED_DOCUMENTS_REGISTRY 등록 확대** — 991개 후보 중 등록
   순서를 정할 기준 필요(민원 빈도, 이미 §LEGAL-BASIS가 정밀한 기관
   우선 등). 이번 조사는 "무엇이 비었는지"만 확인했고 "어떤 순서로
   채울지"는 판단하지 않았다.
3. **benefit-categories §LEGAL-BASIS 공백(§2 발견①) 원인 확인** —
   42개 전체가 빠진 이유(템플릿 문제인지 작성 시점 문제인지) 확인 후
   일괄 보강.
4. **AGENCY_PUBKEY_REGISTRY 활성화 절차 착수** — 코드는 이미 완성돼
   있으므로(§5), 병목은 순수하게 저장소 밖 행정 절차(기관 신원 확인)
   다. 이건 개발 작업이 아니라 주피터님의 대외 절차 판단이 필요한
   항목이다.
