혼디 사용자 인증 및 로그인 — 비밀번호 없는 지갑 기반 인증의 전체 구조

혼디는 이메일·비밀번호가 없다. 계정의 신원은 기기에 저장된 개인키(지갑) 그 자체이며, 로그인은 "그 개인키를 가진 기기가 맞는지"를 스마트폰의 생체인증으로 매번 확인하는 과정이다. 이 문서는 최초 가입부터 PC-폰 기기 연동, 알림(Web Push) 인프라, 세션 수명주기, 남용 방지, 그리고 2026-08-29 세션에서 실사로 재현·수정한 버그 2건까지 — 백지 상태에서도 이 인증 시스템을 다시 이해할 수 있도록 통합했다.

Overview
개요

혼디는 사용자가 비밀번호를 만들거나 기억할 필요가 없다. 계정의 신원은 기기에 저장된 Ed25519 개인키(지갑) 그 자체이고, 최초 가입은 반드시 스마트폰에서 전화번호 인증 1회로만 이뤄진다. 이후 PC 등 다른 기기에서 같은 계정을 쓰려면, 이미 신뢰된 그 폰이 매번 생체인증으로 "이 요청을 승인한다"고 확인해줘야 한다.

이 문서는 2026-08-29 세션에서 실제로 코드를 읽고, 테스트 스크립트로 운영 서버에 직접 요청을 보내고, 그 과정에서 발견한 버그 2건(PC 자기간섭, 세션 만료 재현)을 고치면서 확인한 내용을 통합한 것이다. 설계 의도만 있고 아직 확인 못한 부분은 없다 — 여기 적힌 내용은 전부 코드 인용 또는 실제 재현으로 뒷받침된다.

⓪ Core Concept
핵심 개념 — 비밀번호 없는 인증

일반적인 서비스는 "이메일 + 비밀번호"를 서버에 등록해두고, 로그인 때마다 그 조합을 대조한다. 혼디는 이 모델을 쓰지 않는다. 대신:

  • 신원 = 개인키. 가입 시 기기(반드시 스마트폰)가 Ed25519 키페어를 생성한다. 개인키는 그 기기의 로컬 저장소(IndexedDB)를 벗어나지 않는다.
  • 서버는 공개키만 안다. TOFU(Trust On First Use) 방식으로, 처음 등록된 공개키를 그 계정의 것으로 신뢰한다.
  • 다른 기기에서 쓰려면 "옮기거나" "빌려야" 한다. PC는 원래 개인키가 없다 — ③에서 다루는 device-link로 폰이 승인해야만 PC도 같은 지갑을 쓸 수 있다.
  • 비밀번호 분실이라는 개념 자체가 없다. 대신 "그 폰을 잃어버리면 어떻게 되는가"가 핵심 리스크가 된다 — ⑨ 백업 키, ⑩ 근본 전제에서 다룬다.
중요
이후 모든 섹션(GUID, 기기 연동, 백업 키)은 전부 "개인키가 곧 신원"이라는 이 전제 위에서 설계됐다. 비밀번호 재설정 같은 개념을 찾으려 하면 이 시스템을 오독하게 된다.
① Signup
최초 가입 — 폰에서 시작해야 하는 이유

혼디는 PC에서 첫 가입 자체를 막는다. auth.js의 가입 버튼 클릭 핸들러는 _isMobileDevice()가 거짓이면 즉시 _confirmMobileRegistration()로 한 번 더 확인하고, 그래도 아니면 _showPcRegisterBlockedNotice()로 가입 자체를 중단시킨다.

가입 절차

  1. 휴대폰 번호 입력 → SMS(또는 동등한 수단)로 phoneVerifyToken 발급(_requestAndVerifyPhoneOtp)
  2. 인증 성공 시 _e164ToIPv6(e164)로 GUID를 그 자리에서 계산(② 참고)
  3. _completeRegistration({ ipv6, handle, e164, nickname, digits, phoneVerifyToken })으로 서버에 계정 등록
  4. 같은 기기(폰)의 지갑(gopang-wallet.js)이 Ed25519 키페어를 생성해 공개키를 함께 등록
왜 폰에서만인가
전화번호 인증이 유일한 본인 확인 수단이기 때문에(⑪ 참고), 그 인증을 받는 기기와 지갑을 생성하는 기기가 분리되면 "누가 진짜 그 번호의 주인인가"를 보장할 방법이 사라진다. PC 가입을 원천 차단하는 건 이 하나의 신뢰 사슬을 지키기 위한 설계다.
② GUID
계정 식별자(GUID) — 결정론적 생성
async function _e164ToIPv6(e164) {
  const hash = await _sha256('gopang-phone:' + e164);
  const groups = [];
  for (let i = 0; i < 8; i++) groups.push(hash.slice(i*4, i*4+4));
  groups[0] = '2601';
  groups[1] = 'db80';
  return groups.join(':');
}

GUID는 서버가 발급·배정하는 값이 아니라, 전화번호 하나로 누구든 그 자리에서 재계산할 수 있는 고정값이다. "고정"과 "결정론적 계산"은 모순이 아니다 — 같은 입력이면 언제나 같은 SHA-256 결과가 나오므로, 한 번 계산된 GUID는 그 사용자에게 영구히 동일하다.

시점누가 계산/보유하는가
최초 가입폰이 _e164ToIPv6(e164)로 직접 계산해 서버에 영구 저장
이후 PC device-link 로그인PC는 계산하지 않음 — 서버가 poll 응답(data.guid, sign_request 한정)에 담아 돌려주는 기존 값을 그대로 수신
왜 결정론적인가
중앙 서버의 "조회·배정" 단계 없이, 전화번호만 있으면 어느 컴포넌트든 독립적으로 같은 식별자를 유도할 수 있다 — 탈중앙화 지향 설계(PDV 데이터 주권 원칙)와 일치한다.
③ Device Link
기기 연동 — PC ↔ 폰

auth/device-link.html(PC 쪽)과 auth/device-link-approve.html (폰 쪽)이 짝을 이루는 실제 파일이다. 목적에 따라 두 가지 모드가 있다:

purpose이전되는 것용도
key_transfer개인키 자체(X25519로 암호화된 봉투)PC를 이 계정의 개인 기기로 등록 — 이후 로그아웃 전까지 계속 쓸 수 있음
sign_request서명 결과만(개인키는 이동 안 함)공용 PC 모드 — 매 작업마다 폰 승인이 다시 필요, 개인키는 폰을 벗어나지 않음

key_transfer 흐름

  1. PC가 1회용 X25519 키페어 생성(GopangWallet.generateX25519KeyPair()), 공개키만 서버에 전송
  2. POST /auth/device-link/init { e164, pcLabel, purpose:'key_transfer', pcPubKeyB64u }
  3. 서버가 폰에 Web Push 발송(④), sessionId 반환
  4. 폰이 승인하면 서버가 PC의 공개키로 개인키를 암호화(seal)해 세션에 저장
  5. PC는 GET /auth/device-link/poll로 2초 간격 폴링, state:'delivered'가 오면 자신의 개인키로 복호화(openSealedWithKey) → restoreFromPrivateKey()

입력 보조 — 혼디 숫자 코드 스캔(link-scan.html)

전화번호를 직접 타이핑하는 대신, 이미 로그인된 기기에 뜬 10자리 "혼디 숫자 코드"를 새 기기의 카메라로 찍으면 digitsToPhone()이 곧바로 전화번호로 해석해 device-link.html?phone=...으로 넘겨준다. 2026-07-31에 외부 api.qrserver.com QR 생성 호출을 걷어내고 자체 인코딩(hondi-digit-code.js)으로 교체했다 — 전화번호 유래 데이터를 제3자 API로 보내지 않아도 된다는 부수적 이점이 있다.

이건 인증을 대신하지 않는다
숫자 코드 스캔은 순전히 "타이핑 생략" 편의 기능이다. 실제 본인 확인은 여전히 그 뒤에 이어지는 폰의 생체인증(⑥)에서 이뤄진다 — 코드 자체엔 어떤 인증 권한도 없다.
④ Push
알림 메커니즘 — Web Push(VAPID)

"PC → 폰"으로 알림이 가는 경로는 SMS가 아니라 브라우저 표준 Web Push(VAPID)다. SMS는 뒤에서 다룰 폴백 수단일 뿐이다.

사전 구독(평소에 미리 끝나 있음)

폰이 혼디를 처음 쓸 때 push.js의 requestPushSubscription()이 pushManager.subscribe()로 이 기기·이 브라우저를 가리키는 구독 정보를 만들어 POST /push/subscribe로 서버에 등록한다. 이때 deviceType(mobile/desktop/unknown)도 함께 태깅된다 — ⑤에서 이 필드가 핵심 역할을 한다.

발송 시점 흐름

PC → /auth/device-link/init
     ↓
서버가 VAPID 개인키로 서명 → 폰 브라우저의 벤더 푸시 서버(FCM 등)로 전송
     ↓
폰의 서비스워커(sw.js) 'push' 이벤트 → showNotification()
     ↓
사용자가 알림 탭 → notificationclick → device-link-approve.html 오픈
     ↓
"본인이 맞습니다" → POST /auth/device-link/verify
     ↓
PC의 polling이 상태 변화를 감지 → 로그인 완료
Wi-Fi로도 정상 동작
Web Push는 벤더 푸시 서버와의 상시 연결을 쓰므로 Wi-Fi만으로도 정상 수신된다. 반대로 SMS 폴백은 통신사 신호가 필요해 Wi-Fi 전용 기기에서는 받을 수 없다 — device-link.html의 안내 문구가 바로 이 차이를 설명한다.
⑤ Targeting
발송 대상 필터링 — PC 자기간섭 버그

서버는 계정에 등록된 모든 구독에 푸시를 보낸 뒤, 사후에 deviceType으로 "폰이 실제로 받았는지"만 구분해왔다 — 발송 자체를 막지는 못했다.

2026-08-29 실사 재현
테스트 스크립트로 /auth/device-link/init을 호출했더니 알림이 폰이 아니라 테스트를 실행한 PC(브라우저)로 갔다. 원인은 그 PC가 같은 계정으로 예전에(테스트 등으로) 구독을 남겨둔 상태였고, 서버가 deviceType을 가리지 않고 등록된 구독 전체에 발송했기 때문.

수정 — 발송 대상 자체를 mobile로 제한

// before: 모든 기기에 발송 후 사후 분류
const devices = _parseDeviceSubscriptions(profile?.push_subscription);
hasMobileDevice = devices.some(d => d.deviceType === 'mobile');
if (devices.length) { /* devices 전체에 발송 */ }

// after: 발송 대상을 mobile로 원천 필터링
const devices = _parseDeviceSubscriptions(profile?.push_subscription);
const mobileDevices = devices.filter(d => d.deviceType === 'mobile');
hasMobileDevice = mobileDevices.length > 0;
if (mobileDevices.length) { /* mobileDevices에만 발송 */ }

device-link의 존재 이유 자체가 "요청한 기기가 아닌 다른 신뢰 기기에서 승인"이므로, 데스크톱으로 보낼 이유가 애초에 없다. 단, 죽은 구독(410) pruning은 전체 devices 목록 기준으로 계속 동작하게 남겨뒀다 — GDC 충전 확정 등 다른 알림은 데스크톱도 정상 수신해야 하므로, 이번 필터링 때문에 데스크톱 구독이 실수로 삭제되면 안 된다.

⑥ Approval
승인 흐름 — 위조 방지·승인/거부

device-link-approve.html은 승인 전에 요청한 PC의 정보(브라우저·OS 라벨)를 보여준다 — "본인이 직접 다른 기기에서 로그인을 시도한 게 맞는지" 사용자가 스스로 확인하게 하는 최소한의 피싱 방지 장치다. 코드값 자체는 푸시 payload에 담기지 않고, 알림을 열어 앱(자기 guid)으로 조회해야만 보이게 해 제3자가 푸시를 가로채도 코드까지 얻지 못하게 한다.

동작호출결과
승인POST /auth/device-link/verify세션 state → delivered, PC의 polling이 감지
거부"본인 아님 — 거부" 버튼세션이 무효 처리되어 PC 쪽은 대기 상태로 남거나 만료됨

PC 쪽은 GET /auth/device-link/poll?sessionId=...를 2초 간격으로 폴링한다. 탭이 백그라운드에 있다 포그라운드로 돌아오면 즉시 1회 강제 poll을 추가로 실행해, 브라우저의 백그라운드 탭 타이머 스로틀링으로 인한 반영 지연(최대 40초까지 재현된 적 있음)을 줄인다.

⑦ Session
세션 수명주기 — TTL과 만료
const DEVICE_LINK_TTL_SECONDS = 90;      // 코드 유효기간 — SMS(5분)보다 훨씬 짧게(사용자 지시)
const DEVICE_LINK_MAX_ATTEMPTS = 5;

세션은 90초면 만료된다(SMS 폴백 사용 시 300초로 연장). 네 개 엔드포인트(poll/verify/deliver/session)가 전부 세션을 못 찾으면 404 SESSION_EXPIRED — "세션이 만료됐거나 존재하지 않습니다"를 반환한다.

2026-08-29 재현 사례
배포(GitHub Actions)가 진행되는 동안 /init 요청이 서버에 먼저 도달해 세션이 만들어졌는데, 푸시 알림 자체는 한참 늦게 도착했다. 사용자가 알림을 탭했을 때는 이미 90초가 지나 세션이 사라진 뒤였다 — 배포 지연이 겹친 테스트 타이밍 문제였지, 평소 지연이 곧바로 이 정도는 아니다.

90초는 짧다는 지적이 있을 수 있으나, 이는 "사용자 지시"로 SMS(5분)보다 의도적으로 짧게 설정된 값이다 — 보안(탈취된 세션의 악용 가능 시간을 최소화) 목적과 사용성(정상적으로는 푸시가 1~2초 내 도착) 사이의 트레이드오프로 이해해야 하며, 변경 전 이 의도를 먼저 확인해야 한다.

PUSH_RATE_LIMIT과 IP_RATE_LIMIT을 둘 다 두는 이유는 서로 다른 공격을 막기 위해서다 — 전화번호 기준 제한은 "특정 피해자를 계속 괴롭히는 것"(폭탄 알림)을, IP 기준 제한은 "한 공격자가 여러 번호를 돌아가며 시도하는 것"(스캐닝)을 각각 막는다.

⑨ Backup Key
백업 키 복구

기기 연동이 실패하거나(만료·응답 없음) 아예 다른 기기가 없는 경우, 최후 수단으로 백업 키(개인키, Base64URL)를 직접 입력해 복구할 수 있다 — device-link-approve.html·device-link.html 양쪽에 "백업 키를 직접 갖고 있어요" 버튼으로 노출된다. 

const result = await _restoreFromBackupKey(key.trim());

이 경로는 guid 없이 호출되므로 서버의 공개키 검증 단계를 건너뛴다 (로컬 지갑 교체만 수행) — 대신 이후 페이지의 통상적인 세션 검증 단계에서 PUBKEY_MISMATCH 등으로 걸러진다.

PC의 X25519 키페어(key_transfer용)는 1회용이다. finishImport()가 끝나면 pcKeyPair = null로 참조를 끊어 순방향 비밀성(forward secrecy)을 확보한다 — CryptoKey가 non-extractable이라 참조만 끊어도 메모리에서 재추출이 불가능하다.

⑩ Trust Model
이 설계의 근본 전제와 한계
device-link.html의 만료 안내문(원문 발췌 취지)
"이 방식은 개인키를 가진 다른 기기가 실제로 존재해야만 작동한다 — 서버는 그런 기기가 진짜 있는지 확인할 방법이 없다(개인키는 서버에 없으므로). 있어도 없어도 지금과 똑같이 '응답 없음'으로 보인다."

이건 버그가 아니라 설계가 스스로 인정하는 근본 한계다. 이 인증 시스템 전체는 "그 폰이 실제로 존재하고, 사용자가 그 폰에 접근할 수 있다"는 전제 위에 서 있다. 이 전제가 깨지는 경우(폰 분실·초기화 등)엔 device-link로는 복구할 수 없고, 백업 키(⑨)가 있을 때만 복구 가능하다 — 백업 키조차 없다면 그 계정은 되살릴 수 없다.

같은 이유로, "PC 쪽 클릭 자체는 신원을 증명하지 않는다"는 점도 명확히 해야 한다 — 실제 승인은 항상 폰의 생체인증에서 일어나고, PC는 요청을 발신·수신하는 역할만 한다.

⑬ Constraints
알려진 제약·사고 이력
  • VAPID 키 분실 이력(2026-07-20) — 예전 VAPID 개인키를 백업 없이 분실해 서버가 새 키 쌍으로 교체했다. 교체 이전에 구독한 클라이언트는 FCM이 403으로 조용히 거부(도착 안 함)했고, 재구독이 필요했다. push.js는 지금 구독의 applicationServerKey를 현재 공개키와 바이트 단위로 비교해, 안 맞으면 자동으로 재구독하도록 방어 코드가 들어가 있다.
  • 브라우저·기기별 재구독 필요 — 같은 폰이라도 Chrome·Safari 등 브라우저가 다르면 별개 구독으로 인식된다. 알림은 "평소 혼디를 쓰던 그 브라우저"에서만 받을 수 있다.
  • 공용 PC 모드의 한계 — sign_request는 개인키를 옮기지 않지만, 매 작업마다 폰 승인이 필요해 사용성이 떨어진다. 세션 동안 승인받은 전화번호는 sessionStorage(팝업-opener 공유)로만 재사용되고, 승인(폰 클릭) 자체는 매번 새로 필요하다.
  • 죽은 코드 — auth/qr-login.html이 존재하지 않는 /auth/qr/create 엔드포인트를 여전히 호출한다(⑪). 삭제 또는 명시적 폐기 안내로 정리가 필요하다.
  • Node 테스트 스크립트의 한계 — 이 문서 작성에 쓰인 테스트 스크립트는 /init 호출까지만 검증하고 /poll로 승인을 끝까지 따라가지 않는다. 전체 흐름의 자동화 테스트는 아직 없다.
