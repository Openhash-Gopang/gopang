Overview
이 문서가 왜 있는가

하루 세션인데 성격이 다른 작업 8단계가 이어졌다 — 인수인계 검증, 설계 확장, 사고실험 두 종류(텍스트 추적 vs 라이브 호출), 실제 코드 통합, 실제 배포, 그리고 배포 후 실결함 수정까지. 다음에 이 영역을 다시 건드릴 사람이 "Pathfinder가 지금 어디까지 실제로 작동하는가"를 다시 처음부터 추적하지 않도록, 무엇을 만들었는가보다 무엇을 확인했고 왜 그 확인 방법을 골랐는가 위주로 정리한다.

① Handoff Verification
인수인계 검증 — 기록과 실제 origin 상태 불일치 2건

이전 세션이 남긴 HANDOFF_2026-08-13.md를 그대로 믿지 않고, 두 저장소를 직접 클론해 원격 상태와 대조했다. 이 습관이 이번 세션 초반에 바로 값을 냈다.

발견 1 — origin_guid 평문이 여전히 push된 코드에 남아있었음
feat/govtask-depttask-link 브랜치의 실제 push된 코드를 열어보니, 인수인계서가 "제거했다"고 적은 origin_guid: guid 라인이 그대로 있었다 — 로컬 수정판이 push되지 않은 상태였다.
발견 2 — 가명화 검증 섹션 자체가 origin에도 로컬에도 없었음
docs/pathfinder-privacy-verification 브랜치가 passport 저장소 origin에 아예 존재하지 않았다. 6장(가명화 파이프라인 검증) 설계 내용은 memory 기록을 근거로 다시 작성해 복구했다.

두 건 모두 GitHub 원격에서 직접 fetch/grep으로 검증한 뒤 수정 커밋을 push하고, 다시 원격에서 재확인하는 방식으로 마무리했다 — "로컬에서 커밋했다"와 "원격에 실제로 반영됐다"는 다른 사실이라는 걸 이 세션 내내 반복해서 확인하게 된다(⑦·⑧ 참고).

② PDV Scope
PDV 기록 범위 확장 — 기관/부서/직원 측도 포함

기존 handleGovTaskSubmit()(시민 측)은 pdv_records에 6하원칙 구조화 레코드를 남기지만, dept-task-handler.js (기관/부서/직원 측)는 pdv_records를 전혀 건드리지 않고 dept_tasks.status 전이와 선택적 result_note 자유텍스트만 남긴다는 게 실사로 확인됐다. dept_task_events.actor_hash도 어떤 호출부에서도 채워지지 않아 항상 비어있었다.

이를 근거로 기관/부서/직원의 업무 처리 결과도 시민 측과 대칭적으로 각각 6하원칙 PDV를 기록해야 한다는 설계 원칙을 확정했다. 아직 코드 구현은 없는 설계 단계지만, 이 신설 PDV가 실제로 구현되면 actor_hash 공백(담당자 단위 식별 불가)을 Pathfinder v2를 기다리지 않고도 실질적으로 메울 수 있다는 점이 뒤에 나오는 시민 요청 시나리오(③)와 8건 사고실험(⑥) 설계에 계속 영향을 줬다.

③ Citizen Scenarios
시민 요청 시나리오 사고실험 4건

시민 한 명의 요청 하나가 기관·부서·직원 AI비서를 거쳐 결과물에 도달하는 전체 경로를 4가지 유형으로 그렸다 — 규칙형·단일기관 (폐업신고), 규칙형·다기관연쇄(혼인신고 후 명의변경), 재량형· G18필수(장애인 활동지원 이의신청), 규칙형→재량형 경계 사례 (국외학위 인정). 처음에는 시나리오 3에서 "직원의 실명/직위 확인을 거친 행위"라고 썼다가, 코드 실사로 actor_hash가 어디서도 채워지지 않는다는 걸 확인하고 실제 구현 수준에 맞게 정정했다 — 사고실험도 코드와 어긋나면 틀린 문서라는 원칙을 이 세션 내내 지켰다.

④ The Big Discovery
Pathfinder ↔ 기존 오케스트레이션 실사 — 분리된 두 트랙

"Pathfinder가 호출되는 곳은 AI비서 자신이고, 모든 AI비서는 K-Intent/K-Compose/K-Execute/K-Deliver/K-Report(SP-19~23)를 이미 탑재하고 있다"는 지시를 받고 저장소를 확인했다. 여기서 이 세션의 가장 큰 발견이 나왔다.

이미 있던 것

  • K-Intent~K-Report 5단계 오케스트레이션 릴레이 — call-ai.js의 forward/push 핸드오프로 이미 라이브
  • procedure_maps 캐시(K-Compose STEP1) — "검증된 경로를 저장해두고 즉시 인출"하는 메커니즘도 이미 있었음

실제로 빠져 있던 것

procedure_maps/atom_rows 스키마엔 처리시간 관련 필드가 전혀 없었다 — "구조"(어느 기관을 거쳐야 하는가)만 담고 "시간"(지금 가장 빠른 경로)은 안 담는다. 여기까지는 예상된 공백이었는데, 더 깊이 파보니 K-Execute의 CALL_GOVSYS 경로와 GOV_TASK_SUBMIT_REQUEST(dept_task 생성, Pathfinder의 유일한 데이터 원천) 경로가 완전히 분리된 두 실행 트랙이었다는 게 드러났다.

Lessons
교훈 — 텍스트 추적과 라이브 검증은 서로 다른 결함을 잡는다

8건 텍스트 사고실험(⑥)이 잡은 결함(batch_id 누락, 재개 중복접수)은 둘 다 SP 문서 자체의 논리적 모순이었다 — 문서를 꼼꼼히 읽으면 사람도 찾을 수 있는 종류다. 반면 라이브 실행(⑧)이 잡은 결함(PROJECT_STATE_SAVE 누락)은 SP 지침 자체는 맞는데 모델이 멀티턴 상황에서 그 지침을 안정적으로 따르지 않는 종류였다 — 이건 텍스트를 아무리 읽어도 안 보이고, 실제로 모델을 불러서 여러 턴을 이어봐야만 드러난다. 두 방법론은 대체재가 아니라 서로 다른 결함 계층을 잡는 보완재라는 게 이번 세션에서 명확해졌다.

또 하나 — "atom_id↔dept_task 매핑 규칙을 만들라"는 최초 질문 자체가 전제(같은 시스템 안의 이름공간 불일치)부터 틀렸다는 걸 코드 실사(④)로 확인하고서야 알았다. 질문을 그대로 받아 매핑표부터 만들었다면, 애초에 서로 만난 적 없는 두 트랙을 억지로 잇는 잘못된 해법에 시간을 썼을 것이다 — 구현에 들어가기 전에 "이 둘이 정말 같은 문제 공간에 있는가"부터 코드로 확인하는 게 먼저였다.
