SESSION SUMMARY — 2026-08-15

정부 수수료 기준표를 만들고,
실제 서버에 배포해 정확도까지 측정했다

천안시 민원사무편람 엑셀 한 장에서 시작해, PocketBase 데이터·요율 계산기·gov-router.js 배선·bge-m3 시맨틱 검색까지 쌓아 올린 뒤, 실제 운영 서버(l1-hanlim)에 배포했다. 배포 과정에서 PocketBase 구버전 호환성 문제 3건을 실제로 만나 해결했고, 44건 실사용자 스타일 쿼리로 정확도를 측정해 Top-1 76.5%, 오탐 0%라는 숫자를 얻었다. 마지막으로 그 측정 결과에서 드러난 위험(확신에 찬 오답)을 막는 안전장치를 추가했다 — 전 과정에서 "만들었다"만큼 "실제로 확인했다"를 남기는 데 집중했다.

Overview
이 문서가 왜 있는가

"혼디가 사용자에게 공공 서비스를 제공할 때 GDC를 어떻게 차감할 것인가"라는 질문 하나에서 출발해, 데이터 조사 → 스키마 설계 → 배선 → 실배포 → 실측 → 재보정까지 한 번에 이어졌다. 다음에 이 영역(K-행정 과금)을 다시 건드릴 사람이 지금 뭐가 실제로 동작하고, 뭐가 아직 잠정치인지를 바로 알 수 있도록, 작업 순서 그대로 정리한다.

① Fee Schedule
정부 수수료 기준표 — 천안시 편람 → PocketBase

사용자가 제공한 천안시 민원사무편람(1,110행, 857개 고유 민원)을 분석해, 수수료 원문에서 실제 금액을 파싱하는 정제 파이프라인을 만들었다. 처음엔 아라비아 숫자만 잡았다가, "1만5천원" 같은 한글 단위 표기를 놓치고 있다는 걸 발견해 파서를 개선했다(282건 → 324건 파싱 성공).

분류건수의미
REAL497건 → 461건(버그 수정 후)숫자로 확인된 금액(무료 포함)
NEEDS_REVIEW1건 → 37건(버그 수정 후)조례·별표 참조라 자동 계산 불가, 또는 원문에 금액이 있으나 파싱 실패
MISSING363건원본 편람에 수수료 정보 자체가 없음
발견 — 상태 라벨과 실제 파싱 결과가 어긋나는 버그
67건이 "금액명시"로 분류됐는데도 실제로는 숫자를 못 뽑아 status: REAL이 잘못 붙어 있었다(한글 숫자 표기를 정규식이 놓친 결과). 라벨이 아니라 "실제로 쓸 수 있는 숫자를 확보했는가"로 상태를 다시 계산하도록 고쳤다.
② National Rates
국세·사법 요율 — 인지세·법원 인지대/송달료

지자체 조례로 갈리는 민원 수수료와 달리, 인지세(국세)와 법원 인지대·송달료는 전국 공통 구간표다. 「인지세법」 제3조·제6조, 「민사소송 등 인지법」을 웹 조사해 구간표를 코드화했다 — 하드코딩하지 않고 formula_json에 구간 데이터를 저장해, 요율이 개정돼도 코드 재배포 없이 데이터만 갱신하면 되도록 설계했다.

검증한 계산 예시

  • 부동산 8천만원 계약 인지세 → 70,000원 (5천만~1억 구간)
  • 소가 1천만원 전자소송 인지대 → 45,000원 (기본 5만원의 10% 할인)
  • 송달료(당사자 2명 × 15회) → 165,000원

세 값 모두 국가법령정보센터·법원 전자소송 계산기 공식 예시와 정확히 일치함을 확인했다.

③ Router Wiring
gov-router.js 배선 — 키워드 매칭

src/gopang/gov/gov-fee-lookup.js를 새로 만들어 gov-router.js가 이미 계산해둔 trace(어느 지역·기관으로 매칭됐는지)를 받아 요금을 찾는 배선을 붙였다. gov-router.js의 라우팅 로직 자체는 한 줄도 안 건드렸다 — 이 저장소 자체 컨벤션(기존 코드 주석에 명시된 "라우팅 로직은 건드리지 않는다" 원칙)을 그대로 따랐다.

시코드 표기 불일치 발견
시드 스크립트가 초기에 region_code='cheonan'을 썼는데, gov-router.js의 실제 시코드 체계는 도코드 접두가 붙은 'chungnam_cheonan'이었다. 기본값을 고치고 재시드해 해결했다.
④ Semantic Search
bge-m3+Vectorize 시맨틱 검색 배선

이미 구축된 hondi-entity-registry(bge-m3 임베딩 + Vectorize)와 같은 기술을 재사용하되, "도메인·차원 혼재 방지" 원칙에 따라 전용 인덱스(hondi-gov-fee-schedule)를 새로 만들었다. 기존 entity 검색 코드는 전혀 건드리지 않았다.

entity 버전이 겪었던 버그(Vectorize id로 guid를 써서 실제 PocketBase id와 어긋나 후보 조회가 전량 404 났던 사고)를 설계로 미리 피했다 — Vectorize record id로 처음부터 PocketBase 레코드의 실제 id를 그대로 쓴다.

worker.js에 /orchestration/gov-fee-embed-index(색인)와 /gov-fee-semantic-search(검색) 두 엔드포인트를 추가하고, 그레이스풀 디그레이드(시맨틱 실패·바인딩 없음 시 기존 키워드 매칭으로 자동 전환)를 기본값으로 설계했다.

⑤ Live Deployment
실배포 — PocketBase 구버전 호환성 문제 3건

실제 운영 서버(l1-hanlim, PocketBase 0.22.14)에 배포하는 과정에서 로컬 검증만으로는 못 잡는 문제 세 개를 실제로 만났다.

문제 1 — npm SDK ↔ 서버 버전 불일치
pocketbase npm SDK v0.27.3은 PocketBase 서버 >=0.23의 "_superusers 컬렉션" 모델만 지원하는데, 서버는 0.22.14(구버전 /api/admins/auth-with-password 라우트)였다. 새 방식을 먼저 시도하고 404면 구버전 엔드포인트로 raw fetch 후 토큰을 직접 authStore에 채우는 그레이스풀 디그레이드로 해결 — 이후 일반 레코드 CRUD는 버전 차이가 없어 그대로 동작한다.
문제 2 — 컬렉션 스키마 포맷 차이 + import의 숨은 위험
0.23+용 스키마 JSON(fields 키)을 0.22(schema 키 + 필드별 options)용으로 변환해야 했다. 처음 시도한 /api/collections/import는 새 컬렉션 하나만 추가해도 기존 컬렉션 전체를 재검증해서, 무관한 기존 컬렉션의 해묵은 스키마 결함 때문에 전체가 막혔다 — 단일 컬렉션만 만드는 POST /api/collections로 바꿔 다른 컬렉션에 영향 없이 해결.
문제 3 — Vectorize 메타데이터 인덱스는 소급 적용 안 됨
Cloudflare 공식 문서: "메타데이터 인덱스 생성 이전에 upsert된 벡터는 그 인덱스에 메타데이터가 반영되지 않는다." 벡터를 먼저 넣고 인덱스를 나중에 만들었더니 region_code 필터가 계속 0건이었다 — 인덱스 생성 후 재색인(같은 id로 upsert)해 해결. 비동기 반영 지연(수십 초~1~2분)도 함께 확인했다.
⑥ Baseline Architecture
지역 중립 BASELINE 아키텍처

모든 데이터가 천안시로만 채워진 상태를 개선하기 위해, 천안시 데이터를 특정 지역이 아닌 전국 잠정 기준값으로 분리했다. region_code='baseline'이라는 별도 태그를 도입해 chungnam_cheonan(천안시 자신의 실제 지역 데이터)과 코드상 명확히 구분한다.

새 지역 온보딩 절차

  1. 관리자가 해당 지역 민원사무편람 확보
  2. --region <실제시코드>로 동일 시드 스크립트 실행 → REAL 데이터로 채움
  3. 그 지역에 없는 항목은 자동으로 region_code='baseline' 폴백 — 승인 없이는 과금되지 않음
⑦ Broad Pilot
44건 광역 파일럿 실측

실제 REAL 데이터 7개 카테고리(건축·자동차/건설기계·영업신고· 환경·보건의료·운수업·면허자격)에서 뽑되, 원문 그대로가 아니라 구어체로 바꿔 쓴 34개 긍정 쿼리와, 날씨·넷플릭스 등 정부 민원과 무관한 10개 부정 쿼리로 l1-hanlim 서버를 직접 호출해 측정했다.

지표결과
Top-1 정확도76.5% (26/34)
Top-3 정확도91.2% (31/34)
False Positive율0.0% (0/10) — 무관한 질문은 전부 정상 차단

실패 8건을 원인별로 분류하니 데이터 품질 문제(중복·인코딩 깨짐) 1건, 데이터 누락 의심 1건, 테스트 쿼리 자체의 모호함 1건을 빼면, 진짜 의미 혼동은 5건 — "OO변경신고" "OO재발급" 같은 비슷한 접미어를 가진 서비스끼리 헷갈리는 패턴이었다.

⑧ Safety Guard
1·2위 점수차 안전장치

절대 점수 임계값(0.55)만으로는 "1위가 임계값은 넘었지만 2위와 근소한 차이라 사실은 확신할 수 없는" 케이스를 못 걸렀다 — 예를 들어 "건설기계 등록증 재발급" 질의에서 오답(0.740)이 정답(0.723)을 근소한 차이로 이기고 그대로 채택된 사례가 실측에서 나왔다.

1·2위 점수차가 0.03 미만이면 REAL 레코드라도 OK 대신 NEEDS_APPROVAL을 반환하도록 추가했다. 이미 한 번의 API 호출로 받아온 top-3 데이터에 대한 순수 계산이라 응답 속도에 영향이 없다.

정직한 트레이드오프
이 도메인은 정답일 때도 1·2위 점수차가 자연스럽게 작은 경우가 흔하다(실측: 정답 26건 중 6건이 갭 0.03 미만). 이 안전장치는 오답 8건 중 6건은 잡아내지만, 정답 26건 중 6건에도 불필요한 승인 절차를 추가한다 — 완전한 해결책이 아니라 실측 기반 절충이다.
Lessons
교훈

"44건 정확도 측정"이라는 결과 하나를 얻기까지, 로컬 검증만으로는 절대 못 잡는 문제 세 개(SDK 버전 불일치, 스키마 포맷 차이, Vectorize 인덱스 소급 미적용)를 실제 배포 과정에서 만났다. 단위테스트가 15건 전부 통과해도, 실제 운영 환경의 구버전 인프라와 실제 사용자 발화 앞에서는 전혀 다른 문제가 나온다는 걸 다시 확인했다.

또한 "정확도 76.5%"라는 숫자 자체보다, 그 실패가 왜 위험한지(절대 임계값을 넘어 자동 채택되는 오답)를 구분해서 봐야 실제로 의미 있는 개선(점수차 안전장치)으로 이어진다는 것도 확인했다 — 오탐률 0%라는 좋은 숫자에 안심하고 넘어갔다면 이 위험을 놓쳤을 것이다.
