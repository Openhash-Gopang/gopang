## 시나리오 1 — 물품대금 청구(민사), 결과 불만족으로 2회 재생성

**사건**: A는 B에게 사무용 가구 1,500만원어치를 납품했으나 대금을
받지 못해 물품대금 청구 소송을 준비 중이다. K-Law 인터뷰에서
"청구금액 1,500만원"이 `state.claim_amount`로 추출되어
`conversationState.caseState.claimAmount = 15,000,000`으로 저장된다.

**진행**:
1. STEP0 호출 — `case_id`(신규 UUID) + `claim_amount_krw: 15000000` 전송.
   `_klawFlatFeeForClaimAmount(15000000)`이 "1천만~3천만원" 구간에 매칭 →
   **10,000원 GDC 차감**, `klaw_case_charges`에 사건기록 생성.
2. STEP A/B/C 호출 — 매번 같은 `case_id`가 실리지만 `step_cycle=false`이므로
   `settleKlaw`의 `if (!step_cycle) return;` 분기로 빠져 **과금 없이 통과**
   (전편 발견1 수정이 의도대로 동작 — ✅).
3. 사용자가 결과가 마음에 안 들어 "🔁 이 사건으로 다시 생성" 버튼을
   1회 누름 — `regenerateSameCase()`가 `conversationState.caseId`를
   그대로 둔 채 `runJudgementSim()` 재호출. 서버는 `_klawFindCaseCharge`로
   기존 사건기록을 찾아 **차감 없이 `verdict_count`만 2로 증가**.
4. 여전히 불만족 — 다시 한번 재생성(3번째 STEP0 호출) → **여전히 무료**,
   `verdict_count=3`.

**판정**: GDC 관점에서는 ✅ (10,000원 1회만 청구, 이후 전부 무료 — 의도한
동작).

**그러나 ⚠️**: 이 사용자는 오늘 STEP0를 이미 3번 호출했다
(`KLAW_USER_DAILY_STEP_LIMIT = 3`). `recordStep()`은 `settleKlaw` 맨
앞에서 **과금 여부와 무관하게** 항상 실행되므로(§새로 발견된 사항 F2),
무료 재생성 2번도 카운트를 소진시켰다. 오늘 다른 사건을 새로 시작하려
하면 →

## 시나리오 2 — 같은 날, 새 사건(가사) 시도 → 즉시 차단

**사건**: 같은 사용자가 시나리오 1 직후, 배우자와의 재산분할 상담을
위해 새 대화를 시작한다. 청구금액을 8천만원으로 인터뷰가 마무리되고
`runJudgementSim()`이 호출된다.

**진행**: `handleKlawRelay` 최상단의 사전 체크 —
```js
if (step_cycle && stepCount >= KLAW_USER_DAILY_STEP_LIMIT) {
  return _err(429, 'KLAW_STEP_LIMIT_EXCEEDED', ...);
}
```
`stepCount`가 이미 3이므로 **LLM 호출 자체가 나가지 않고 즉시 429
차단**. GDC는 물론 원가(토큰 비용)도 전혀 발생하지 않음 — 사전 게이트가
제대로 작동한다(✅, 플랫폼 보호 관점에서는 의도대로).

**판정**: ⚠️ — 서버 보호 로직 자체는 정상이지만, 사용자 체감에서는
"재생성 버튼 두 번 눌렀을 뿐인데 완전히 다른 새 사건을 오늘 하루 종일
못 만든다"는 결과로 이어진다. `regenerateSameCase` 버튼 문구
"🔁 이 사건으로 다시 생성 (추가 요금 없음)"이 GDC 요금만 언급할 뿐
**일일 생성 횟수 한도가 함께 깎인다는 사실은 어디에도 안내되지 않는다**
(desktop.html/webapp.html 전체 검색 결과 `STEP_LIMIT` 관련 문구는
클라이언트에 없음 — 서버 429 에러 메시지로만 사후에 알게 됨).

## 시나리오 3 — 형사사건(절도), 소송가액 없음

**사건**: C는 편의점 절도 혐의로 수사를 받고 있으며, K-Law로 예상
판결을 가늠해보려 한다. 형사사건은 금전청구가 없으므로 인터뷰
내내 `state.claim_amount`가 한 번도 채워지지 않고
`conversationState.caseState.claimAmount`는 초기값 `0`으로 남는다.

**진행**: `runJudgementSim()`의 STEP0 호출부:
```js
claimAmountKrw: isStep0 ? (cs.claimAmount || null) : null,
```
`cs.claimAmount`가 `0`이므로 `0 || null` → **`null`이 서버로 전송된다**
(JS에서 `0`은 falsy). 서버는 `_klawFlatFeeForClaimAmount(null)`에서
`Number.isFinite(null)`이 false → **`null` 반환** → `_klawIsCaseFlow &&
!_klawFlatFee` 분기로 빠져 `KLAW_CASE_FLOW_NO_VALID_AMOUNT` 로그만 남기고
**과금도 사건기록 생성도 하지 않는다**. C는 완전히 무료로 STEP0~C
전체를 받는다.

**판정**: ⚠️ (전편과의 불일치 — §새로 발견된 사항 F1). 전편 시나리오 12는
"`claim_amount_krw=0`이 서버에 명시적으로 도달해 최소 tier(5,000원)가
부과된다"고 예상했으나, 실제 클라이언트 코드는 `0`을 `null`로 바꿔
보내므로 **시나리오 12는 현재 클라이언트로는 도달 불가능한 죽은
경로**다. 형사·소년보호처럼 원래 소송가액이 없는 사건 유형은 전부
이 시나리오 3의 무과금 경로를 탄다 — 이게 "의도한 무료 정책"인지
"우연히 그렇게 된 버그"인지는 상품 정책 결정이 필요하다(전편이 남긴
미결정 사항이 그대로 유효하되, 실제로 어느 쪽으로 귀결되는지는 이번에
명확해졌다).

**사이드 이펙트**: 사건기록이 없으므로 C가 "다시 생성"을 눌러도 매번
새 사건처럼 취급된다. GDC 관점에서는 무해(어차피 매번 무료)하지만,
"동일 사건 재생성 추적"(`verdict_count` 통계) 기능 자체가 형사사건류에는
전혀 작동하지 않는다는 뜻이다.

## 시나리오 4 — 고액 손해배상, GDC 잔액 0원인 상태로 시도

**사건**: D는 교통사고 손해배상 청구(소송가액 4억 5천만원)를 K-Law로
시뮬레이션하려 한다. 그런데 D의 GDC 지갑 잔액은 **0원**이다(무료 한도도
이미 소진, 충전도 안 한 상태).

**진행**: STEP0 호출 직전, `_gdcFreeQuotaGate(env, guid, ...)`가 실행된다.
그런데:
```js
const FREE_QUOTA_ENFORCEMENT_ENABLED = false; // 993/1016줄
```
이 플래그가 꺼져있어 `_gdcFreeQuotaGate`는 함수 맨 앞
`if (!guid || !FREE_QUOTA_ENFORCEMENT_ENABLED) return null;`에서 **잔액을
확인하지도 않고 즉시 통과**시킨다. 즉 D의 잔액이 0원이든 마이너스든
STEP0~C 호출은 전부 정상 실행되고, DeepSeek API 실호출 비용이
플랫폼에 발생한다.

STEP0가 끝난 뒤 `settleKlaw`가 `_chargeGdcForAiUsage`로 소송가액
"3억~5억원" 구간 **35,000원 청구를 시도** → D의 잔액 부족으로
`chargeResult.ok = false` → `if (chargeResult?.ok) { ... 사건기록 생성 ... }`
조건에 걸려 **사건기록도 생성되지 않는다**. 하지만 이미 STEP0
응답은 스트리밍으로 D에게 전달된 뒤다(§새로 발견된 사항 F4 — 정산은
`ctx.waitUntil`로 응답과 분리되어 사후 처리됨). D는 STEP A/B/C도
그대로 이어서 받아 **완전한 판결문 한 편을 무료로 받는다**.

**판정**: ❌에 가까운 ⚠️ — 코드가 깨진 건 아니지만(에러 없이 "정상"
동작), 결과적으로 **잔액이 0원인 사용자가 사실상 무제한(일일
STEP_LIMIT=3회까지) 고액 사건도 전부 공짜로 이용 가능**하다. 사건기록이
안 남으므로 D가 "다시 생성"을 눌러도 매번 새로 35,000원 청구를
시도하지만 매번 잔액 부족으로 실패하고, 매번 무료로 결과만 받는
사이클이 하루 3번까지 반복 가능하다. 전편·현재 코드 주석
(`_gdcFreeQuotaGate` 상단, "K-Law 등 요청 크기가 큰 티어가 이 게이트를
타게 되면 이 단순화를 재검토해야 한다")이 우려한 지점이 **"문턱값
3원이 너무 낮다"가 아니라 "게이트 자체가 완전히 꺼져 있다"**는 더
심각한 형태로 이미 실현돼 있다는 뜻이다.

## 시나리오 5 — 순차적 재생성 중 정산 지연으로 인한 이중청구 가능성

**사건**: E는 이혼 및 재산분할 소송(소송가액 8천만원, "3천만~1억원"
구간 15,000원)의 STEP0~C를 받은 뒤, 결과가 마음에 안 들어 "다시 생성"을
누른다. 전편 시나리오17은 이 경로를 "거의 동시에 병렬 클릭"이라는
악의적/우연적 더블클릭 상황으로 한정했는데, 실제 코드를 보면 그보다
넓은 창구가 있다.

**진행**: STEP0의 응답 처리부(스트리밍 경로):
```js
const usageTask = _parseUsageFromStream(forUsage).then(usage => _recordAiUsage(...));
if (ctx?.waitUntil) ctx.waitUntil(usageTask); else usageTask.catch(() => {});
return new Response(forClient, { ... }); // 정산을 기다리지 않고 즉시 반환
```
즉 **STEP0의 HTTP 응답(판결문 텍스트)은 GDC 차감·`klaw_case_charges`
기록 생성이 끝나기 전에 이미 클라이언트로 스트리밍되기 시작한다**.
클라이언트(`regenerateSameCase` → `runJudgementSim`)는 STEP0 응답을
받으면 곧바로 STEP A로 넘어가고, 사용자가 "결과가 별로다" 판단 후
재생성 버튼을 다시 누르기까지 걸리는 시간은 보통 수 초 이상이라
실제로는 첫 정산이 이미 끝나 있을 가능성이 높다 — 다만 **L1
PocketBase 응답 지연·Worker 콜드스타트·네트워크 혼잡 등으로 이
`waitUntil` 작업이 예상보다 오래 걸리는 경우**, 사용자가 정상적인
속도로(더블클릭이 아니라) 두 번째 STEP0를 트리거해도 첫 번째 사건기록이
아직 안 써진 시점에 `_klawFindCaseCharge`가 "기록 없음"으로 판정할 수
있다.

이 경우: 두 번째 STEP0도 `_klawFlatFee` 판정을 다시 통과해
`_chargeGdcForAiUsage`로 **15,000원을 한 번 더 차감** → 이후
`_klawCreateCaseCharge`가 `klaw_case_charges`의 (guid, case_id) 유일
인덱스 제약으로 실패 → E는 **GDC 30,000원이 빠져나갔는데 사건기록엔
1건(첫 번째 것)만 남는다**. 화면엔 "추가 요금 없음"이라고 안내됐던
재생성인데 실제로는 이중 청구된 것이다.

**판정**: ❌→⚠️ (전편과 동일 결론이지만, 트리거 조건이 "악의적 동시
클릭"보다 넓다는 게 이번 추적의 새 발견 — §새로 발견된 사항 F4). 발생
빈도는 낮게 유지되겠지만(정상적인 재생성 간격이면 대개 안전), L1 응답
지연이 잦아지는 시점(예: 트래픽 급증, hanlim 재시작 직후)에는 발생
확률이 올라간다.

## 새로 발견된 사항

- **F1 — 전편 시나리오 12는 클라이언트로 도달 불가능한 죽은 경로다.**
  `webapp.html`의 `cs.claimAmount || null`이 `0`을 falsy로 처리해 `null`로
  치환한다. 서버가 실제로 `claim_amount_krw: 0`을 받는 경우는 없고,
  소송가액이 0이거나 처음부터 없는(형사 등) 사건은 전부 시나리오 3의
  "무과금+무기록" 경로로 수렴한다. 전편이 "①그대로 최소요금 부과"로
  남겨둔 정책 미결정 사항은, 코드 현황만 놓고 보면 **이미 사실상
  ③(비금전 사건은 사실상 전부 면제)으로 귀결돼 있다** — 의도한
  정책인지 재확인 필요.
- **F2 — "무료 재생성"은 GDC 기준으로만 무료다.** `recordStep()`이
  `settleKlaw` 최상단에서 과금 성공/실패/스킵 여부와 무관하게 항상
  실행돼 `KLAW_USER_DAILY_STEP_LIMIT`(1일 3회)를 소진시킨다. 재생성
  버튼 문구 "추가 요금 없음"은 정확하지만 불완전한 안내다 — 일일
  생성횟수 한도까지 함께 깎인다는 사실이 UI 어디에도 없다.
- **F3 — GDC 사전 잔액 확인 게이트가 현재 전면 비활성 상태다.**
  `FREE_QUOTA_ENFORCEMENT_ENABLED = false`로 인해 `_gdcFreeQuotaGate`는
  guid만 있으면 무조건 통과시킨다. K-Law 정액요금(최소 5,000원, 최대
  100,000원)은 이 게이트를 거치지도 못한 채 사후 결제 실패로만
  걸러지므로, **GDC 잔액이 0원인 사용자도 일일 STEP_LIMIT(3회)까지는
  고액 사건을 포함해 전부 무료로 이용 가능**하다. 코드 주석이 예상한
  "문턱값이 K-Law엔 너무 낮다"보다 심각한 "게이트 자체가 꺼져 있다"는
  현재 상태.
- **F4 — STEP0 정산이 HTTP 응답과 비동기로 분리돼 있어, 순차적인 정상
  재생성도 타이밍에 따라 이중청구 레이스에 노출될 수 있다.** 전편
  시나리오17이 "동시 클릭"으로 한정했던 위험이, 실제로는 `ctx.waitUntil`
  기반 사후 정산 구조 때문에 클릭 타이밍이 아니라 **L1 응답 지연**에
  좌우되는 더 넓은 창구임을 확인했다.

## 권장 조치 (우선순위 순, 구현은 이 문서 범위 밖)

1. **F3(게이트 비활성)이 가장 시급** — K-Law처럼 건당 단가가 큰
   서비스에 한해서만이라도 `_gdcFreeQuotaGate`를 활성화하거나, K-Law
   전용으로 별도의 사전 잔액 확인(예: 최소 5,000원 문턱값)을
   `handleKlawRelay` 안에 추가하는 걸 검토할 것.
2. **F2** — `regenerateSameCase` 버튼에 남은 일일 생성 횟수를 표시하거나,
   최소한 429 발생 시 "오늘 판결 생성 한도를 모두 사용했습니다(재생성
   포함)"처럼 재생성도 한도에 포함된다는 걸 명시하는 에러 문구로 보강.
3. **F1** — 형사·소년보호 등 비금전 사건 유형에 대한 과금 정책을
   명시적으로 결정(무료로 유지할지, 별도 정액을 신설할지). 결정
   이후엔 클라이언트가 `0`을 `null`로 치환하는 현재 동작이 그 정책과
   일치하는지 재점검.
4. **F4** — `_klawCreateCaseCharge` 실패(유일 인덱스 위반)를 감지했을 때
   자동 환불 경로를 추가하거나, 최소한 이런 이중청구가 발생한 건을
   운영자가 조회할 수 있는 로그/대시보드 쿼리를 마련.

이 문서는 라이브 스모크테스트 이전 단계의 코드 추론이다. 특히 F3(게이트
비활성)은 영향도가 크므로, 실제 배포 환경에서 GDC 잔액 0원 테스트
계정으로 재현 확인을 우선순위 높게 권장한다.
