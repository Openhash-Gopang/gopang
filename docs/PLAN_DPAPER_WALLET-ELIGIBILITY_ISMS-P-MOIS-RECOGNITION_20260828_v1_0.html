전자증명서 지갑용(+신청용) API 자격 확보 추진계획

혼디는 사용자 데이터를 서버에 보관하지 않고 중계만 하며, 전자증명서는 사용자 본인의 PDV(로컬 IndexedDB)에 저장하는 구조를 취한다. 이 구조는 전자증명서_서비스_연계안내서(2024.09)가 정의하는 "지갑용" 연계와 본질적으로 같으나, 지갑용 참여자격 8개 항목 중 혼디가 즉시 충족하는 항목이 없다 — 남은 현실적 경로는 ⑥ ISMS-P 인증 취득과 ⑧ 행정안전부장관 개별 인정 둘뿐이다. 이 문서는 두 경로를 동시에 추진하는 이유와 절차, 그리고 인증 완료 이전 공백 기간의 임시조치를 정리한다.

대상 API 지갑용 + 신청용 (신청용은 지갑용 승인 종속) 근거 문서 전자증명서 서비스 연계안내서 v3.0 §1-3, 이용약관 제6조 상태 초안 — KISA/행안부 실제 문의 결과로 갱신 필요
Overview
왜 지갑용 API 자격이 필요한가

혼디는 사용자가 정부 기관과 주고받는 문서를 중계만 하고 서버에 보관하지 않는다. 전자증명서를 발급받아 IndexedDB 기반 로컬 볼트(idv-store.js의 gopang_idv_vault)에 저장하고, 필요할 때 다시 꺼내 제출하는 이 흐름은 전자증명서 안내서가 정의하는 지갑용("이용자가 전자증명서를 열람·발급·제출할 수 있도록 정부 전자문서지갑 기능을 앱에 구현")과 구조적으로 동일하다.

신청용은 별도 트랙이 아니다. 안내서 3절은 신청용의 대상을 "지갑용과 동일"로 명시하고, 지갑용 연계 승인을 이미 받은 유통기관 앱에서만 신청용을 추가로 신청할 수 있도록 규정한다. 따라서 이 계획은 지갑용 승인을 1차 목표로 삼고, 승인 직후 신청용을 연이어 신청하는 순서로 짠다.

정직하게 밝힘 — 이 평가의 한계
위 수치는 일반 기업 대상 공개 자료를 근거로 한 잠정치이며, 혼디처럼 "서버에 개인정보를 저장하지 않는" 특수 구조가 ISMS-P 심사에서 어떻게 취급되는지는 실제 KISA 사전상담 없이는 확정할 수 없다. 오히려 서버 저장이 없다는 점이 일부 심사 항목(예: 개인정보 암호화 저장, 접근권한 관리)을 "해당 없음"으로 단순화시켜 유리하게 작용할 가능성과, 반대로 표준 심사 항목 자체가 이런 구조를 전제하지 않아 심사관 재량에 따라 해석이 갈릴 가능성이 공존한다. 1단계 실행계획(§단계별 실행계획)의 첫 항목을 "KISA 사전상담"으로 잡은 이유가 이것이다.
P3 · 대안 경로 및 권고
왜 "택일"이 아니라 "병행"인가

P2 평가 결과 어느 트랙도 단독으로 확실하다고 볼 근거가 없다 — 트랙 A는 절차는 확실하지만 혼디 구조와의 정합성이 불확실하고, 트랙 B는 구조적 정합성은 높지만 선례가 없어 성사 여부 자체가 불확실하다. 이 상황에서 하나를 선택하고 실패 시 처음부터 다시 시작하는 것은 시간 손실이 크므로, 주피터님이 이미 제시한 대로 두 트랙을 동시에 진행하는 것이 이 시점의 최선 경로로 판단한다.

  • 선행 우선순위 — 트랙 B(행안부 개별 인정)를 먼저 접촉한다. 비용이 들지 않고, 제주도 시범사업 관계라는 이미 확보된 협상 지렛대를 쓸 수 있으며, 결과와 무관하게 이 협의 과정에서 트랙 A 심사 시 유용할 "행안부 측 소명 논리"를 확보할 수 있다.
  • 병행 착수 — 트랙 A(ISMS-P)는 트랙 B의 결과를 기다리지 않고 동시에 준비를 시작한다. 관리체계 구축·운영 최소 2개월이라는 자체 소요기간이 있어, 순차 진행 시 전체 일정이 길어진다.
  • 중간 목표 재검토 지점 — 트랙 B에서 행안부 사전 문의 결과가 나오는 시점(§단계별 실행계획 1단계 종료)에 두 트랙의 우선순위를 다시 판단한다. 행안부가 개별 인정에 긍정적이면 트랙 A 준비 강도를 낮추고, 부정적이면 트랙 A에 자원을 집중한다.

이 권고 이후에도 최종 결정은 주피터님의 몫이다. 이미 "6, 8번 항목을 각기 진행"하겠다고 결정하셨으므로, 아래 실행계획은 그 결정을 그대로 지원하는 형태로 짰다.

Track A
ISMS-P 인증 취득 경로

절차 개요 (KISA 공식 안내 기준, 4단계)

  1. 관리체계 구축·운영 — 인증 기준에 맞는 정보보호·개인정보보호 관리체계 수립, 최소 2개월 이상 실제 운영 증적 확보
  2. 인증심사 신청 — 인증 신청 공문, 인증 신청서, 인증 명세서, 사업자등록증을 인증기관에 제출. 희망 심사일 최소 8주 전 신청 권장
  3. 인증심사(서면+현장) — 통상 1~2주 소요, 규모·범위에 따라 변동
  4. 결함보완 및 인증 의결 — 결함사항 보완 최대 100일 이내, 인증위원회 심의·의결 후 인증서 발급

인증 이후에도 매년 사후심사(1년 차·2년 차), 3년 차에 갱신심사가 이어지는 3년 주기 유지관리 의무가 발생한다는 점을 자원 계획에 반영해야 한다.

검토할 완화 제도
중소기업 규모·특성에 맞춰 인증 항목과 비용을 낮춘 "ISMS/ISMS-P 간편 인증 제도"가 존재한다. 혼디의 현재 조직 규모라면 이 제도의 적용 대상 여부를 가장 먼저 확인해야 한다.

Track B
행정안전부장관 개별 인정 경로

Interim Measure
인증·인정 획득 이전의 임시조치 — 관제탑 보강과의 연결점

트랙 A·B 모두 최소 수개월이 걸리는 절차이므로, 그 사이 사용자가 전자증명서를 필요로 하는 상황 자체는 계속 발생한다. 이 공백을 메우기 위한 둘째 방향은 혼디가 API로 직접 발급·제출을 대행하는 대신, 사용자 본인이 정부24·카카오톡·네이버 등 기존 채널로 증명서를 발급받아 자신의 PDV(또는 정부 표준 전자문서지갑)에 저장하도록 단계별로 안내하는 것이다.

이 안내 절차의 구체적 설계(관제탑 원칙에 어떻게 편입할지, 어느 SP 계층에 배선할지)는 이 문서의 범위가 아니며, 다음 세션에서 "관제탑 원칙 보강" 작업으로 별도 진행한다. 여기서는 두 작업의 관계만 명시해 둔다 — 트랙 A·B가 완료되면 이 임시조치는 API 기반 자동 발급·제출로 대체되고 안내형 흐름은 폐기 대상이 된다.

1단계 — 사전 확인KISA/심사기관 사전상담 신청, 간편 인증 대상 여부 확인1600-8613 전화 사전협의두 경로 각각의 실제 소요기간·비용·가능성에 대한 확인된 정보(이 문서의 P2 표를 확정치로 갱신)
2단계 — 병행 준비관리체계 구축 착수(담당자 지정, 정책·규정 문서화, 최소 2개월 운영)정식 협의 요청 공문 작성·제출ISMS-P 관리체계 운영 증적, 행안부 협의 공문 및 회신
3단계 — 재평가트랙 B 회신 결과를 반영해 우선순위 재조정(§P3 참조)갱신된 우선순위 결정 기록
4단계 — 심사/승인인증심사 신청 → 현장심사 → 결함보완 → 인증 획득(승인 시) 지갑용 연계 신청서(별지 제2호) 제출ISMS-P 인증서 또는 행안부 승인 통지
5단계 — API 신청자격 확보 즉시 지갑용 API 이용신청 → 승인 후 신청용 API 추가 신청지갑용 API Key, 신청용 API Key

각 단계의 실제 착수일·완료일은 1단계 사전 확인 결과가 나오기 전까지는 확정하지 않는다 — 특히 트랙 B는 공식 처리기간이 없어 임의로 날짜를 박아 넣는 것 자체가 부정확한 계획이 된다.

항목유의할 점
두 트랙 동시 진행 비용ISMS-P 준비(문서화·컨설팅)와 행안부 협의를 동시에 진행하면 인력 부담이 커진다 — 1단계 결과가 나오는 즉시 우선순위를 좁힐 것.
ISMS-P 구조 정합성서버 미보관 구조가 인증 기준에서 유리하게도 불리하게도 해석될 수 있다는 점을 사전상담에서 반드시 확인할 것 — 확인 없이 관리체계 구축부터 시작하면 헛수고가 될 위험.
행안부 개별 인정 전례 부재성사 여부를 예측할 근거가 없다. 이 트랙에 자원을 과도하게 집중하지 말고 트랙 A를 동시에 준비할 것.
임시조치의 성격사용자 안내형 관제탑 절차는 어디까지나 공백기 임시조치다 — 두 트랙 중 하나가 완료되면 API 자동화로 전환하는 것을 전제로 설계해야 한다(별도 문서에서 다룸).
문서 갱신 규칙이 문서의 P2 평가표·실행계획 표는 실제 문의·심사 결과가 나올 때마다 잠정치를 확정치로 갱신할 것 — 새 버전 번호를 올리지 말고 이 문서를 직접 수정.
