INFRA SNAPSHOT — 2026-08-10 GDC 세션

한림읍 테스트가 끝나면, 여기부터 다시 읽을 것

GDC 충전/차감 자동화 작업(방식A 오픈뱅킹 폴링 + 방식B PG 가상계좌 웹훅)을 진행하던 중, PocketBase 7노드 인프라의 실제 상태를 직접 확인할 필요가 생겼다. 그 과정에서 hanlim을 제외한 6개 노드가 2026-07-15부터 마이그레이션이 밀린 채 멈춰있었다는 사실과, 공유 마이그레이션 폴더 구조의 함정, 그리고 이미 만들어져 있었지만 아무도 몰랐던 자동배포 파이프라인까지 하루 만에 전부 드러났다. 이 문서는 그 전체 그림을 한림읍 테스트 종료 후 전국 확장을 설계할 팀(미래의 자기 자신 포함)이 처음부터 다시 발견하지 않도록 정리한 것이다.

대상 저장소 Openhash-Gopang/gopang 관련 PR #297, #301~#305 작성 2026-08-10
Overview
이 문서가 왜 있는가

"GDC는 한림 외에 전국에 적용되어야 한다"는 방향이 확인됐지만, 실제로 확인해보니 제주 세부 지역용 6개 노드가 실사용자 0명인 채로 두 달 가까이 방치돼 있었다. 오늘은 그 상태를 안전하게 되살리려다 크래시 루프까지 겪었고, 결국 "지금은 hanlim 하나로 GDC 기능을 완성하고, 전국 확장은 별도 단계로 분리한다"는 결정으로 정리됐다. 이 결정 자체는 옳았지만, 다음에 전국 확장을 다시 시도할 사람이 오늘의 시행착오를 반복하지 않으려면 무엇을 발견했는지 기록이 남아야 한다.

이 문서를 읽어야 하는 상황
한림읍 단일 노드 테스트를 마치고 제주 세부 지역 또는 전국으로 확장을 계획할 때 / l1-aewol·l2-jeju 등 6개 노드를 다시 켤 때 / L1_NODE_MAP 기반 지역 자동배정을 재개할 때.

Incident Log
오늘 발견된 것들

① 공유 마이그레이션 폴더의 함정

7개 노드 전부 WorkingDirectory=/opt/gopang를 공유한다. PocketBase jsvm 마이그레이션 로더는 --migrationsDir 플래그가 없으면 작업 디렉터리 기준 상대경로를 보는데, 실제 "진짜" 공유 경로는 /opt/gopang/pb/pb_migrations (한 단계 더 안쪽)였다. /opt/gopang/pb_migrations는 그 경로를 가리키는 심볼릭 링크였던 것으로 보이며, 이를 모르고 "격리"(mv)했더니 링크만 이름이 바뀌고 실제 폴더는 그대로 살아있어 격리가 안 된 채 다음 재시작에 그대로 다시 읽혔다. 이 폴더에 파일 하나를 새로 넣으면 7개 노드 전부에 영향을 준다.

② 2026-07-15부터 6개 노드 마이그레이션 동결

hanlim만 157/157로 최신이고, 나머지 6개는 전부 62~64/143에서 멈춰 약 80개가 밀려 있다. 재시작을 걸면 곧바로 sql: no rows in result set 류 크래시가 나며, 그중 하나(1783500002_created_org_profiles.js 등 7건)는 "이미 있는 컬렉션을 다시 만들려는 오래된 중복 파일"이라 안전하게 skip 가능하지만, 나머지(예: updated_ledger_entries가 created_ledger_entries보다 먼저 오는 순서 꼬임)는 기계적 순차 재생이 안전하지 않다는 게 실제로 확인됐다.

재발 방지가 아니라 "재개 전 필수 확인"
이 상태는 오늘 우리 작업이 원인이 아니라 7/15부터 이미 그랬던 것이다. 6개 노드를 다시 켜기 전에는 반드시 80개 목록을 다시 진단(어떤 게 중복 skip 대상이고 어떤 게 실제 필요한지)한 뒤, hanlim 기준 스키마 동기화 방식(§전국 확장 체크리스트 참고)으로 접근할 것 — 순차 재생 시도는 이번에 두 번 다 크래시로 이어졌다.

③ 실사용자 영향은 없었음(확인 완료)

6개 노드 전부 profiles/ai_usage_log/ charge_requests 0건, guid_home_l1 레지스트리도 2026-07-07 테스트 계정 1건뿐이다. 즉 이 6개 노드는 단 한 번도 실제 트래픽을 받은 적이 없다 — "실운영 데이터가 쪼개졌을 위험"은 조사 결과 해당 없음으로 확인됐다.

④ 이미 존재하던 자동배포 파이프라인을 뒤늦게 발견

.github/workflows/deploy-pb-migrations.yml(hanlim 전용, main push 시 자동으로 pb_migrations/** 변경분만 안전 검증 후 반영 + migrate up 성공 후에만 재시작)와 deploy-worker.yml(worker.js 자동 Cloudflare 배포)이 이미 있었다. 전자의 주석에는 "2026-07-16 사고(마이그레이션 파일이 GitHub에만 있고 서버엔 한 번도 안 들어간 문제) 재발 방지용"이라고 명시돼 있다 — 오늘 우리가 겪은 것과 같은 유형의 사고가 이미 한 번 있었고, 그 교훈으로 만들어진 도구를 모르고 반나절을 수동 SSH로 씨름한 것이었다.

앞으로는 이 경로만 쓸 것
pb_migrations/*.js 변경은 PR 병합만 하면 hanlim에 자동 반영된다(§배포 파이프라인 참고). SSH로 직접 pb_migrations 폴더에 파일을 만들지 말 것 — 오늘 이 방식으로 heredoc 붙여넣기 손상, 심볼릭 링크 오판, 손상된 기존 파일(1784200001_created_public_data_usage.js, 2026-07-16 사고의 잔재로 추정) 발견까지 전부 이 수동 경로에서 비롯됐다.

Architecture Decision
한림읍 고정 잠금 — 위치와 원복 방법

GDC 기능이 hanlim 하나에서만 완성·검증되는 동안, 실수로라도 다른 노드로 신규 가입자가 배정되지 않도록 worker.js의 handleRegisterKey()에서 클라이언트가 뭘 보내든 무조건 hanlim으로 고정했다(PR #301).

const homeNodeId = 'KR-JEJU-JEJU-HANLIM'; // 2026-08-10 임시 고정 — L1_NODE_MAP 매핑 자체는 보존됨

전국 확장 재개 시, 이 한 줄을 원래 로직(클라이언트가 보낸 home_l1을 L1_NODE_MAP에서 조회, 없으면 hanlim 폴백)으로 되돌리기만 하면 된다 — L1_NODE_MAP 매핑 테이블(43개 읍면동 + KR + GLOBAL) 자체는 전혀 손대지 않고 그대로 남겨뒀다. 단, 그 전에 §전국 확장 체크리스트를 먼저 완료할 것.

Before You Expand
전국 확장 전 체크리스트
  • 6개 노드 마이그레이션 상태 재확인 — 오늘 이후 시간이 지났다면 SELECT COUNT(*) FROM _migrations로 각 노드 현황을 다시 확인할 것(오늘 기록은 스냅샷일 뿐).
  • 순차 재생 대신 hanlim 스키마 동기화 방식 사용 — 80개 마이그레이션을 순서대로 재생하면 순서 꼬임(§인시던트②)으로 다시 크래시 난다. hanlim의 실제 컬렉션/필드를 REST API로 조회해 부족한 부분만 추가하는 방식을 권장(작업 중 설계했던 방식, 실행 전 대화 흐름이 "전국 hanlim 고정"으로 바뀌며 미완료 상태로 남음).
  • l3-jejudo부터 우선 복구 — guid_home_l1 레지스트리(크로스노드 거래 라우팅 단일 소스)가 여기 있어, 다른 노드들의 P2P 거래·평점 기능이 이 노드에 의존한다.
  • l4-kr/l5-global 우선순위 검토 — "전국"의 실제 코드상 목적지는 이 두 노드다. 제주 43개 세부노드보다 먼저 검증이 필요할 수 있음.
  • 한림읍 고정 잠금 원복 — §아키텍처 결정 참고, handleRegisterKey() 한 줄.
  • 배포 파이프라인 노드별 확장 — §배포 파이프라인 참고.
  • nginx 프록시 대상 정합성 확인 — 52개 포트 설정 중 실제 프로세스가 없는 45개(주로 제주 세부 읍면동)는 그 시점에 실제로 프로비저닝할지, 매핑에서 제거할지 결정 필요.
  • GDC 자동충전(방식A/B) 재검토 — 지금은 hanlim 단일 노드 전제로 L1_DEFAULT에 하드코딩돼 있다. 노드가 늘어나면 사용자의 홈 노드에 따라 충전 요청을 라우팅할지, 아니면 GDC 원장 자체를 계속 hanlim으로 중앙화할지 아키텍처 결정이 먼저 필요하다.
