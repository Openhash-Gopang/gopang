L1(hanlim) 서버 유료 전환·마이그레이션 + 온디맨드 기동 시스템

Always Free(E2.1.Micro, 1/8 OCPU·1GB)로 운영되던 L1 서버를 유료(E4.Flex, 1 OCPU/8GB)로 전환하는 과정에서 겪은 시행착오와, 42개 L1 노드를 상시 기동 대신 온디맨드(유휴 자동 종료 + 요청 시 자동 기동) 방식으로 전환한 작업을 정리한다. 실패한 경로와 그 원인도 그대로 남겨, 다음에 비슷한 작업을 할 때 같은 시행착오를 반복하지 않도록 하는 게 이 문서의 목적이다.

대상 인스턴스 l1-hanlim → l1-hanlim-new (152.67.196.86) 신규 사양 VM.Standard.E4.Flex, 1 OCPU / 8GB, 월 약 $27.4 영향 범위 hanlim + L1 42개 + L2 2개 + L3 1개 + L4 1개 + L5 1개(총 48개 노드)
Overview
개요 — 왜 유료 전환이 필요했나

기존 l1-hanlim은 Oracle Cloud Always Free 등급의 VM.Standard.E2.1.Micro (1/8 OCPU 버스터블, 1GB RAM)로 운영되고 있었다. 43개 L1 노드 중 hanlim만 실질적으로 가동 중이었고 나머지 42개 + L2~L5는 지연 인스턴싱 설계에 따라 대부분 꺼져 있는 상태였다. 서비스가 유료 전환을 앞두고 있어 "순간 접속자 10명" 수준의 안정적인 처리 능력을 확보하기 위해 사양 확장을 진행했다.

예산은 첫 달 테스트 목적으로 월 $30 이하로 제한했고, 이 기준에서 1 OCPU / 8GB(월 약 $27.4)를 선택했다. 둘째 달부터 실사용 데이터를 보고 사양을 재조정할 계획이다.

① Discovery
리사이즈 불가 발견 → 신규 인스턴스 생성으로 전환

당초 계획은 기존 인스턴스를 정지하고 Shape만 바꾸는 단순 리사이즈였다. 그런데 OCI 콘솔에서 "Edit → Change Shape" 메뉴 자체가 안 보여서 한참 헤맨 끝에, Oracle 공식 문서에서 VM.Standard.E2.1.Micro는 애초에 shape 변경이 불가능한 목록에 포함된 shape라는 걸 확인했다.

교훈
Always Free 등급의 Micro shape는 콘솔에서 Edit 메뉴를 아무리 찾아도 안 나온다. 다음에 비슷한 리사이즈 요청이 오면, UI를 뒤지기 전에 대상 shape가 변경 가능 목록에 있는지부터 공식 문서로 먼저 확인할 것.

이후 방향을 "새 인스턴스 생성 → 데이터 마이그레이션 → DNS 전환"으로 바꿨다. OCI CLI(Windows PowerShell, MSI 설치)를 새로 세팅해서 진행했다 — 콘솔 UI보다 정확한 파라미터로 한 번에 처리 가능해서, 이후 신규 인스턴스 생성 작업은 CLI로 진행하는 게 안정적이었다.

② False Alarm
Reserved IP 전환 헤맴 — 결국 불필요했던 절차

리사이즈(정지→shape변경→시작) 과정에서 Ephemeral(임시) 공인 IP가 바뀌면 DNS 전체가 죽을 수 있다는 우려로, Ephemeral IP를 Reserved(고정)로 전환하는 절차를 콘솔에서 찾아 상당한 시간을 썼다. VNIC 상세 페이지, "Reserve public IP address" 마법사 등 여러 경로를 시도했으나 전부 "새 IP를 발급"하는 기능이었고, 기존 IP를 유지한 채 타입만 Reserved로 바꾸는 기능은 Ephemeral/Reserved가 애초에 서로 다른 오브젝트라 존재하지 않는다는 걸 뒤늦게 확인했다.

이후 Oracle 공식 문서를 재확인한 결과, ephemeral public IP는 VNIC이 detach/삭제되거나 인스턴스가 완전히 terminate될 때만 사라지고, 단순 Stop만으로는 바뀌지 않는다. 즉 이 절차 전체가 처음부터 불필요했다.

교훈
"IP가 바뀔 수 있다"는 우려가 들면, 콘솔에서 전환 경로부터 찾기 전에 공식 문서에서 "어떤 조건에서 ephemeral IP가 사라지는가"부터 먼저 확인할 것. 결과적으로 이번 마이그레이션에서는 새 인스턴스를 만드는 방향으로 갔기 때문에 (기존 IP 자체가 아예 새 IP로 바뀌는 시나리오였음) 이 문제는 다른 형태로 다시 등장하지 않았지만, 향후 "정지 후 shape 변경이 가능한" 인스턴스를 다룰 때는 이 조사가 시간 낭비였다는 걸 기억해둘 것.
③ Execution
데이터 마이그레이션 + DNS 전환

진행 순서

  1. Always Free → Pay As You Go 계정 업그레이드 (카드 등록 시 $100 상당 검증 홀드는 정상 절차)
  2. OCI CLI로 VM.Standard.E4.Flex(1 OCPU/8GB) 신규 인스턴스 생성 — 기존과 같은 VCN/subnet, 같은 SSH 공개키 재사용, x86 이미지(aarch64 아님) 선택
  3. 임시 SSH 키 쌍을 생성해 기존 서버 → 새 서버 간 직접 연결을 뚫고 rsync로 /opt/gopang 전체(255MB, 455개 파일) 이전
  4. systemd 유닛 파일 48개, nginx 설정, Let's Encrypt 인증서 이전
  5. 새 서버 iptables에 80/443 인바운드 규칙 수동 추가 (Oracle 표준 이미지는 22번만 기본 허용)
  6. DNS를 건드리기 전, curl --resolve로 새 IP를 강제 매핑해 도메인+SSL+nginx+PocketBase 전체 경로 사전 검증
  7. Cloudflare에서 l1-hanlim.hondi.net A레코드를 새 IP로 전환 (Proxy status는 기존과 동일하게 "DNS only" 유지)
주의
Oracle 표준 Ubuntu 이미지는 iptables에 22(SSH)번만 기본 허용되어 있다. 신규 인스턴스를 만들 때마다 80/443을 수동으로 열어야 한다는 걸 잊지 말 것 — nginx가 정상 기동돼도 이 규칙이 없으면 외부에서 전혀 접속이 안 되는데 로그에도 단서가 잘 안 남아 원인 파악에 시간이 걸린다.
④ Bug Found

시도했으나 실패한 우회

_migrations 테이블에 두 파일 모두 "적용됨"으로 수동 기록해 실행 자체를 건너뛰는 방식(예전 hanlim 사건 때 쓰던 방법)을 빈 DB에 시도했으나, 건너뛴 마이그레이션이 만들었어야 할 테이블이 실제로는 없는 상태라 다음 마이그레이션(1783500004_seeded_ bankruptcy_procedure_data.js 등)이 빈 테이블을 찾다가 연쇄적으로 또 실패했다. 이 우회법은 기존 데이터가 있는 DB에만 유효하고, 빈 DB에서 처음부터 마이그레이션을 재생하는 상황에는 안 맞는다.

최종 해법

hanlim 자체는 전체 마이그레이션을 순서대로 통과해 이미 최신 스키마를 갖춘 상태였으므로, hanlim의 완성된 data.db(데이터는 비어있고 스키마만 완성된 상태)를 나머지 47개 노드 전체에 그대로 복제하는 방식으로 해결했다. 마이그레이션을 다시 재생할 필요 자체가 없어져 47개 전체가 문제없이 통과했다.

남은 과제
이 중복 마이그레이션 쌍 자체는 아직 코드베이스에 그대로 남아있다. 지금은 "완성된 DB를 복제"하는 방식으로 우회했을 뿐이라, 향후 새 노드를 처음부터 프로비저닝(빈 DB에서 마이그레이션 재생)해야 하는 상황이 오면 동일한 문제가 재발한다. 중복 파일 3쌍 중 하나씩을 정식으로 제거하거나 통합하는 정리 작업이 별도로 필요하다.
⑤ Incident
47개 동시 기동 시도 → CPU 과부하로 전멸

스키마 문제 해결 후 47개 서비스를 systemctl start로 배치 기동(11개씩 4배치)했을 때는 문제없이 다 떴다. 그런데 이후 게이트웨이 작업 검증 과정에서 47개를 한꺼번에 재기동하는 상황이 발생했고, 1 OCPU(2 vCPU 스레드) 위에서 47개 Go 프로세스가 동시에 마이그레이션 체크·DB 오픈을 시도하면서 load average가 95까지 치솟아 전부 포트 바인딩에 실패했다. systemctl status는 "active (running)"으로 표시했지만 실제로는 포트가 하나도 열리지 않은 상태 — systemd 상태 표시를 곧이곧대로 믿을 수 없는 상황이었다.

ss -tln으로 실제 포트 바인딩 여부를 직접 확인하는 방식으로 문제를 진단했고, pkill -9로 전부 정리한 뒤 하나 기동 → 포트 열릴 때까지 최대 15초 대기 → 확인되면 다음으로 진행하는 순차 기동 스크립트로 전환해 47개 전체를 안정적으로 올렸다.

교훈
1~2 OCPU 사양에서 수십 개의 PocketBase 프로세스를 다룰 때는 절대 배치나 일괄 기동을 쓰지 말고, 포트 바인딩을 직접 확인하는 순차 기동만 사용할 것. systemctl is-active나 systemctl status의 "running" 표시는 이 사양에서는 신뢰할 수 없는 신호다.
⑥ New System
L1 42개 노드 온디맨드 기동 시스템 신설

48개 전체를 상시 기동해보니 메모리 사용량이 8GB 중 6.5GB(여유 209MB)까지 올라가, 트래픽이 조금만 늘어도 재발 위험이 있다고 판단했다. hanlim과 L2~L5(5개, 가벼운 상위 계층)는 상시 기동을 유지하고, L1 42개는 유휴 시 자동 종료 + 요청 시 자동 기동 방식으로 전환했다.

유휴 자동 종료 — gopang-idle-shutdown.timer

  • 5분마다 /opt/gopang/ops/idle-shutdown-l1.sh 실행
  • nginx access.log에서 각 노드(/n/l1-<name>/)의 마지막 요청 시각을 확인
  • 15분(900초) 이상 요청이 없으면 systemctl stop
  • nginx 로그 없이 최근에 기동만 된 경우엔 ActiveEnterTimestamp로 대체 판단

요청 시 자동 기동 — gopang-wake-gateway.service

  • Node.js로 작성한 소형 게이트웨이, 127.0.0.1:9000에서 대기
  • nginx의 각 /n/l1-<name>/ location이 PocketBase 포트 직결 대신 이 게이트웨이로 프록시
  • 요청 도착 시 대상 포트가 열려있으면 즉시 프록시, 닫혀있으면 sudo systemctl start 실행 후 포트가 열릴 때까지 최대 8초 대기
  • ubuntu 계정에는 gopang-pb-l1-* 서비스의 start/stop만 허용하는 좁은 sudoers 규칙(/etc/sudoers.d/gopang-idle-gateway)을 별도로 부여 — 전체 sudo 권한은 주지 않음
검증 결과
실제 도메인(l1-hanlim.hondi.net) 경로로 꺼진 노드(gujwa, jocheon)에 요청을 보내 자동 기동 → 정상 응답까지 확인했다. 시스템 적용 후 메모리 사용량은 6.5GB → 1.2GB로 내려가 6GB 이상의 여유를 확보했다.

nginx location 블록에 남아있던 rewrite ^/n/l1-<name>/(.*)$ /$1 break; 구문은 게이트웨이가 직접 경로를 파싱하는 방식과 충돌해서 전부 제거했다 — 게이트웨이가 /n/l1-<name>/... 원본 경로를 그대로 받아서, 어느 노드인지 식별한 뒤 /...만 벗겨서 PocketBase에 전달하는 구조다.

항목주의할 점
E2.1.Micro 리사이즈Shape 변경 자체가 불가능. 반드시 신규 인스턴스 + 마이그레이션 경로로 진행할 것.
Ephemeral IP인스턴스를 Stop만 하는 경우는 IP가 안 바뀐다. VNIC detach·삭제나 인스턴스 terminate 시에만 사라진다 — Reserved 전환은 대부분 불필요.
신규 인스턴스 방화벽Oracle 표준 이미지는 iptables에 22번만 기본 허용. 80/443은 매번 수동으로 열어야 함.
다중 PocketBase 동시 기동1~2 OCPU 사양에서는 배치/일괄 기동 금지. 포트 바인딩을 직접 확인하는 순차 기동만 사용할 것.
systemd 상태 신뢰도과부하 상황에서는 active (running)이어도 실제 포트가 안 열려있을 수 있다. ss -tln으로 직접 확인할 것.
마이그레이션 중복 버그procedure_maps/org_profiles/atom_rows 3쌍이 아직 코드에 남아있음. 빈 DB에서 마이그레이션을 처음부터 재생하는 상황이면 재발한다 — 완성된 스키마 파일 복제로 우회 가능하나 근본 수정은 별도 필요.
WAL 모드동시 접속자 처리 안정성의 전제 조건. PRAGMA journal_mode;로 wal 확인 후 진행할 것 (이번엔 이미 켜져있었음).
