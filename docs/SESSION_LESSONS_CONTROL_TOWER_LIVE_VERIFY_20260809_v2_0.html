② Grader Fix
마크다운 볼드체 미탐지 — 오탐·미탐 둘 다 사전에 잡고 보정

BOLD_RE를 새로 추가하되, 적용 전 오프라인 유닛테스트에서 두 가지 결함을 미리 잡았다:

오탐 — 지수 표기(x**2)를 볼드로 오판

단순한 \*\*[^*]+\*\* 패턴은 "x**2 + y**2" 같은 공학·수학 계열 텍스트에서 "**2 + y**"를 볼드로 잘못 잡았다. 마크다운 볼드는 여는/닫는 **가 통상 알파벳·숫자·밑줄에 바로 붙지 않는다는 점(앞뒤에 공백·문장부호가 옴)을 이용해 lookaround로 경계를 구분했다.

미탐 — 한국어 조사가 경계 문자 클래스에 걸림

위 lookaround에 파이썬 정규식의 \w를 그대로 쓰면 한글도 word 문자로 포함돼, "**핵심 포인트**는"처럼 볼드 뒤에 조사가 바로 붙는 흔한 한국어 패턴을 볼드가 아니라고 놓친다 — check_domain_keyword_collision.py에서 이미 한 번 발견됐던 "한국어 조사에서 \b 경계 실패"와 동일 유형의 버그였다. 경계 판정을 ASCII 영숫자·밑줄로만 좁혀서 해결했다.

일반화 가능한 교훈
한국어 텍스트에 대한 정규식 경계 판정(\b·lookaround 둘 다)에서 \w를 그대로 쓰면 한글이 섞여 들어가 예상 밖의 방식으로 매칭 범위가 넓어지거나 좁아진다. 경계 조건이 필요하면 처음부터 A-Za-z0-9_로 명시적으로 좁히는 걸 기본값으로 삼을 것 — 이번 세션에서만 이 패턴이 두 번 (볼드체 lookaround, ⑤의 원문자 판정) 반복됐다.

__밑줄볼드__는 일부러 탐지 대상에서 뺐다 — 파이썬 dunder 표기(__init__ 등)와 여는/닫는 경계가 원천적으로 구분 불가능하다는 게 오프라인 테스트로 확인됐고, 실사로 관측된 위반은 전부 **였다. 관측 근거 없는 패턴까지 욕심내다 오탐을 만들기보다 확인된 위반만 정확히 잡는 쪽을 택했다.

ASCII 번호 목록(1. 2. 3.)의 MCQ 비대칭 — 왜 손대지 않았는가

2차 배치 재검증에서 ct-wide-physician-internal-medicine이 이번엔 원문자가 아니라 ASCII 번호 ("1. G3a A2" ~ "5. G4 A3")로 같은 국시 5지선다 보기를 냈고, 기존 NUMBERED_LIST_RE(이번 세션이 새로 만든 게 아니라 원래부터 있던 정규식)가 이걸 위반으로 잡았다 — 같은 응답에 볼드(**[문제 1]**)도 있어서 최종 판정(FAIL) 자체는 결과적으로 맞았지만, ⑤에서 원문자에 준 것과 같은 "짧은 항목이면 MCQ 보기로 보고 예외" 로직을 NUMBERED_LIST_RE에도 대칭적으로 넣을지가 남은 질문이었다.

의도적 결정 — 왜 대칭으로 옮기지 않았는가
원문자(①②③)와 ASCII 번호(1. 2.)는 겉보기엔 같은 문제 같지만 위험도가 다르다고 판단했다. 원문자는 한국어 실무 문서에서 거의 전적으로 "보기 나열"에만 쓰여 길이 기준 예외를 걸어도 다른 걸 놓칠 위험이 거의 없다. 반면 1. 2. 3.는 하네스가 애초에 잡으려던 진짜 위반의 전형적 형태다("필요 서류: 1) 신분증 2) 임대차계약서 3) 사업자등록증"). 그리고 이 문서 나열형 위반도 항목 하나하나는 짧다("신분증" 5자 안팎) — 원문자에 쓴 "항목당 평균 15자 미만이면 예외" 기준을 그대로 옮기면 MCQ 오탐은 막아도 바로 그 문서 나열 위반을 다시 못 잡는 구멍을 스스로 만드는 셈이다. 원문자 예외에서는 안전했던 기준이 ASCII 번호에서는 안전하지 않다. 게다가 지금까지 관측된 모든 MCQ 사례는 전부 볼드도 같이 써서 최종 판정 자체는 이미 맞게 나오고 있다 — 급하게 고쳐야 할 "실제로 틀린 판정"이 아직 한 건도 없다. 진짜 트리거는 "MCQ인데 볼드도 안 쓰고 번호만 써서 억울하게 FAIL나는 사례"가 실사로 나왔을 때이고, 그때는 길이가 아니라 "다음 중 가장 적절한 것은?" 같은 MCQ 문두 패턴 + 번호 목록의 조합으로 잡는 게 더 정확한 방향이라고 판단했다 — 근거 없이 선제적으로 구멍을 뚫지 않기로 했다.
⑧ Known Issue
biomedengineering — finish=stop인데 content가 빈 문자열 (미해결)

2차 배치에서 ct-wide-biomedengineering이 빈 응답을 냈는데, finish_reason이 length가 아니라 stop이었다 — ⑥의 토큰 예산 소진과는 다른 종류다. completion_tokens=161이 전부 reasoning_tokens로만 쓰였고(reasoning_content_len=281, 짧음), 모델이 추론을 짧게 마친 뒤 스스로 "끝났다"고 선언하며 답변을 한 글자도 안 냈다.

의도적으로 안 판 이유
max_tokens로는 못 고치는 종류의 실패이고, 아직 1회만 관측됐다 — 재현 여부부터 확인하는 게 먼저다. 같은 시나리오로 재실행해서 또 빈 응답이 나오면 해당 페르소나 조립 체인(professor-electrical-computer)의 실제 프롬프트 내용에 문제가 있는지 파고들고, 이번 한 번뿐이면 API 쪽 일시적 변동으로 보고 넘어간다. SESSION_LESSONS_SUBJECT_GATE_ MAX_TOKENS_20260809_v1_0.html ⑨의 professor-gap-15 flaky 케이스와 같은 판단 기준(재현 불안정한 소수 케이스에 더 파기보다 구조적 결함에 집중)을 그대로 적용했다.
⑨ Process
같은 세션에서 워크플로 이름 혼동이 세 번 반복됨

이번 세션에서만 워크플로를 잘못 실행한 시도가 여러 번 있었다 — Live Smoketest (DeepSeek, 300 scenarios)(1단계 라우팅 검증, live_smoketest.py)와 Live Smoketest — Control Tower (professor EXPERT personas)(형식 준수 검증, control_tower_live_ smoketest.py)는 스키마가 완전히 달라서, 후자용 시나리오 파일을 전자에 넣으면 KeyError: 'no'로 즉시 죽는다. 사이드바에 이름이 비슷한 워크플로가 여러 개 나란히 있는 게 근본 원인이다.

확실한 구분법
관제탑 워크플로의 "Run workflow" 입력 폼은 입력 필드가 정확히 1개이고, placeholder에 파일명 기본값만 있을 뿐 "300"이라는 숫자가 절대 나오지 않는다. "Debug: only run first N scenarios"라는 별도 필드가 보이면 100% 잘못된(라우팅용) 워크플로다. 헷갈릴 때는 사이드바 클릭 대신 URL을 직접 입력하는 게 가장 확실하다: github.com/<org>/<repo>/actions/workflows/live-smoketest-control-tower-professor.yml
