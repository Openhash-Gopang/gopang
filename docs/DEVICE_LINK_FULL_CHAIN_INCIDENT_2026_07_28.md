# PC 로그인(device-link) 전체 체인 — 콘솔 에러 하나에서 시작된 근본 원인 8건 (2026-07-28)

`webapp.html`의 콘솔 에러 스크린샷 하나("appendChild of null")에서 시작해,
디버깅하며 따라간 체인이 도메인 인프라·인증 흐름·지갑 암호화·서버 저장소
아키텍처까지 이어졌습니다. 개별 증상 하나하나는 사소해 보였지만, 끝까지
쫓아가 보니 전부 "겉보기엔 무관해 보이는 근본 원인"이 있었습니다. 이 문서는
그 전체 체인을 순서대로 기록합니다 — 앞으로 비슷한 증상을 보면 여기부터
먼저 확인할 것.

## 1. 배경 — gopang.net → hondi.net 브랜드 전환이 코드베이스에 고르게
   반영되지 않았음

최초 증상(webapp.html의 CORS 에러)의 근본 원인은 nginx가 옛 도메인
(`l1-hanlim.gopang.net`) 인증서만 갖고 있던 것이었습니다. 이걸 고치는
과정에서 "그럼 코드에도 남아있지 않을까"로 이어졌고, 실제로 **16개
K-서비스 저장소 중 5개**(특히 `security-agent.js` — 모든 서브시스템이
공유하는 스크립트)에 `gopang.net`이 하드코딩돼 있었습니다. 조직 전체를
`grep`으로 훑어 전부 제거했습니다.

**교훈**: 브랜드/도메인 전환은 "한 파일 고치면 끝"이 아니라 조직 전체를
검색해서 확인해야 함. `grep -rn "gopang\.net"` 같은 전수 검사를 전환
작업의 마지막 단계로 항상 넣을 것.

## 2. `_showDeviceMismatchNotice` — 불필요한 확인 화면 제거

기기 불일치 시 "스마트폰으로 승인하기/백업 키/닫기" 3버튼 확인 화면을
띄우고 클릭을 기다렸으나, 이 함수가 호출된 시점 자체가 이미 확정 판정이라
PC 쪽 클릭은 실질적 보안 효과가 없었습니다(실제 승인은 폰에서 일어남).
곧장 자동 진행하도록 바꾸고, 남용 방지는 서버 rate limit(§5)로 이전.

## 3. 전화번호 뒷자리 처리 — `slice(0, need)` vs `slice(-need)`

`010` 포함 입력(자동완성 등)이 앞 8자리를 취해 엉뚱한 번호가 되는 버그.
`device-link.html`이 2026-07-27에 이미 이 패턴(`slice(-need)`, 뒤에서부터)
으로 고쳐졌었는데, 자매 파일 `auth.js`(회원가입 본화면)에는 반영이 안 되고
남아 있었습니다.

**교훈**: 같은 버그를 두 곳에서 각자 고치면, 한쪽만 고치고 다른 쪽을
잊기 쉽다. 로직이 중복되면 공유 함수로 빼는 걸 우선 검토할 것.

## 4. 지갑 잠금 오탐 — `wallet_not_ready`가 영구 상태를 "일시적"으로 취급

`_issueSession()`이 `wallet_not_ready`를 반환하면 항상 "잠시 후 다시
시도해 주세요"로만 안내하고 멈췄습니다. 그런데 이 상태에는 **두 가지 영구
상태**가 섞여 있었습니다:
- `gopangWalletLocked` — 기존 지갑 복호화 영구 실패
- `gopangWalletNeedsSetup` — PC/미확인 기기라 애초에 지갑 자동 생성 안 함

둘 다 재시도해도 절대 안 풀리는데, 이 구분이 없어서 사용자가 무한 재시도
메시지에 갇혔습니다. 두 플래그를 확인해 영구 상태면 기기 불일치(device-link)
경로로 즉시 넘기도록 두 호출부(`_loginExisting`, `initAuthWithPhone`) 모두
수정.

## 5. 남용 방지 — rate limit 2단계

확인 화면을 없애면서(§2) 유일한 마찰이 사라졌으므로, 서버(`handleDeviceLinkInit`)
에 명시적 rate limit을 신설:
- 전화번호(피해자)당 시간당 N회 — 같은 사람 반복 괴롭힘 방지
- 발신 IP당 시간당 N회 — 번호를 순차로 훑는 스크립트형 열거(enumeration) 방지
  (①만으로는 번호당 한도 안에서 서로 다른 번호 수천 개를 시도하는 공격을
  못 막음 — 실제 MFA push-bombing 공격과 동일 패턴)

개발 중 자신의 반복 테스트가 스스로 걸리는 문제가 있어 한도를 상향 조정.

## 6. 지갑 엔트로피 근본 결함 — `navigator.userAgent`를 암호화 키로 사용

`_deviceEntropy()`가 `navigator.userAgent + 고정salt`를 SHA-256 해싱해
로컬 지갑 암호화 키로 썼습니다. 그런데 UA는 "동일 기기·동일 브라우저"에서도
고정값이 아닙니다 — DevTools 기기 에뮬레이션 전환, 브라우저 자동 업데이트,
Chrome의 User-Agent Reduction 정책 등으로 언제든 바뀔 수 있습니다. 그
결과 **자기 자신이 방금 만든 지갑을 같은 세션 안에서도 못 여는** 사고가
재현됐습니다.

**수정**: UA 대신 최초 1회 랜덤 생성해 `localStorage`에 영구 저장하는
고정 비밀값(`LS_DEVICE_SECRET`)을 씀. 구버전(UA 기반)으로 이미 암호화된
지갑은 `load()` 시 자동 폴백·재암호화(마이그레이션)로 하위호환 처리.

## 7. push 알림이 폰이 아니라 PC로 (§ 재발)

`docs/PUSH_SUBSCRIPTION_MULTIDEVICE_2026_07_23.md`에서 이미 한 번 고친
문제와 같은 증상이 재발한 것처럼 보였으나, 실제로는 **"삭제된 게 아니라
애초에 진단 정보(deviceType)가 없었을 뿐"**이었습니다. 07-23 수정 이후
등록된 구독에는 `deviceType` 필드가 없어서, PC/폰 어느 쪽이 응답했는지
서버가 구분을 못 하고 있었습니다.

**수정**:
- 클라이언트(`push.js`)가 구독 등록 시 `deviceType: 'mobile'|'desktop'`
  같이 전송
- 서버가 `pushSentToMobile`(폰이 실제로 받았는지)을 `pushSent`(누군가
  하나라도 받았는지)와 분리해서 응답
- 410(Gone) 받은 죽은 구독 자동 정리(pruning)
- Web Push `TTL`을 60초 → 3600초로 상향(FCM은 TTL 지나면 재시도 없이
  그냥 폐기 — 60초는 Doze 모드·약한 신호에서 너무 짧았음, "한 번 시도해서
  실패"의 근본 원인)
- `Urgency: high` 헤더 추가(기존엔 아예 없어서 FCM 기본값 `normal`로
  배칭·지연 대상이 됐었음)

**교훈**: "예전에 고친 문제가 재발했다"고 보일 때, 진짜 재발인지 "그때의
수정이 이후 추가된 필드/경로를 놓쳐서 불완전해진 것"인지 먼저 구분할 것.
이번 건 후자였다.

## 8. device-link 세션 저장소 — Cloudflare KV의 최종적 일관성

폰이 승인(`deliver`)한 직후에도 PC의 `poll`이 최대 1분 가까이 "아직
안 옴"으로 보이는 문제. 원인은 세션 상태(`devlink:{sessionId}`)를
저장하던 **Cloudflare Workers KV가 "최종적 일관성"** 저장소였기
때문입니다 — 한 엣지에서 쓴 값이 다른 엣지에 전파되는 데 최대 60초 걸릴
수 있다고 Cloudflare가 공식 문서에 명시.

**수정**: 세션 상태만 KV에서 **Durable Object**(`DeviceLinkSessionDO`,
`wrangler.toml` v2 마이그레이션)로 이전. sessionId 하나당 DO 인스턴스
하나(`idFromName`)라 항상 같은 물리적 위치에서 읽고 써서 전파 지연 자체가
없음 — 게다가 DO는 요청을 한 번에 하나씩 순차 처리(단일 액터 모델)해서
기존 KV 버전보다 경쟁 조건에도 더 안전해짐. Rate limit 카운터(§5)는 강한
일관성이 필요 없어 KV에 그대로 둠(전부 옮기지 않은 것은 의도적 선택).

배포 과정에서 `wrangler.toml`의 DO 바인딩 커밋이 실제로는 안 올라가는
사고가 한 번 있었음(`worker.js`엔 클래스가 있는데 바인딩 선언이 없어서
`DO_NOT_BOUND`) — 두 파일을 같이 바꿀 때는 `git status`/`git diff`로
실제로 스테이징됐는지 커밋 직전에 반드시 재확인할 것.

## 9. PC↔서버 왕복 지연 — 순차 실행 vs 병렬화

"시작하기"부터 대기 화면이 뜨기까지 10~15초 걸리던 문제. 두 개의 서로
무관한 원인이 겹쳐 있었음:

1. **`handleDeviceLinkInit` 내부** — rate limit KV 조회 2번 → L1 프로필
   조회를 전부 순차 실행. 서로 의존하지 않는 작업이라 `Promise.all`로
   병렬화.
2. **`_waitForWallet()`** — `window.gopangWallet`이 채워질 때까지 100ms
   마다 최대 **15초** 폴링. 그런데 PC/미확인 기기에서는 `gopang-wallet.js`
   부트 IIFE가 `window.gopangWallet`을 **영구적으로 `null`로 확정**하는데
   (`gopangWalletNeedsSetup=true`로 대신 표시), 이 폴링 루프는 그 사실을
   몰라 매번 15초를 꽉 채우고서야 포기했음 — 실측 지연의 대부분이 여기.

`gopangWalletNeedsSetup`/`gopangWalletLocked` 플래그가 이미 서 있으면
즉시 포기하도록 수정.

**교훈**: "느리다"는 증상은 한 곳이 아니라 여러 독립적인 지연이 누적된
결과일 수 있다. 하나 고치고 끝내지 말고, 고친 뒤에도 남는 지연이 있으면
계속 프로파일링할 것.

## 10. 페이지 이동 자체의 비용 — 오버레이로 인라인화

위 최적화를 다 해도 남는 고정비용이 있었음: `webapp.html` →
`device-link.html`로의 전체 페이지 이동(`location.href`) 자체가 HTML/CSS/JS
를 처음부터 다시 받아 파싱·실행하는 비용. `_showDeviceMismatchNotice`를
페이지 이동 대신 **같은 페이지 안의 오버레이**로 리팩터링 — 요청 전송·
폴링(`visibilitychange` 기반 즉시 재폴링 포함)·복호화·로그인 완료까지
전부 `auth.js` 안에서 처리하도록 이식. `device-link.html` 자체는 삭제하지
않음 — 공용 PC 서명 요청(`sign_request`) 팝업 용도로는 여전히 필요.

## 11. 남는 한계 (통제 밖)

- **FCM(구글) 전달 시간**: Android Chrome은 Web Push 엔드포인트를 브라우저가
  강제로 `fcm.googleapis.com`으로 고정한다 — 서버 코드로 이걸 우회할 방법이
  없다(Safari→애플, Firefox→모질라도 마찬가지 구조). `Urgency: high`·
  긴 TTL 정도가 코드로 조정 가능한 전부이고, 최종 전달 시점은 폰의
  OS 전원 관리(Doze)·네트워크 상태가 결정한다.
- **`window.close()`의 신뢰성**: 알림을 탭해서 연 창은 브라우저가 스크립트의
  강제 닫기를 막는 경우가 대부분이라(악성 사이트가 사용자 탭을 마음대로
  못 닫게 하는 공통 정책), 100% 자동 닫기를 보장 못 한다 — 시도 후 실패하면
  "닫으셔도 됩니다" 안내로 전환하는 정도가 현실적 목표.

## 12. 작업 중 스스로 두 번 만든 실수 (기록용)

`str_replace`로 큰 함수를 교체하다가 옛 코드의 뒷부분(닫는 괄호 등)을
놓쳐 고아 코드 조각이 남는 실수를 **두 번** 했음(`auth.js`의
`_showDeviceMismatchNotice`, `gopang-wallet.js`의 `load()`). 둘 다
`node --check`만으로는 안 잡히고(문법상 우연히 유효했음), `git diff`로
직접 리뷰해야 발견됐다.

**교훈**: 큰 함수를 통째로 교체할 때는 `node --check` 통과만 믿지 말고,
편집 직후 반드시 `git diff`로 정확히 의도한 라인만 바뀌었는지 눈으로
확인할 것 — 특히 옛 코드가 여러 줄에 걸친 함수 본문일 때.
