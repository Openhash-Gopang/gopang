이 문서가 왜 있는가

"가상 사건 5건 시뮬레이션 + 비용 산정·GDC 차감·무료 반복 평가"라는 단순해 보이는 요청이, 실제로는 2단계 사고실험(서사형 → 라이브)과 3개 이상의 실제 프로덕션 결함 발견·수정으로 이어졌다. 다음에 K-Law 과금 로직을 다시 건드릴 사람이 같은 과정을 반복하지 않도록, 각 결함을 왜 몰랐는지와 어떻게 잡았는지 위주로 정리한다 — 특히 ⑥의 "테이블이 애초에 없었다"는 발견은, 코드 리뷰나 텍스트 추론만으로는 절대 못 잡고 실제 라이브 호출 + DB 직접 조회로만 잡을 수 있었던 종류의 결함이라는 점이 이 세션 전체의 핵심 교훈이다.

① klaw Migration
klaw Supabase→PocketBase 이관 마무리 — 동시 브랜치 경합 발견·조정

klaw 저장소 클라이언트 4개 화면(dashboard/desktop/benchmark/board.html)도 전부 worker.js 프록시(admin 토큰 인증) 경유로 전환했다. 도중에 또 다른 동시 브랜치(feat/klaw-pocketbase-client)를 발견했는데, 이쪽은 브라우저에서 L1 PocketBase를 인증 없이 직접 호출하는 설계였다 — 해당 컬렉션들의 API 규칙이 listRule: null(admin 전용)이라 실제로는 403이 날 걸로 판단해 폐기하고, 검증된 프록시 방식으로 진행했다.

서사형 사고실험 5건 — 8/12 사고실험이 못 본 4가지 새 발견

2026-08-12에 이미 파라미터 조합 20개짜리 사고실험 문서 (klaw_case_billing_thought_experiment_2026-08-12.md)가 있었다 — 이번엔 그걸 반복하는 대신, 가상의 구체적인 사건 5건(물품대금 청구, 새 사건 동시 시도, 형사사건, 고액 손해배상, 순차 재생성)을 처음부터 끝까지 따라가며 8/12 문서가 다루지 않은 클라이언트 코드 경로 (webapp.html)까지 함께 추적했다.

③ F3 Fix

기존 live_smoketest.py 계열은 DeepSeek을 직접 불러 AC-PRO-CORE 라우팅 태그를 채점하는 방식이었다. ⑥ Root Cause
발견 — klaw_case_charges 테이블이 DB에 애초에 없었음

Origin 헤더를 고친 2차 실행에서 시나리오1(F3 차단)은 PASS했지만 나머지 3개가 다른 이유로 실패했다 — 특히 F1 시나리오가 KLAW_STEP_LIMIT_EXCEEDED(이미 3회 소진)로 막혔는데, 이 테스트 guid로 성공한 STEP0 호출은 한 번도 없었다. 게다가 조금 전 잔액 20,000원을 직접 확인했던 guid의 잔액이 갑자기 0으로 조회됐다.

완전히 새 guid로 재민팅해 재현 여부부터 확인했다(오염된 guid 하나의 우연인지, 시스템 버그인지 구분하기 위해). 새 guid의 3차 실행에서 F1·F3는 정확한 금액(5,000원·10,000원)으로 PASS했지만, 재생성 무료 확인 시나리오만 다시 실패했다 — 이미 결제된 case_id로 재생성했는데도 서버가 "새 사건"으로 오판해 재청구를 시도한 것.

gopang 저장소에서 klaw_case_charges 컬렉션을 만드는 마이그레이션 파일 자체를 찾아봤더니 존재하지 않았다. SSH로 L1(hanlim) 서버에 직접 접속해 sqlite3로 확인한 결과도 동일 — 테이블이 DB에 없었다.

실제 파급 — "무료 재생성"이 한 번도 작동한 적이 없었음
_klawCreateCaseCharge(기록 생성)는 실패를 console.error로만 로그하고 클라이언트 응답에는 영향을 주지 않게 설계돼 있었다. 그 결과 _klawFindCaseCharge는 매번 "기록 없음"을 반환했고, 2026-08-11/12 신설 이후 모든 재생성이 매번 새로 과금되고 있었다 — 아무도 몰랐던 건 에러가 조용히 삼켜지는 구조였기 때문이다.
⑦ F4 Fix
F4 — 이중과금 레이스를 "선점 후 처리"로 재설계

테이블을 만들면서 F4(②에서 문서화만 하고 보류했던 레이스)도 함께 고쳐야 했다 — 테이블이 없는 동안엔 이 레이스가 실제 문제를 일으킬 수 없었지만(항상 "기록 없음"이었으므로), 테이블을 고치면 그대로 노출되는 구조였기 때문이다. 주피터의 요구도 명확했다 — "레이스 창구 자체가 존재하면 안 됩니다."

기존 순서(조회→과금→기록)를 선점 후 처리로 뒤집었다. (guid, case_id) 복합 유일 인덱스에 대한 INSERT 성공 여부 자체를 원자적 락으로 쓴다 — 두 요청이 거의 동시에 도착해도 SQLite가 INSERT를 직렬화하므로 물리적으로 하나만 성공한다. "확인 시점"과 "행동 시점" 사이의 간격이라는 레이스의 근본 조건 자체가 사라진다.

단계기존(레이스 있음)재설계(레이스 없음)
1기록 존재 여부 조회기록 선점 시도(INSERT, fee_krw=0 placeholder)
2없으면 GDC 과금INSERT 성공 시에만 GDC 과금
3과금 성공하면 기록 생성과금 성공 시 placeholder를 실제 금액으로 확정(PATCH)
실패 처리기록 생성 실패는 로그만(원장 불일치 방치)과금 실패 시 예약을 롤백(DELETE)해 다음 시도가 정상 재시도 가능

누락됐던 klaw_case_charges 마이그레이션도 처음부터 이 유일 인덱스를 포함해 다시 작성했다(1787600001).

⑧ Final Verification
최종 재검증 — 4/4 LIVE-PASS

마이그레이션은 hanlim의 nohup 실행 프로세스가 재시작 없이도 자동 반영했다(sqlite3로 테이블·유일 인덱스 둘 다 직접 확인). 완전히 새로운 테스트 guid를 다시 민팅해 4개 시나리오 전체를 재실행했다.

Lessons
교훈

텍스트 사고실험과 라이브 검증은 서로 다른 종류의 결함을 잡는다. 서사형 사고실험(②)은 코드를 읽는 것만으로 F1~F4를 찾아냈지만, "테이블이 애초에 존재하지 않는다"는 결함은 코드가 전제로 삼은 인프라 상태 자체가 틀렸던 경우라 실제로 호출해보고 DB를 직접 열어보지 않으면 원리적으로 발견할 수 없었다. 두 방법론을 같이 쓰는 게 왜 필요한지 이번 세션이 명확히 보여줬다.

에러를 조용히 삼키는 코드는 결함을 숨긴다. _klawCreateCaseCharge의 실패가 클라이언트 응답에 영향을 주지 않도록 설계된 건 "결제(mint)는 이미 끝났으니 기록 실패로 사용자 경험을 망치지 말자"는 합리적인 의도였다. 하지만 그 방어적 설계가 거꾸로 "이 기능이 애초에 작동한 적 없다"는 사실을 몇 주간 완전히 숨겼다. 부수 실패를 삼킬 땐 최소한 알림/모니터링이라도 남겨야 한다는 게 이번 사건의 교훈이다.

"레이스가 존재하면 안 된다"는 요구는 재시도 로직이 아니라 원자성으로 풀어야 한다. "확인 후 처리"는 아무리 재시도·재검증 스텝을 추가해도 확인과 행동 사이의 간격 자체는 없어지지 않는다. 유일 인덱스를 락으로 쓰는 "선점 후 처리"만이 그 간격 자체를 없앤다.
