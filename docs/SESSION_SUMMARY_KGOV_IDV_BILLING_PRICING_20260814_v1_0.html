Overview
이 문서가 왜 있는가

이번 세션은 "정부24 민원 하나를 사용자가 요청하면 kgov가 어떻게 반응하는가"라는 좁은 질문에서 시작해, 꼬리를 물고 8개의 서로 다른 작업으로 번졌다. 공통점은 매번 "이게 맞나?"라고 한 번 더 확인했더니, 실제로는 다르게 동작하고 있었거나 아예 작동한 적이 없었다는 것이다 — IDV 저장 버튼이 사용자에게 안내된 적이 없었던 것, kgov의 실제 서비스 경로에 GOV_TASK 처리가 없었던 것, 과금 신호가 51건 중 8건씩 조용히 사라지고 있었던 것, PocketBase 마이그레이션이 SSH로는 몇 시간을 파도 원인을 못 찾다가 알고 보니 GitHub Actions 자동배포가 따로 있었던 것, "SP 300개는 한 키로 캐시 못 한다"는 그럴듯한 전제가 검색 한 번에 반려된 것. 다음에 이 영역을 다시 건드릴 사람이 같은 과정을 반복하지 않도록 정리한다.

① Passport IDV
혼디 패스포트 IDV — 모델 A 확정 + 정부24 카탈로그 94건 사고실험

dpaper.kr 전자문서지갑 수취 API 신청서(서식2·서식3)를 마무리하는 중, "API 승인이 나도 그걸로 사용자 문서를 자동으로 받아올 수 있나"를 사고실험으로 짚어봤다. 결론은 모델 B(API 자동 연계)는 서버 인프라·보안 리스크가 크고, 모델 A(사용자가 직접 발급받아 채팅에 첨부 → IDV 저장)로 이미 핵심 문제가 풀려 있다는 것 — API 승인은 선택적 고도화일 뿐, 서비스를 켜기 위한 필수 관문이 아니라고 정리했다.

이어서 정부24 민원 카탈로그(총 94건, 3차에 걸쳐 첨부)를 사용자 발화로 상정한 사고실험을 진행했다. 처음엔 개별 항목을 하나씩 따라가다가, 실제로는 처리 패턴이 발급/신청/신고/조회/ 사이트가기/예약형/제도안내형/취소철회형 등 소수의 유형으로 수렴한다는 걸 발견 — 그런데 v3.20에서 "정부24 버튼 라벨로 유형을 구분하면 된다"고 설계했던 게, v3.22 실사에서 버튼 라벨 자체가 신뢰할 수 없다(예: "신고"인 민원인데 버튼은 "발급하기")는 게 드러나 근본 전제부터 뒤집혔다.

발견 — §공문서 발급 안내가 IDV 저장 버튼을 한 번도 안내한 적 없음
같은 세션 앞부분에서 만든 "IDV 저장" 버튼이, 정작 사용자에게 말을 거는 §공문서 발급 안내 섹션엔 한 줄도 언급돼 있지 않았다 — 존재해도 사용자가 우연히 발견하지 못하면 영원히 안 쓰이는 죽은 기능이었다.

SP-10을 v3.19(IDV 안내 신설)부터 계속 개정하며 예약형·환급형· 제도안내형·취소철회형·지자체별 개별등록 주의·신규재발급 구분 원칙을 차례로 추가했다 — 상세는 ②에서 이어진다.

③ Structural Gap
regional-gov.html — GOV_TASK 태그 처리가 실서비스 경로에 아예 없었음

§REQUIRED-DOCUMENTS의 GOV_TASK_SCHEMA_LOOKUP/ SUBMIT_REQUEST 태그를 처리하는 로직( _handleGovTaskTags)은 call-ai.js에 이미 있었다. 문제는 kgov가 GWP 핸드오프로 항상 새 탭 (regional-gov.html)을 열고 /gov/relay 경로를 타는데, 그 경로엔 이 태그 처리 호출이 아예 없었다 — 즉 342개 기관이 공유하는 유일한 실서비스 경로에서, kgov의 §REQUIRED-DOCUMENTS 파이프라인 전체가 한 번도 정상 작동한 적이 없었을 가능성이 있었다.

  • _handleGovTaskTags import + 태그 처리 루프 (_tagAwareSend) 신설 — 재귀 깊이 상한(5회)도 기존 메인 챗에 없던 안전장치로 새로 추가
  • 이후 task_key를 태그에서 뽑아 세션에 기억해두고 (④의 자율 과금 신호 기록용), gov_task_roundtrips 카운트까지 함께 배선
④ Autonomous Billing
자율 과금 제안 시스템 신설 — 라이브 검증 중 ctx.waitUntil 누락(51건 중 8건 신호 유실) 발견

"1천만 명 규모에서는 새 요청 유형마다 관리자에게 물을 수 없다"는 전제로 설계했다 — 기본값은 항상 안전한 쪽(기존 토큰과금 유지), 표본 50건이 쌓이면 기존 K-서비스 가격구조에서만 배율을 보간해 즉시 활성화하고, 관리자는 사후에 배치로 검토해 확정하거나 거부(거부 시 소급 전액 환불)한다.

구성요소역할
billing_signal_events신호 축적(원가·외부API 호출 여부·왕복횟수)
billing_rule_proposals자동 제안 배율, task_key당 UNIQUE로 중복 방지
_maybeProposeBillingRule표본 50건 도달 시 klaw-pro 원가 구조에서 배율 보간, 상한 5배 강제
라이브 검증에서 실제로 발견된 결함 — 신호 51건 중 8건 유실
첫 라이브 스모크테스트에서 51회 호출했는데 신호가 43건만 기록됐다. 원인은 _recordBillingSignal/ _maybeProposeBillingRule을 응답 지연 없이 fire-and-forget으로 던졌는데, Cloudflare Workers가 응답을 반환하는 즉시 실행 컨텍스트를 종료시켜 완료 전의 요청이 통째로 죽는 게 실측으로 확인됐다. ctx.waitUntil로 감싸도록 수정한 뒤 재실행하니 50/50 표본 도달, 배율 3.107(klaw-pro 기준)로 정확히 제안·활성화됐다.

승격 기준 자체에도 버그가 있었다 — gov-flash가 klaw-flash와 완전히 같은 단가라, "klaw-flash 수준 승격"이 항상 배율 1.0(사실상 무변화)로 죽어있었다. 2단계 분기를 걷어내고 klaw-pro 단일 승격 기준으로 단순화, 왕복 횟수가 원가 비교 없이 단독으로 승격을 트리거하도록 정정했다.

⑤ Deployment Archaeology
PocketBase 배포 파이프라인 수사 — SSH 수동 시도는 전부 허당, 정답은 GitHub Actions였다

새로 만든 billing_signal_events/ billing_rule_proposals가 실서버(l1-hanlim)에 반영됐는지 SQLite로 직접 조회했는데 계속 비어 있었다. migrate, history-sync, WAL 체크포인트까지 순서대로 의심하며 몇 시간을 팠지만 전부 헛다리 — 서버 프로세스가 애초에 data.db를 열어놓고 있지도 않았다(/proc/$PID/fd 로 직접 확인).

실제 정답
정식 배포 절차는 GitHub Actions가 SSH로 접속해 apply-pb-migrations.sh를 원격 실행하는 구조였다(main에 pb_migrations/** 변경이 push되면 자동 트리거). SSH에서 손으로 돌린 명령은 이 정식 경로와 무관해 계속 헛손질이었을 뿐 — PR을 열어 main에 병합하자 자동으로 반영됐고, PocketBase Admin API로 직접 조회해 최종 확인했다(파일 직접 열람이 왜 계속 어긋났는지는 끝내 완전히 규명하지 못함 — 원인 불명으로 남김).

부수적으로 어제(8/13) 만든 klaw_case_charges도 같은 이유로 실제 서버엔 반영된 적이 없었다는 게 같이 드러났다 — 배포 파이프라인 확인 자체가 오늘 세션에서 가장 시간을 많이 쓴 단일 작업이었다.

⑥ Pricing Redesign
단일 요금제(990원) 재설계 — 사업자·학생·전문직 티어 폐지

기존 4단계 요금제(시민 9,900원 / 사업자·학생 49,900원 / 전문직 99,900원)를 시민 990원 단일 요금제로 재설계 — 행정 서비스는 기본 포함, 그 외 모든 서비스(K-Law, 교수 페르소나, 사업 운영 지원 등)는 건별 과금으로 통일했다.

  • SUBSCRIPTION_TIERS를 citizen(990원) 하나로 축소
  • 존재 근거가 "학생 티어와의 가격 차별화"였던 교수 페르소나 월 8회 제한 게이팅을 완전히 폐지(항상 무제한)
  • K-Law "전문직 무료" 체크 로직은 구조만 남기고 항상 false로 귀결되도록 주석 정리(향후 재사용 대비)
  • 공개 요금 안내서(reports/hondi-pricing.html 등) 3페이지를 2페이지로 재작성, 도중 K-Law 요금표 자체가 문서(1만/2.5만/7.5만 3단계)와 실제 코드(5천~10만 8단계)가 달랐던 것도 함께 발견해 코드 기준으로 정정
  • 구독 미납 유예기간도 7일 → 1일로 별도 정정
⑦ Caching Verification
DeepSeek 캐싱 원리 검증 — "SP 300개는 API키 하나로 못 캐시한다"는 전제 반려

"SP 종류가 수백 개니 SP마다 별도 DeepSeek API 키를 써야 한다"는 제안이 나와, 구현 전에 사실관계부터 검색으로 확인했다. 결과: 전제가 틀렸다. DeepSeek 공식 문서상 캐시는 프리픽스 단위로 독립 저장되고("공통 프리픽스를 감지하면 독립 캐시 유닛으로 유지"), 축출은 개수 경쟁이 아니라 비활성 기간(몇 시간~며칠) 기준이다 — 키 하나로 수백 개 SP를 동시에 캐시하는 데 기술적 문제가 없다.

오히려 SP별로 키를 쪼개면 이미 확립된 SP-COMMON-05 H6 원칙(같은 키를 써야 UNIVERSAL-common 같은 공통 블록이 서비스 간에 캐시 공유됨)과 정반대 방향이라 손해만 크다고 정리, 진행하지 않기로 했다.

같은 맥락에서 K-Law 캐시 프리픽스 순서(_insertSystemNote)도 코드로 직접 확인했다 — 사용자별로 달라지는 위치·날짜 안내가 정적 SP 텍스트 뒤에 붙도록 이미 정확히 설계돼 있었다(의도한 대로 구현이 맞았던 드문 경우).

⑧ Tier Autopromotion
flash/pro 자동승격 — 브라우저에서 서버로 이관, 라이브 검증(경계값 포함) 6/6 PASS

복잡도 기반 flash/pro 자동승격(_resolveHondiTier)은 일반 챗에만 있고 kgov는 gov-flash로 하드코딩돼 있었다. 처음엔 "새로 안 만들고 기존 함수 재사용"으로 kgov에 배선했는데, 곧바로 이 판단 로직이 브라우저( window 의존)에만 있어 순수 함수 단위테스트조차 안 된다는 한계가 드러났다.

서버(callDeepSeek/handleGovRelay)가 이미 messages 전체를 받고 있다는 걸 확인하고, 판단 로직 자체를 worker.js로 이관 — 클라이언트가 보낸 tier 값을 더 이상 신뢰하지 않고 서버가 직접 재계산한다. kgov의 중복 배선은 걷어내고, 이제 브라우저 없이도 실제 배포 서버를 HTTP로 직접 테스트할 수 있게 됐다.

교훈

내가 방금 세운 원칙도 다음 라운드 실사로 뒤집힐 수 있다. v3.20에서 "버튼으로 유형을 구분하면 된다"고 정리했던 게, 바로 다음 실사(v3.22)에서 근본 전제 자체가 틀렸다고 드러났다. 사고실험은 한 번에 끝나는 게 아니라 라운드마다 이전 결론을 의심하는 과정이어야 한다는 걸 다시 확인했다.

"결과가 비정상적으로 좋다"는 의심은 매번 값어치가 있다. 4/4, 6/6처럼 전부 PASS가 나올 때마다 실제로 한 겹 더 파보면(billed_krw 대조, 경계값 재설계) 진짜인지 가짜인지가 갈렸다 — 이번엔 진짜였지만, 그 확인 과정 자체가 생략 가능한 절차가 아니었다.

그럴듯한 아키텍처 제안도 구현 전에 사실관계부터 확인해야 한다. "SP 300개는 키 하나로 못 캐시한다"는 전제는 상식적으로 그럴듯했지만 검색 한 번으로 틀렸다는 게 드러났다 — 만약 그대로 구현했다면 캐시 공유 이점을 스스로 없애는 방향으로 몇백 개의 키를 만들 뻔했다.

SSH로 안 되면 배포 절차 자체를 의심하라. 몇 시간을 SQLite 파일 조회로 헤맨 끝에, 문제는 명령어가 아니라 애초에 "SSH 수동 실행"이 이 프로젝트의 정식 배포 경로가 아니었다는 것이었다. 반복해서 안 되는 수동 작업은, 방법을 더 파기 전에 "이게애초에 맞는 절차인가"부터 되물어야 한다.
