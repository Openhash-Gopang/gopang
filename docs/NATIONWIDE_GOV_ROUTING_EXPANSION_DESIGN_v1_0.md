# NATIONWIDE_GOV_ROUTING_EXPANSION_DESIGN_v1.0.md
## 제주 지역 라우팅의 전국 확대 설계

작성일: 2026-08-04 | 작성자: 주피터 지시, Claude 작성

## 0. 목적

지금까지 gov-tree는 제주특별자치도 하나를 완결시키는 데 집중해왔다. 이 문서는
"AC가 사용자 발화를 분석 → ①공공행정 영역인지 판별 → ②중앙정부/지방자치단체
기능 분류 → ③(지방이면) 사용자 위치·주소지 획득 → ④해당 지자체·산하기관·부서
호출" 흐름을 **전국 17개 광역시도로 확대**하기 위해, 2026-08-04 세션에서 실제
코드를 추적해 확인한 현황과, 확장 순서·체크리스트를 정리한다.

## 1. 현황 — 이미 갖춰진 것 (코드 추적으로 확인 완료)

### 1-1. 위치 획득 → 라우팅 전달 파이프라인 (완전 배선 확인됨)

```
services/location.js
  ① 사용자 프로필 저장 주소 최우선 조회(handleProfileGet)
  ② 없으면 GPS → Kakao 역지오코딩(/geocode)
  → _userLocation 설정
      ↓
ai/call-ai.js
  매 턴 _buildLocNote()로 메인 AC 시스템 프롬프트에 주입
  GWP 라우팅 시 _buildRoutingFacts()가 currentLocation 추출
      ↓
gwp/engine.js _gwpLaunch()
  facts를 base64 인코딩해 새 탭 URL 쿼리(facts, facts_enc)로 전달
      ↓
pages/regional-gov.html (새 탭)
  facts.currentLocation → _urlFactsLocation
  → assembleGovSystemPrompt(userText, _urlFactsLocation, ...)
      ↓
gov/gov-router.js
  발화 텍스트에서 도/시군구 못 찾으면 pdvLocationHint(=_urlFactsLocation)로 2차 판별
  → _currentResolvedProvinceCode 확정
```

**이 파이프라인은 제주 전용이 아니라 처음부터 전국 대응으로 설계돼 있다**
(2026-07-20 주석: "제주는 전체 광역시도 중 하나일 뿐입니다. 완전히 걷어내고,
백지 상태에서 사용자의 발화에 대응하는 광역시도 및 시군구를 결정하도록
수정하십시오" — 주피터 지시 인용).

### 1-2. 중앙정부/지방자치 분기 구조 (형제 노드로 이미 구현)

`JEJU-NATIONAL-SP`가 `JEJU-GOV-COMMON` 바로 아래, `JEJU-DO-SP`(도청 트리)와
**형제 노드**로 존재한다. 매칭 우선순위(위에서 아래로):

| 단계 | 매칭 대상 | 위치(도) 의존 여부 |
|---|---|---|
| -0.9 | directCode(K-Search 엔티티 매칭으로 이미 확정) | 기관에 따라 다름 |
| -0.8 | policy-bodies(위원회·청 등 전국 단일기관, 지사 없음) | **무관** — 도 판별 게이트보다 먼저 실행되도록 이미 이동됨 |
| -0.5 | 도 판별 게이트("지역 미판별"이면 조기 반환) | — |
| 0 | agencies(국세청 지사 등 도별 지사형 집행기관) | **의존** — `_nationalTable()`이 `PROVINCE_TABLES[도코드]?.national`로 도 코드를 키로 씀(지사 SP가 도마다 다른 파일이라 구조적으로 불가피) |
| 0 | catalogOnly(아직 미완결 중앙기관 폴백) | 폴백 문구에 **"제주 지역 사무소"가 하드코딩**(§2-3 참조) |
| 1~ | 도청 트리(do-dept/do-agency/city/emd/org) | 의존 |

**결론**: 중앙/지방 분기 자체는 구조적으로 올바르게 구현돼 있다(정책기관은
위치 무관 우선 매칭, 지사형 기관은 도 판별 후 매칭 — 이는 버그가 아니라
지사 제도 자체의 특성을 반영한 의도된 설계다).

### 1-3. 전국 데이터 준비 상태

| 항목 | 준비 상태 |
|---|---|

| `sigungu-national-list.json`(시군구→광역 역매핑) | 전국 230개 시군구 완비 |
| `gov-common-overlay-master-data.json`(도별 오버레이: 콜센터명·번호 등) | **17개 중 4개만**(제주·경기·서울·전남광주) |
| do-dept/do-agency/city/emd/org 실제 SP 파일 | **제주만 완결**, 나머지는 도메인 템플릿 단계(3단계 원칙의 2단계) |
| entity-semantic-search 색인 | 제주 267건 스코프 파일럿만 |
| **[2026-08-04 정정]** 시군구 라우팅 키워드 골격(도메인 분류까지) | **전국 17개 도 전부 이미 존재**(`gen_nationwide_phase3.py`, 2026-07-24 생성 — `_makeMetroCityTable`/`_makeGenericCityDeptEntries`로 전국 시군구·10개 도메인 키워드 매칭까지는 됨). 단 전부 `file: null` — 실제 부서명·연락처·근거법 SP 파일은 제주 외엔 없음. 즉 "라우팅 골격은 전국 완료, 콘텐츠만 제주만 완료"가 더 정확한 현황이다. |

## 2. 전국 확대 시 반드시 처리해야 할 항목

### 2-1. `CATALOG_ONLY` 도별 파라미터화 (§1-2에서 발견)

현재 폴백 문구가 "제주 지역 사무소"로 하드코딩돼 있다. `c.ministry`처럼
`c.province_office_name` 또는 `_resolveProvinceCode()` 기반 렌더링으로 바꿔야
타 지역 사용자에게 오정보를 주지 않는다.

### 2-2. `agencies`(지사형 국가기관) 도별 데이터 부재

`PROVINCE_TABLES[도코드]?.national`은 제주 외 도에서는 사실상 빈 배열이다.
지사형 기관(국세청·경찰청·병무청 등)은 전국 데이터가 없으면 해당 도 사용자는
이 경로에서 매칭 자체가 안 된다 — §3 파일럿에서 최소 1개 도라도 채워
구조 검증이 필요하다.

### 2-3. 오버레이 13개 도 공백

콜센터명·번호 등 도별 오버레이가 없으면 `_renderGovCommonOverlay()`가
빈 문자열을 채운 문서를 내보낸다 — 최소한 파일럿 도는 이 공백부터 메운다.

## 3. 파일럿 대상 도 선정 기준 및 후보

### 선정 기준

1. **오버레이가 이미 있는 도 우선** — 경기·서울·전남광주 중에서 고르면 §2-3
   작업을 건너뛸 수 있다.
2. **행정구조가 제주와 유사한 규모의 도 우선** — 광역시(서울)보다는 도 단위가
   제주(1도 2행정시 43읍면동 구조)와 구조적으로 더 가까워 템플릿 재사용률이
   높다.
3. **인구·행정기관 수가 지나치게 크지 않은 도** — 검증 단계에서 전수 작업량이
   과도하지 않아야 한다.

### 후보 비교

| 도 | 오버레이 유무 | 비고 |
|---|---|---|
| 경기도 | 있음 | 인구·시군 수가 전국 최대급 — 파일럿 규모로는 과도 |
| 서울특별시 | 있음 | 광역시라 "행정시→읍면동" 구조 자체가 제주와 다름(구 단위) — 템플릿 재사용률 낮음 |
| 전남광주통합특별시 | 있음 | 신생 통합자치단체라 조직 개편 빈도가 높아 데이터가 빨리 낡을 위험 |
| **강원특별자치도** | 없음(신규 작성 필요) | 제주처럼 "특별자치도"이고, 도 단위 조직 구조가 제주와 유사(시·군·읍·면·동 체계) |

**제안**: 오버레이 3개 도 중 하나를 쓰면 §2-3을 건너뛸 수 있어 당장은 빠르지만,
"제주 모형이 실제로 다른 도에 재사용 가능한가"를 검증하는 게 파일럿의 본래
목적이므로, **오버레이부터 새로 만들어야 하는 도(강원 등)를 파일럿으로 삼는
편이 검증 강도가 높다.** 다만 작업량이 더 든다 — 최종 선택은 주피터님 판단이
필요하다.
