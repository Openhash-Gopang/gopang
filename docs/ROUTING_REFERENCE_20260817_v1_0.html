Overview
이 문서가 왜 있는가

혼디는 "그림자 AI"(AC)가 발화를 받아 §CORE 4단계(의도 파악 → 최적 주체 결정 → 대응 SP 검색 → 호출 또는 생성)를 거쳐 적절한 곳으로 위임하는 구조다. 하지만 그 "적절한 곳"이 24개 K-서비스인지, 62개 전문가 AI 중 하나인지, 70개 정부기관·561개 부서 중 어디인지, 아니면 표 밖의 무언가라 K-Intent부터 시작하는 5단계 오케스트레이션이 필요한지는 코드와 프롬프트를 직접 읽지 않고는 알기 어렵다. 이 문서는 그 전체 지도를 한 번에 확인할 수 있게 만든 참고 자료다 — 새로 합류하는 개발자든, 기존 라우팅 규칙이 왜 이렇게 됐는지 확인이 필요한 사람이든 여기서 시작하면 된다.

⑥ Orchestration
§ORCHESTRATION 내부 처리 — K-Intent → K-Compose → K-Execute → K-Deliver → K-Report

AC가 [CALL_KINTENT: query={발화 원문}]을 낸 뒤 벌어지는 일. AC는 이 체인의 중간 단계에 개입하지 않는다 — R0(응급) 신호 감지 시에만 [ORCHESTRATION_HANDOFF_BACK: reason=emergency]로 즉시 복귀.

K-Intent(SP-19, 403줄) — "무엇을" 확정

STEP1 goal·domain·mode(single/composite/project) 1차 추출 → STEP2 확신도 확인(막연하면 최대 2회 되물음) → STEP3 mode 확정 → STEP4 [HANDOFF_TO_KCOMPOSE]로 이관. human_authority_gate_needed는 본인확인 현장등록·실물서명·법정출석·현장검증 4가지만 Y.

K-Compose(SP-20, 599줄) — "어떤 순서로" 결정

STEP1 PROCEDURE_MAP_LOOKUP(캐시 조회) → STEP1-B 미스 시 [KSEARCH_HANDOFF]로 기관 실존 확인 후 PROCEDURE_MAP_DRAFT 등재 → STEP2 목표 적합성 확인(캐시 히트여도 항상 1회) → STEP3 공익·사익 재분류 게이트(C40) → STEP4 [HANDOFF_TO_KEXECUTE]로 이관(parallel_group·fanout_mode 여기서 결정) → STEP5 무료 이관 시 역할 종료.

K-Execute(SP-22, 696줄) — 실제 실행

STEP1 매 단계 착수 직전 예외 없이 [ORCHESTRATION_PROGRESS] 고지(2026-08-05, 5분+ 무응답 지연 문제로 신설) → STEP1-P 병렬·팬아웃("병렬"=순서 의존관계 없음으로 재정의, 진짜 동시실행 아님) → STEP2 일치도 검증 게이트: match_score = domain_fit × jurisdiction_fit, 0.7 미만 전부 기각 → STEP3 실체 요건 확인 → STEP4 [HANDOFF_TO_KDELIVER]로 이관.

K-Deliver(SP-21, 350줄) — 이용자에게 전달

STEP1 결과 조립(case_type="project_paused"면 pending_user_action 1~2문장만 전달 후 즉시 AC 반환) → STEP2 인간 경계 고지(C39, 여기서 딱 한 번만) → STEP4 PROCEDURE_MAP_UPDATE → STEP5 [HANDOFF_TO_KREPORT].

대화 스타일 절대 원칙(2026-08-06, 사용자 직접 지적으로 수정)
마크다운 제목·번호목록·"### 유의사항" 같은 문서형 응답 금지 — 사람이 옆에서 말해주듯 자연스러운 문장으로. "지금까지 한 일"을 되짚어 설명하지 않는다(사용자는 이미 알고 있음).

K-Report(SP-23, 288줄) — 이해당사자 통지·신고

STEP1 이해당사자 식별(K-Execute가 이미 처리한 기관은 제외 — 중복 통지 방지) → STEP2 automation.level이 full_api면 STEP3(직접 제출), 아니면 STEP4(초안 생성) → STEP5 [ORCHESTRATION_COMPLETE]로 AC 최종 반환.

가장 중요한 금지 조항
공식 API 연동이 없는 기관에 "제출했다"·"기록했다"고 말하지 않는다. 초안만 만들었으면 반드시 "초안을 준비했고, 실제 제출은 아직 안 됐다"고 명시한다.
⑦ K-Search
K-Search(SP-18, 917줄) 내부 처리

"혼디 생태계 전체의 유일한 검색 실행 에이전트" — 다른 어떤 SP도 검색 로직을 자체적으로 갖지 않는다. K-Intent/K-Compose/K-Execute가 [KSEARCH_HANDOFF]로, K-Market 등이 [CALL_KSEARCH]로 위임할 때만 등장한다.

STEP 0-A — 개인/공직자 특별조항(최우선 게이트)

동의 확인(STEP0)보다도 먼저 통과해야 함. 공직자·공무원 개인(직책·소속 언급만으로도 해당 — "동사무소 담당자"도 포함), 정치인, 공인이면 STEP1(웹 검색)로 진행하지 않고 정중히 거절. 단 그 사람이 속한 기관 자체의 대표 채널 안내는 별개로 허용.

RULE-02 표준 처리 흐름(STEP 1~5)

STEP1 의도 파싱(caller·mode·target_type·단서들 추출) → STEP2 모호성 판단(단서 부족하면 [KSEARCH_CLARIFY]로 최대 2회 되물음) → STEP3 [SEARCH] 실행(품목 동의어 자동 확장 포함) → STEP4 후보 평가·확정(모호하면 [KSEARCH_CANDIDATES]로 이용자가 직접 고름) → STEP5 [KSEARCH_RESULT: status=matched|matched_list|not_found|institution_only|insufficient]로 반환.

RULE-04 — not_found와 institution_only 구분

"동장님 개인을 콕 집어달라"는 요청을 not_found로 뭉뚱그리면 이용자가 "아직 안 만들어졌나보다"로 오인해 미청구 프로필 생성(RULE-03)으로 잘못 이어질 위험이 있다(v1.1 사고실험 #29·#36에서 발견) — institution_only로 명확히 구분 반환.

RULE-07 — 웹 검색·공공데이터 보완

보완형(guid 확정 대상의 부족한 속성 채움, [웹 참고정보] 표시)과 대체형(스키마 밖 정보, guid 없이 external_info_only로 종료) 구분. 정부·공공기관은 data.go.kr 최우선, 그 외는 [WEB_SEARCH](Serper.dev 프록시).

Limitations
정직하게 밝힘 — 이 문서의 한계
  • §CATALOG 342개 GWP 각각의 개별 SP 본문(예: K-Market 자체 절차)과 gov-tree division SP 561건의 개별 내용은 다루지 않았다 — 이건 "그 경로를 타고 도착한 뒤의 내용"이지 "경로" 자체가 아니다.
  • worker.js handleSearch()·_handleUnclaimedProfilePost·search_entities RPC의 실제 코드는 열어보지 않았다 — SP 텍스트가 서술한 인터페이스만 확인했다.
  • mode=project(project_brief 자연어 방식)의 완전한 세부 절차(STEP P·STEP1-PROJECT 등)까지는 옮기지 않았다.
  • 각 SP 파일 모두 RULE-03("자기 갱신 제안")로 지속 개정되는 구조라, 이 문서는 2026-08-17 기준 스냅샷이며 다음 버전이 나오면 재검토가 필요하다.
  • worker.js에서 assembleGovSystemPrompt가 classifyFn=null로 단 한 번만 호출되는 것만 확인했다 — AC-PRO-CORE를 실제로 호출하는 메인 챗 엔드포인트 코드 자체는 이 문서 작성 시점엔 특정하지 못했다.
