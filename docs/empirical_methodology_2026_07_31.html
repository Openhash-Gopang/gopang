1. 실험 개요

혼디의 AI 라우팅(§CATALOG·§CATALOG-EXPERT 기반 [GWP:id]/[EXPERT:id] 태그 라우팅)이 실제로 설계대로 동작하는지를 4단계에 걸쳐 실증적으로 검증했다. 정적 코드 검토만으로는 "모델이 실제로 어떻게 반응하는지"를 알 수 없다는 한계를 인지하고, 이번 세션에서 처음으로 실제 LLM API(DeepSeek)를 호출하는 라이브 행위 테스트를 GitHub Actions 기반으로 구축해 수행했다.

2. 1단계 — 정적 구조 스모크 테스트 (300건)

방법론

실제 LLM을 호출하는 대신, 각 시나리오가 라우팅돼야 할 서비스/페르소나에 대해 코드베이스 상에서 (1) 카탈로그 등록 여부 (2) 목적지 파일·핸들러 실존 여부 (3) 백엔드 PDV 등록 정합성(SVC_ALIAS) (4) AI 시스템 프롬프트 문서화 여부, 4가지를 코드 검색으로 정적 검증했다. 의미적 경계 판단(예: 두 서비스 중 어느 쪽이 맞는지)이나 실제 응답 품질은 이 방식으로 검증할 수 없어 WARN으로 분류했다.

시나리오 구성

gwp-registry.js·expert-registry.js에 실제 등록된 trigger 키워드를 근거로 GWP 모듈 27개(108건) + 전문가 AI 페르소나 63개(150건) + 플랫폼 기능·경계·부정 테스트(42건) = 300건.

3. 2단계 — 규칙기반 심화분석

1단계의 WARN 44건을 AC-PRO-CORE 시스템 프롬프트에 실제로 명문화된 판단 규칙(§CORE 되묻기 규칙, 트리거 우선순위 설계, 카탈로그 예시문 등)에 대조해 재검토했다. 이 단계도 여전히 문서화된 규칙 대조이지 실제 모델 응답 관찰이 아니라는 점을 명시했다 — 이 시점까지 이 샌드박스에 Anthropic API 키가 없어 라이브 호출이 불가능했다.

결과

7건이 PASS로 재확정됐고(예: "정보 없으면 되묻는다", "제주시청처럼 관청명 언급 시 kregionalgov"), 심화 조사 과정에서 문서·유지보수 결함 2건이 새로 발견됐다.

최종 재분류: PASS 247 / WARN 37 / FAIL 16. 남은 WARN 중 진짜 라이브 검증이 필요한 항목은 3건(프롬프트 인젝션 저항력·다국어 처리 품질·복합의도 분기)으로 좁혀졌다.

4. 3단계 — DeepSeek 라이브 API 테스트 (300건)

인프라 설계

이 세션이 진행된 샌드박스는 api.deepseek.com으로의 네트워크 egress가 차단돼 있어(host_not_allowed), 직접 API를 호출할 수 없었다. 대신 GitHub Actions를 실행 환경으로 사용하는 하네스를 설계했다:

  • tests/live_smoketest/live_smoketest.py — 300개 시나리오를 실제 prompts/AC-PRO-CORE_v1_0.txt(§CATALOG/§CATALOG-EXPERT 포함)를 시스템 프롬프트로 그대로 사용해 deepseek-chat에 1턴씩 전송, 응답에서 [GWP:id]/[EXPERT:id] 태그를 추출해 기대값과 대조
  • .github/workflows/live-smoketest.yml — workflow_dispatch 수동 트리거, 결과를 보호되지 않은 results/live-smoketest 브랜치에 자동 커밋(main은 브랜치 보호로 직접 push 불가)
  • DeepSeek API 키는 GitHub Actions repository secret으로 별도 등록(Cloudflare Worker 시크릿과는 무관한 저장소)

채점 로직의 진화

최초 채점 로직은 태그 유무만으로 단순 PASS/FAIL을 매겼으나, 5건 시험 실행에서 §CORE의 "넘겨짚지 않고 먼저 되묻는다" 지침에 따른 정상적인 되묻기 응답이 대량으로 FAIL 오판정되는 것을 발견했다. 이를 반영해 CLARIFY(정당한 되묻기 가능성, 1턴 테스트의 한계)를 별도 판정으로 분리했다.

핵심 발견

  1. 정적 분석 결과가 라이브에서 재확인됨 — #287 "구매자문 어드바이저 AI 연결해줘"가 advisor로 안 가고 kcommerce로 오라우팅. 결함 #3(advisor 카탈로그 미기재)이 실제 모델 행동으로도 그대로 나타났다.
  2. "정상경로" 가정 자체의 오류 — "카탈로그 트리거 기반 = 즉시 명확"이라고 가정했던 시나리오 상당수가 실은 진짜 중의적이었다(예: "필라테스 강도"의 '강도'가 운동강도/범죄 중의성).
  3. 태그 누락 패턴(패턴A) — 모델이 "OOO를 호출하겠습니다"처럼 의도는 명확히 밝히면서 실제 [GWP:id] 태그 자체를 빠뜨리는 사례 4건 발견(예: "K-Insurance를 호출하겠습니다."로 끝나고 태그 없음).
  4. §HONESTY 위반 패턴(패턴B) — #134 "상표 등록 절차 알려줘"에서 모델이 patent-attorney(변리사)가 §CATALOG-EXPERT 표에 있음에도 "전담 서비스가 현재 없다"고 답함.
  5. 하네스 자체 버그 2건 발견 — (a) EXPERT 태그 추출 시 라벨을 전문가AI(한글)로 지정했는데 시나리오 기대값은 EXPERT(영문)라 ID가 정확히 일치해도 라벨 불일치로 가짜 FAIL 27건 발생. (b) PLATFORM 카테고리 22건이 애초에 AC-PRO-CORE가 소유하지 않는 기능이라 검증 방법론 자체가 틀렸음.

PR-4(worker.js) 특이사항 — 스코프 확장

결함 2를 고치던 중 kqna(qna.hondi.net)가 SVC_ALIAS뿐 아니라 REGISTERED_SERVICES 자체에도 전혀 등록돼 있지 않다는 걸 발견했다. 이건 단순 별칭 추가가 아니라 신뢰 레벨(minAuth)을 새로 정해야 하는 보안 설정 결정이라, 임의로 값을 넣지 않고 사람에게 확인받은 뒤(L0, public과 동일 수준) 진행했다.

7. 방법론적 한계와 교훈

  • 1턴 테스트의 근본적 한계: §CORE의 되묻기 설계상, 모호한 발화의 상당수는 애초에 1턴만으로 최종 라우팅까지 도달하지 않는다. CLARIFY 207건 중 실제로 2턴째 정확히 라우팅되는지는 이번 실험으로 확인하지 못했다.
  • DeepSeek 비결정성: temperature=0으로 고정해도 동일 발화가 실행마다 다른 응답을 낸 사례가 실측됐다(예: "살려줘에 대해 상담받고 싶어요"가 실행마다 kemergency/mental-health-professional로 갈림). 단일 샘플로 결론 내리지 않도록 주의가 필요하다.
  • 테스트 하네스 자체도 결함의 원천: 이번 실험에서 발견한 결함 중 2건(EXPERT 라벨 불일치, PLATFORM 범위 오분류)은 대상 시스템이 아니라 테스트 코드 자체의 버그였다. 정적 분석뿐 아니라 검증 도구 자체도 검증 대상이라는 교훈.
  • 범위 밖 항목 혼입 위험: PLATFORM 카테고리처럼 애초에 검증 대상 시스템(AC-PRO-CORE)이 소유하지 않는 기능을 같은 하네스로 테스트하면 방법론 자체가 틀어진다.

8. 다음 단계 — Function Calling 전환 계획

패턴A(태그 누락)의 임시 완화(#138)를 넘어서는 근본 해결책으로, 텍스트 안에 문자열 태그를 "기억해서 써주길 바라는" 현재 구조를 LLM API의 네이티브 tool-calling으로 전환하는 프로젝트 계획을 별도 문서로 작성했다. 6개 프로바이더(openrouter/anthropic/gemini/deepseek/openai/xai) 중 실질적으로 스키마는 Anthropic 방식과 OpenAI 호환 방식 두 갈래뿐이며, DeepSeek가 production 기본값(deepseek-default)이라는 것도 이 과정에서 확인했다. 섀도우 모드 → 컷오버 → 정리의 3단계 마이그레이션으로 설계했다. 상세 내용은 별도 계획 문서(option3_function_calling_migration_plan.md) 참고.
