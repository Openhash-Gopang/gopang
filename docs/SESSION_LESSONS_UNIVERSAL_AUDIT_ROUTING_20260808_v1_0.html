professor 리프 정밀화(subject-gate) 통합에서 시작해, CALL_KINTENT 과적합 재발견, 미성년자 안전 설계 신설, 저장소 전수조사(300건 스모크테스트)를 거쳐 — 결국 "UNIVERSAL-INTEGRITY는 전체 SP 공통 최상위 원칙"이라는 문서 자신의 선언이 실제로는 GWP 27개 중 6개와 AGENT-SUPPLIER 78개 전부에서 지켜지지 않고 있었다는 걸 발견한 하루였다. 라이브 검증 하네스 자신의 버그(빈 응답 트리비얼 PASS)도 두 번 잡았다. 이 문서는 그 과정에서 반복된 실패 패턴과 설계 원리를 정리한다.

Overview
이 문서가 왜 있는가

이 세션은 좁은 버그 수정 하나로 시작해서 저장소 전체의 아키텍처 감사로 번졌다. professor EXPERT 페르소나가 157개 세부전공을 가졌는데 라우팅 LLM이 리프를 못 찾아 CALL_KINTENT로 새는 버그를 고치다가("과목 게이트" 신설), 그 수정 자체가 과적합이었다는 걸 라이브 재검증으로 발견했고, 그걸 계기로 "판사가 klaw를 전문 도구로 쓸 때와 시민이 쓸 때를 구분해야 하는가"라는 더 큰 질문을 거쳐, 최종적으로 "혼디의 모든 SP가 지켜야 할 공통 원칙이 실제로 다 지켜지고 있는가"라는 전수감사로 이어졌다.

이 문서를 읽어야 하는 상황
라우팅 오분류를 예시 문구 추가로 고치려 할 때 / AC-PRO-CORE의 system 프롬프트를 매 턴 다르게 만들고 싶을 때 / 새 K서비스나 업종을 추가할 때 / 라이브 스모크테스트 결과가 "너무 깨끗하게" 나올 때 / 여러 세션이 동시에 같은 저장소를 건드리고 있을 때.
① Overfitting Discipline
과적합 — 예시 암기가 아니라 원칙을 고쳐야 한다

professor가 CALL_KINTENT로 새는 걸 고치려고, 실패했던 발화 문장("1:1로 지도해 줄 교수님 연결해줘")의 리터럴 표현을 §CATALOG-EXPERT 표에 예시로 박아넣었다(v1.3). 라이브 재실행 결과 그 두 문장은 통과했다. 그런데 같은 의도를 다른 표현으로 바꾼 패러프레이즈 10건으로 다시 돌리자 3건이 그대로 다시 샜다 — 모델이 원칙을 이해한 게 아니라 그 문장 자체를 외운 것이었다.

판별 신호
라이브 재검증 결과가 갑자기 100%로 깨끗해지면, 방금 고친 예시 문구와 테스트 발화가 리터럴하게 겹치는지부터 대조한다. 겹친다면 "고쳐졌다"가 아니라 "암기했다"다 — 다른 표현의 패러프레이즈 시나리오로 다시 검증해야 진짜다.

실제로 효과가 있었던 재수정(v1.6)

두 번째 시도는 실패했던 문장을 더 넣는 대신, 근본 원인 가설을 §CORE 2단계에 일반 원칙으로 명문화했다 — "찾다"·"구하다"·"연결해달라" 같은 동사 자체는 §ORCHESTRATION 신호가 아니고, 대상이 표 안에 있으면 표 조회 자체가 "찾기"이자 태그가 곧 "연결"이라는 원칙. 이건 아직 라이브 재검증 전 상태로 핸드오프됐다 — 이 문서 자신이 인용하는 사례가 그렇듯, 비슷한 수정이 이 파일 안에서만 이미 세 번 반복 실패한 이력이 있다.

② Caching Constraint
"system은 절대 안 바뀐다"는 원칙이 설계를 뒤집었다

원래 계획은 "0단계(trigger 매칭)+1단계(도메인 분류)로 후보를 좁혀서, 그 후보만 담은 slim AC-PRO-CORE를 매 턴 동적으로 만들어 CFG.system에 넣는다"였다. 그런데 call-ai.js에 이미 명문화된 원칙이 있었다 — "system 메시지는 세션 내 절대 변경하지 않는다(DeepSeek Auto Prompt Caching 캐시 prefix 보존)". 매 턴 다른 system을 넣으면 캐시가 매번 깨져서, 짧아진 프롬프트인데 캐시 할인 없이 매번 전액을 내는 역설이 생길 수 있다.

그래서 이미 코드베이스에 확립된 다른 패턴(GUID·위치·PDV 요약처럼 "매 턴 바뀌는 데이터"는 system이 아니라 user 메시지 앞 [ctx] 블록에 얹는 방식, _buildEnhancedUserContent)을 그대로 따랐다 — AC-PRO-CORE 쪽엔 "[ctx]에 라우팅후보: 힌트가 있으면 그것부터 본다"는 한 문장만 추가했다. system 텍스트 자체는 안 줄어들지만(캐싱 유지가 우선), flash가 93개 대신 5~25개 안에서 판단하는 신뢰성 효과는 그대로 얻는다.

일반화 가능한 교훈
"프롬프트를 줄이고 싶다"와 "판단 신뢰도를 높이고 싶다"는 다른 목표다. 전자는 캐싱 아키텍처와 정면 충돌할 수 있고, 후자는 동적 컨텍스트 힌트로 캐싱을 안 건드리고도 달성 가능하다 — 둘을 섞어서 설계하면 원래 목표 하나를 몰래 포기하게 된다.

후보 상한을 잘못 잡아 정답을 잘랐던 실수

0단계(trigger 실매칭)는 점수 우열이 있어 상한을 세게 잘라도 안전하지만, 1단계(도메인 분류) 폴백 경로는 도메인 소속 여부만 있고 우열이 없다 — 상한 8을 그대로 적용했다가, education 도메인 12개 후보 중 하필 professor가 순서상 잘려나가는 걸 테스트로 잡았다(정확히 이 통합 작업의 출발점이었던 그 시나리오가 힌트에서 빠지는 사고). 가장 큰 도메인(health, 21개)도 안 잘리도록 25로 올려 해결했다.

③ Safety Design
미성년자 안전 — 캐묻지 않고도 보호하는 설계

8개 페르소나(주부·학생·직장인·판사·의사·어린이·노인·정치인)로 발화 분기표를 짜다가, AC-PRO-CORE 전체에서 "나이·연령·아동· 미성년" 매칭이 0건이라는 걸 발견했다 — 어린이가 위기 발화를 해도 성인과 완전히 동일한 경로만 탔다.

수정 원칙은 세 가지다. ①감지: 나이를 캐묻지 않고, 이용자가 스스로 밝힌 것만 신호로 삼는다. ②위기 결합: 미성년자로 보이면서 위기 신호(완곡한 표현 포함 — "때려요"·"굶겨요" 등)가 겹치면 더 낮은 확신도에서도 응급 처리하고, 세부 정황을 캐묻지 않는다(그건 조사기관의 역할). ③비위기: 성인용 서비스는 막지 않되 보호자 동반을 안내한다.

발화결과
"저 초등학생인데요, 아빠가 자꾸 때려요"[GWP: kemergency] — 라이브 확인됨
"15살인데 학원비 낼 돈이 부족해서 대출받고 싶어요"라우팅은 진행하되 "만 15세이시라면... 보호자와 함께 상담을" 자발적으로 안내(시나리오에 없던 대안까지 스스로 제시)
서술 수위에 대한 원칙
안전 관련 원칙 문서는 탐지 메커니즘의 세부(정확히 어떤 문구 조합이 트리거를 발동시키는지)를 자세히 나열하지 않는다 — 그 자체가 회피 방법을 알려주는 셈이기 때문이다. 패턴 수준까지만 서술한다.
④ Repository Inventory
전수조사 — 라우팅 대상은 89개뿐이었다

sp-catalog.json 총 472개 키를 5개 계층으로 분류했다. 사용자 발화가 실제로 "라우팅 결정"의 대상이 되는 건 GWP 27 + EXPERT 루트 62 = 89개뿐이었다 — 나머지(EXPERT 세부 리프 272개, AGENT-SUPPLIER 78개, GOV-TREE 지방행정 246개 기관, 공통 인프라 레이어 ~30개, AC 자신의 코어 프롬프트 3개)는 그 89개 결정 이후 코드가 내부적으로 처리하는 하위 메커니즘이거나, 아예 라우팅 대상이 아닌 부품이다.

이 조사 중 문서화 비대칭도 하나 발견했다 — professor· physician·lawyer는 다단 트리(리프 157/23/46개)라는 게 §CATALOG-EXPERT 표에 명시돼 있지만, accountant(9)·patent-attorney(10)는 똑같이 다단 트리인데 그 사실이 표에 전혀 없었다. subject-gate.js의 리프 정밀화 함수는 특정 루트에 하드코딩돼 있지 않아 코드상 작동은 하지만, 라우팅 LLM이 "이 한 줄로 충분하다"는 판단 근거를 못 얻는다는 점에서 professor가 겪었던 CALL_KINTENT 누수와 같은 클래스의 잠재 결함이다.

300건 스모크테스트 배분 원칙

실제 등록 비율에 비례해 배분했다(GWP 정상/패러프레이즈 80, EXPERT 정상/패러프레이즈 176, 리프 정밀화 15, R1/R2 인접쌍 하드케이스 20, 오케스트레이션 15, 응급+미성년자 15, 일반대화 15, 사각지대 12, CALL_KINTENT 패러프레이즈 10, 표현 다양성 22). 제작 과정에서 하네스 채점 규약(direct-response· crisis-intervention·k-intent 같은 sentinel 값)을 처음에 null로 잘못 채워서, "정답인 무응답"이 전부 FAIL로 잘못 채점될 뻔한 걸 기존 시나리오 파일과 직접 대조해서 잡았다.

⑤ Declared vs Actual
"전체 SP 공통 원칙"이 실제로는 아니었다

UNIVERSAL-INTEGRITY_v1_0.md는 스스로 "적용 범위: 트랙 무관 — 정부·K-서비스·전문직 페르소나·AGENT-COMMON· AGENT-SUPPLIER 전부"라고 선언한다. 실제 강제 경로 세 곳(클라이언트 manifest-loader.js, 서버 범용 relay, 서버 전용 relay들)을 전부 추적한 결과:

이 패턴 자체가 처음이 아니다 — klaw·kgov 코드에는 이미 "UNIVERSAL-common이 한동안 빠져 있었다(2026-07-20 발견)", "CONTROL-TOWER-PRINCIPLE도 마찬가지였다(2026-08-06 발견)"는 이력이 남아 있다. 새 K서비스가 추가될 때마다 이 강제 주입 목록에 넣는 걸 반복해서 깜빡하는 것으로 보인다.

⑥ Structural Defense
방어책 — opt-in 구조 자체가 반복되는 누락의 원인이었다

지금까지 4곳(handleLLMRelay·handleKlawRelay·handleBusinessRelay· AGENT-SUPPLIER 합성 함수)이 각자 3종 fetch를 Promise.all([...])로 반복 작성해왔다 — 이 반복 자체가 누락의 근본 원인이다. _fetchUniversalLayers() 공통 헬퍼 하나로 통일했다: 원칙 문서가 네 번째로 늘어나도 이 함수 안에만 추가하면 이미 헬퍼를 쓰는 모든 호출부에 자동 반영된다.

사람의 기억력에 의존하지 않는 두 번째 방어선

tools/check_universal_layers_coverage.py — gwp-registry.js의 모든 active 서비스가 실제로 상속 경로를 갖는지 자동 검증하고, CI가 매 push/PR + 매일 재확인한다. 스크립트를 임의로 망가뜨려서 (화이트리스트에서 항목 제거) 실제로 FAIL을 잡아내는지 양성 대조군 테스트까지 했다 — 그 과정에서 스크립트 자체의 버그 (검색 윈도우 4000자가 실제 거리 8270자보다 짧아 오탐 FAIL)도 하나 발견해 바로 고쳤다.

일반화 가능한 교훈
"다음엔 안 잊어야지"는 방어책이 아니다. 반복되는 누락 패턴을 발견하면, 그 반복 자체를 구조적으로 없애는 공통 헬퍼로 리팩터링하고, 그 헬퍼 사용 여부를 CI가 자동으로 검증하게 만드는 두 단계가 필요하다. 검증 스크립트 자신도 양성/음성 대조군으로 검증해야 신뢰할 수 있다.
⑦ Test Your Tests
라이브 테스트 자신의 버그를 두 번 잡았다

CONTROL-TOWER-PRINCIPLE("관제탑 원칙" — 한 번에 하나씩 지시, 장황한 나열 금지) 준수 여부를 라이브로 검증하는 하네스를 새로 만들었는데, 첫 실행에서 8/8 PASS가 나왔다. 의심하고 raw_response 원문을 직접 열어보니 7/8이 완전히 빈 문자열이었다 — 빈 문자열은 헤더도 목록도 없으니 정규식 채점기가 트리비얼하게 통과시킨 것이었다.

디버그 필드(finish_reason·reasoning_content 길이)를 추가해 재조사한 결과, finish_reason: "length"이고 reasoning_tokens가 예산을 이미 다 써버린 상태였다 — deepseek-v4-flash가 추론형 모델이라 추론 토큰도 max_tokens 예산에 포함되는 것으로 보인다. max_tokens를 800→2000→6000으로 올려도 여전히 reasoning_tokens 9636까지 쓰고 잘리는 케이스가 하나 남았다.

증상원인조치
8/8 PASS(가짜)빈 응답이 정규식 채점을 트리비얼 통과빈 응답을 명시적 FAIL로 채점
finish=length, content 빈값추론 토큰이 max_tokens 예산 소진max_tokens 상향 + debug 로깅
finish=stop인데 content 빈값(completion_tokens=91 전부 reasoning)실제 앱과 달리 사업체 실시간 데이터(예: table_availability)를 안 채운 정적 SP만 이어붙임 — 모델이 §HONESTY와 충돌해 판단 마비하네스 한계로 기록, 별도 동적 데이터 주입 필요(미착수)
이번 세션에서 세 번째로 반복된 패턴
라이브 검증 결과가 유독 깨끗하면 채점 로직 자체를 의심한다 — 특히 새로 만든 하네스일수록. "예상보다 좋은 결과"는 실력이 아니라 계측 오류일 확률이 실전에서 상당히 높았다(①의 과적합, 이번 8/8, 그리고 이전에도 "결과가 비정상적으로 좋다"는 의심이 여러 번 옳았다).
⑧ Concurrent Sessions
협업자 커밋을 조용히 덮어쓸 뻔한 사고

이 세션은 여러 세션이 동시에 같은 저장소를 건드리는 상황에서 진행됐다. prompts/sp-catalog.json을 여러 차례 편집하면서, 로컬 클론을 매번 새로 받지 않고 재사용한 탓에 다른 두 세션이 이미 고쳐놓은 29개 항목(SP 파일명 버전업)을 조용히 되돌릴 뻔했다 — 사용자 지적으로 발견해 복구했다.

공유 핫파일(sp-catalog.json·worker.js 등)을 편집하기 전에는 매번 git fetch + git reset --hard origin/main으로 로컬을 진짜 최신으로 맞춘다. 편집 후에는 git diff --stat으로 변경 범위가 의도한 파일·줄 수와 정확히 일치하는지 확인한다.
⑨ Design Reversal
"전문가 vs 시민" 구분을 설계하다가 폐기한 이유

발화 분기표에서 "판사가 klaw를, 의사가 physician을 전문 도구로 쓸 때와 시민이 상담받을 때를 구분해야 하지 않느냐"는 구조적 공백이 발견됐다. verified affiliation(기관 소속 승인, 실제 구현 확인됨) 기반 판별 근거까지 설계하다가, "애초에 구분이 필요한가"를 되짚어보고 폐기했다.

이유 셋: ① professor가 이미 같은 문제(초등학생과 대학원생을 어떻게 구분하나)를 "직업 신원 확인"이 아니라 "대화 자체를 신호로 삼는" 방식(§3-1 학습자 프로파일 확정)으로 풀었고 같은 패턴이 재사용 가능했다. ② 직업과 "이번 질문에 필요한 깊이"는 상관관계가 약하다(형사전문 변호사가 세법을 물으면 시민과 다를 게 없다). ③ 틀렸을 때의 비대칭이 나쁜 방향이다 — verified affiliation은 소속 기관만 검증하고 개인 자격까지는 검증 못 하는데, 잘못 판별되면 안전 고지가 빠지는 쪽으로 틀린다.

일반화 가능한 교훈
새 구분 축을 설계하는 도중에도 "이 구분이 정말 필요한가"를 별도로 재검증할 가치가 있다 — 이미 다른 곳에서 검증된 더 간단한 패턴(대화 자체가 신호)이 있는지, 그리고 오판 시 위험이 어느 방향으로 기우는지를 먼저 따진다.
