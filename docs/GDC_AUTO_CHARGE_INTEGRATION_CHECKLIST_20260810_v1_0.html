GDC 입금 자동 확정은 방식A(오픈뱅킹 조회 API 폴링)와 방식B(PG 가상계좌 웹훅)를 동시 지원하도록 이미 코드·스키마가 준비돼 있다(worker.js의 _mintAndRecordCharge 공용 코어, channel/external_tx_id 등). 다만 두 경로 모두 실제 외부 기관의 API 문서와 자격증명이 없으면 완성할 수 없는 지점에서 TODO로 멈춰 있다 — 이 문서는 협의 자리에서 정확히 무엇을 요청해야 하는지 정리한 체크리스트다. 항목이 채워지면 worker.js의 TODO 두 곳만 교체하면 되므로, 코드 작업 자체는 반나절이면 끝난다.

Overview
이 문서가 왜 있는가

은행·결제 API는 필드명 하나만 틀려도 조용히 실패하거나, 최악의 경우 금액이 잘못 처리될 수 있다. 실제 문서 없이 "그럴듯하게" 채우는 대신, 두 경로 모두 기본값이 완전히 비활성 (AUTO_CONFIRM_OPENBANKING_ENABLED / AUTO_CONFIRM_PG_WEBHOOK_ENABLED)인 채로 안전하게 대기하도록 만들어 뒀다 — 기존 관리자 수동 확인 (charge-admin.html) 흐름은 그대로 살아있으므로 운영에 지장이 없다.

이 문서를 읽어야 하는 상황
금융결제원 오픈뱅킹 이용기관 등록을 신청하기 전 / PG사와 가맹계약 협상 중 요구사항을 정리할 때 / 실제 API 문서가 도착해서 worker.js의 TODO를 채워야 할 때.
방식A
오픈뱅킹 조회 API (금융결제원)
회사 고정계좌 입금 내역을 10분 주기로 폴링 → 매칭코드 대조 → 자동 확정

① 이용기관 등록 후 발급받아야 할 것

  • 이용기관코드(client_id)
  • 이용기관 시크릿(client_secret)
  • 핀테크이용번호(fintech_use_num) — 회사 고정계좌(GDC 충전 전용 계좌) 등록 후 발급되는 값. 이 계좌의 입출금 내역 조회에 필수.
  • 검증(테스트베드) 환경 접속 정보 — 실거래 전 샌드박스 선검증

② 접근토큰(access token) 발급/갱신

  • 토큰 발급 엔드포인트 URL (검증/운영 환경이 다를 수 있음 — 반드시 확인)
  • 요청 파라미터 형식(body 전달 vs Basic Auth 헤더)
  • access_token 만료 시간과 refresh_token 갱신 방식 — 자동 재발급 스케줄 설계에 필요
  • refresh_token 자체 만료 여부 및 재인증 필요 조건

③ 입출금 거래내역조회 API

  • 정확한 엔드포인트 URL과 HTTP 메서드
  • 요청 파라미터: 조회 기간 형식, 계좌번호 전달 방식, 페이지네이션 유무
  • 응답 필드명 전체 — 아래 표 4개가 코드에 그대로 매핑돼야 함
  • 조회 가능한 최대 기간 — 현재 10분 폴링 주기 설계에 영향
  • 호출당 과금 여부·단가 — 유료면 폴링 주기 조정 검토
  • 호출 제한(초당/분당 rate limit)
필요 항목코드 내 용도
거래고유번호externalTxId — 멱등성 키(중복 폴링·재조회로 두 번 민팅되는 것 방지)
입금자명매칭코드(HDxxxxxx) 탐지 대상
적요매칭코드가 여기 들어올 수도 있음 — 입금자명과 함께 확인
입금액krwAmount — 발행할 GDC 계산 기준

④ 장애/예외 상황

  • 정기점검 시간대(보통 새벽) 유무
  • 오류 코드 목록 — 특히 "조회 권한 없음", "토큰 만료" 등 구분 처리가 필요한 것들
방식B
PG 가상계좌 (다날 / NHN KCP / 토스페이먼츠 등)
사용자별 전용 가상계좌 발급 → 입금 즉시 웹훅 → 자동 확정

① PG사 선정 시 확인할 것 (계약 전 비교 기준)

  • 가상계좌(무통장) 발급 API 지원 여부
  • 수수료율(입금액 대비 % / 건당 고정비)
  • 정산 주기(익일/D+2 등) — GDC는 입금 즉시 발행이라 무관하지만 현금흐름 파악에 필요
  • 가상계좌 유효기간 정책(무기한 vs 주기적 갱신)
  • 웹훅(실시간 통지) 지원 여부 — 필수 조건

② 가맹계약 체결 후 발급받아야 할 것

  • 가맹점 ID / API 키 / 시크릿키
  • 테스트(샌드박스) 가맹점 키
  • 웹훅 URL 등록 방법 — 등록할 URL: https://<워커 도메인>/biz/charge-webhook-pg

③ 가상계좌 발급 API

  • 엔드포인트 URL, 요청 파라미터(예금주명, 유효기간, 사용자 식별자 전달 방식)
  • 응답 필드: 발급된 계좌번호, 은행명
  • 1인 1계좌 정책 기본 지원 여부(재발급 시 이전 계좌 처리)

④ 웹훅(입금 통지) 스펙 — 가장 중요

  • 서명 검증 방식 — 헤더 이름, 알고리즘(보통 HMAC-SHA256), 서명 대상(raw body 전체 vs 특정 필드 조합)
  • 페이로드 필드명 전체 — 아래 표 참고
  • 웹훅 재전송 정책(미응답 시 재시도 횟수·간격)
  • 웹훅에 대한 응답 규격(특정 상태코드/바디를 "정상 수신"으로 인식하는지)
  • IP 화이트리스트 필요 여부 — Cloudflare Worker는 고정 IP가 아니므로 서명 검증만으로 신뢰성 확보 가능한지 사전 확인
필요 항목코드 내 용도
가상계좌 번호account_no — virtual_accounts 컬렉션에서 guid 역조회
입금액deposited_krw — 발행할 GDC 계산 기준
입금자명depositor_name — 기록용
거래고유번호tx_id — 멱등성 키(웹훅 재전송돼도 중복 처리 방지)
필드명은 PG사마다 다르다
handleChargeWebhookPG() 안의 필드명(account_no, deposited_krw 등)은 지금 가정값이다 — 실제 계약된 PG사 문서를 받으면 반드시 그 스펙에 맞춰 교체해야 한다.
