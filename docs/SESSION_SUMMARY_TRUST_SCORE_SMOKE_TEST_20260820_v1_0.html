Overview
이 문서가 왜 있는가

"신용평가 모듈을 완성하겠다"는 짧은 요청이, 실제로는 어디까지가 결제 중재이고 어디부터가 규제 대상 금융업인지를 가르는 범위 협상과, 그 범위 안에서도 실제로 동작하게 만드는 데 겪은 네 번의 디버깅 라운드로 이어졌다. 다음에 이 인프라를 확장할 사람이 같은 시행착오를 반복하지 않도록, 각 실수를 왜 몰랐는지와 어떻게 잡았는지 위주로 정리한다.

① Scope
범위 결정 — 대출·채권·자산유동화는 왜 제외됐나

작업에 들어가기 전, 여러 방안이 순서대로 제안되고 각각 규제 이유로 반려됐다. "사용자가 스스로", "사적 AI 비서가", "협상일 뿐"이라는 재구성이 반복될수록 실질은 규제 대상 금융업(환전업, 대부업, 투자중개업, 자산유동화업)에 더 가까워진다는 패턴이 드러났다.

검토된 방안결론
GDC → 위안화 CBDC 자체 환전으로 이자수익보류 — 외국환거래법상 환전업/자본거래 중개 소지
신용평가 기반 대출한도 산정보류 — gdc-credit.js LEGAL-HOLD(2026-07-18) 유지, 대부업법 등록 미확정
사용자간 채권 발행 시 혼디가 이자율 산정보류 — 투자중개업/투자자문업 인가 필요
혼디가 채권 매입 후 자체 증권 발행보류 — 사실상 자산유동화(ABS), SPC 등록 필요
혼디 회사 지분(주식) 판매별개 트랙 — 상법상 통상적 자금조달, 사모/크라우드펀딩 규제선만 준수
순수 신뢰점수(trust_level) — 이번 구현 범위승인 — 대출/이자율과 완전히 분리, 판매자 노출·분쟁 우선순위 등 비금전적 용도만
결정
사업 초기에는 결제 중재만 하고, 사업이 안정화된 뒤에만 인가받은 금융기관과 협력 체계를 구축한다. "안정화" 판단을 사후적·주관적으로 하지 않도록 §9에서 정량 지표로 고정했다.
② Infrastructure
account_risk_score 컬렉션 + trust-score.js 산식 신설

account_risk_score 마이그레이션(guid, current_score, trust_level[L0~L4], score_basis[json, 산식 근거 투명 공개], step_up_required 등)을 신설하고, ledger_entries (이미 해시체인·append-only로 살아있던 재무제표 원장)의 거래 이력만으로 점수를 계산하는 trust-score.js를 만들었다.

점수 산식 (v1, 가중치를 코드에 그대로 노출)

  • tenure(계정 나이) — 최대 30점, 180일=만점
  • volume(누적 거래 건수) — 최대 30점, 40건=만점
  • consistency(최근 90일 내 활동) — 최대 20점
  • fraud override 계정은 배치가 점수를 올려쓰지 않음(사기 탐지 우선)
경계 표시
trust-score.js 파일 최상단에 "대출 한도·이자율·채권가격 계산 함수를 이 파일에 절대 추가하지 말 것"이라는 경계를 명시했다. §1의 범위 결정이 나중에 다른 세션이나 협업자에 의해 조용히 허물어지지 않도록 하는 코드 레벨 안전장치다.
③ Trigger
이벤트기반 트리거 연결 — cron 배치 대신 원장 쓰기에 직결

모든 원장 쓰기가 POST /internal/ledger-entries 단일 엔드포인트를 거치는 구조를 활용해, 원장 기록 성공 직후 ctx.waitUntil()로 비동기 재계산을 트리거했다. 응답 지연 없음, 재계산 실패해도 원장 쓰기 응답은 그대로 반환(기존 "fs 기록 실패해도 정산은 안 막는다" 원칙과 동일). 5분 스로틀 가드로 고빈도 계정의 과도한 재조회도 막았다.

④ Mistake 1
패치 스크립트 비멱등성 — 재실행이 중복 선언을 만듦

트리거 패치를 적용하는 과정에서, 다운로드가 안 된 줄 모르고 같은 패치 스크립트를 두 번 실행하는 상황이 생겼다. 패치의 "이전 상태" 매칭 문자열이 "이후 상태"에도 부분적으로 포함되는 문자열이었던 탓에, 재실행 시 RECOMPUTE_THROTTLE_MS 선언과 스로틀 if-block이 통째로 중복 삽입돼 SyntaxError: Identifier already declared가 발생했다.

원인
패치 스크립트가 "이미 적용됐는지" 자체를 확인하지 않고 "적용 전 문자열이 존재하는지"만 확인했다 — 그 문자열이 적용 후에도 여전히 부분적으로 남아있으면 재실행이 안전하지 않다.
수정
git reset --hard origin/main으로 로컬을 이미 정상 푸시돼 있던 origin/main 상태로 되돌려 해결. 이후 모든 패치 스크립트에 "이미 적용됨" 마커를 먼저 검사하는 idempotent 가드를 추가하고, 신선한 클론에 두 번 연속 실행해 안전성을 확인하는 걸 표준 절차로 삼았다.
⑤ Mistake 2
커밋 없이 배포된 디버그 코드 — git과 실제 서비스의 드리프트

원인 진단을 위해 console.log 디버그 코드를 추가해 wrangler deploy로 바로 배포했는데, 이때 git commit·push를 건너뛰었다. 이후 git diff가 비어있다는 걸 보고 "로컬이 깨끗하다"고 판단했지만, 실제로 서비스 중인 Worker에는 여전히 디버그 로그가 떠 있는 상태였다 — 로컬 파일 상태와 배포된 Worker 상태는 별개라는 점을 재확인했다.

수정
git status/git diff로 로컬이 origin과 일치함을 확인한 뒤, 그 상태로 wrangler deploy를 한 번 더 실행해 실제 서비스를 git 상태와 다시 동기화했다.
⑥ Mistake 3
computeTrustScore가 매번 profiles를 재조회 — 신규 계정에서 조용히 실패

첫 스모크 테스트에서 ledger_entries는 정상 기록되는데 account_risk_score가 전혀 생성되지 않았다. computeTrustScore()가 항상 resolveGuidToL1(guid)로 profiles 컬렉션을 재조회했는데, 테스트 guid처럼 profiles 레코드가 없는 계정은 GUID_NOT_FOUND_IN_ANY_L1로 실패하고 ctx.waitUntil().catch()에 조용히 묻혔다. 원장 쓰기 자체는 성공 응답을 줘서 겉으로는 멀쩡해 보였다.

수정
handleInternalLedgerEntry는 원장 쓰기 시점에 l1Base를 이미 알고 있다(l1_node → resolveL1Base 완료). 그 값을 computeTrustScore에 세 번째 인자로 그대로 넘겨, profiles 존재 여부와 무관하게 동작하도록 수정했다. l1Base를 안 받는 호출(향후 배치/수동 재계산)은 기존 방식으로 자동 폴백해 하위호환은 유지했다.
⑦ Mistake 4 — Root Cause
json 필드 maxSize 누락 — 이미 문서에 경고돼 있던 문제였다

⑥을 고치고 재배포했는데도 여전히 레코드가 안 보였다. 디버그 로그를 추가해 보니 computeTrustScore는 실제로 "완료"까지 로그를 남기고 있었다 — 그런데도 PocketBase에는 아무 것도 없었다. 원인은 upsertAccountRisk()가 pbFetch()의 응답 상태(res.ok)를 전혀 확인하지 않고 그냥 await만 하고 끝났다는 것이었다 — 쓰기가 실패해도 예외를 던지지 않았다.

상태 검사를 추가해 재배포하자 진짜 원인이 로그에 드러났다. score_basis(json 타입) 필드 마이그레이션에 options.maxSize를 빠뜨렸고, 실서버에 maxSize: 0으로 저장돼 있었다. 이건 이 저장소의 기존 개발자 문서에 이미 경고돼 있던 문제였다:

docs/POCKETBASE-STRUCTURE-GUIDE_v1_1_addendum_2026-07-19.md §5
"PocketBase 0.22.x 스키마 작성 시 숨은 필수값 — json 타입 → options.maxSize(바이트, 정수) 필수. 관례: 2000000(2MB)." — 새 마이그레이션을 작성할 때 이 문서를 먼저 확인했다면 애초에 겪지 않았을 문제였다.

1788100001_fixed_account_risk_score_basis_maxsize.js 마이그레이션으로 maxSize: 2000000을 채우고, pb_migrations/** push 시 자동으로 L1(hanlim) 서버에 적용되는 기존 GitHub Actions 워크플로우 (deploy-pb-migrations.yml)를 통해 배포했다.

Lessons
교훈

"성공 응답"과 "실제로 반영됨"은 다르다. 이번 세션의 네 실수 전부 겉으로는 정상 응답(200/ok:true)이 오는데 실제 데이터는 없는 형태였다. 코드가 예외를 안 던진다고 실제로 성공했다는 뜻이 아니다 — 외부 API를 호출하는 모든 지점에서 응답 상태를 확인하고, 마지막엔 반드시 대상 시스템에서 직접 데이터를 조회해 확인해야 한다.

패치 스크립트는 재실행을 전제로 짜야 한다. 파일 다운로드 실패, 세션 재시작, 동시 작업 등으로 같은 패치가 두 번 돌 가능성은 항상 있다. "이미 적용됐는지" 마커를 최우선으로 검사하고, 신선한 클론에 두 번 연속 실행해보는 걸 표준 절차로 삼아야 한다.

로컬 git 상태 ≠ 실제 배포 상태. wrangler deploy는 로컬 파일을 그대로 올린다 — git에 커밋했는지와 무관하다. 디버깅 중 빠르게 배포·롤백을 반복할 때 특히 이 둘이 어긋나기 쉬우므로, 배포 직전엔 항상 git status로 로컬이 의도한 상태인지 확인해야 한다.

같은 유형의 문제는 이미 문서화돼 있을 가능성이 높다. ⑦의 근본 원인은 반복적인 시행착오 대신 저장소 개발자 문서를 먼저 확인하자는 제안 한 번으로 몇 분 만에 찾아냈다 — 이 문서 자체도 그 원칙에 따라 작성됐다.
