SITE MANUAL — 2026-08-09 세션 발견 정리

HTTP 200인데 content가 빈 문자열인 이유

subject-gate 2단계 리프 정밀화의 라이브 커버리지를 38건 늘리려다가, 기존 시나리오까지 포함해 거의 전량이 "JSON 파싱 실패 — raw: (빈 문자열)"로 죽는 걸 발견했다. 네트워크도, 인증도, 시나리오 품질도 아니었다 — deepseek-v4-flash가 사고 과정 (reasoning_content)에 먼저 토큰을 쓰고 최종 답변 (content)은 나중에 내는데, max_tokens: 60이 사고 과정만으로 소진되고 있었다. 같은 결함이 프로덕션 subject-gate.js·domain-classifier.js· report-utils.js 세 곳에 전부 있었다. 이 문서는 그 규명 과정과, 과정에서 부딪힌 CI 인프라·시나리오 설계·에이전트 실행 환경의 부수적 결함들을 정리한다.

대상 저장소 Openhash-Gopang/gopang 작성 2026-08-09
Overview
이 문서가 왜 있는가

출발점은 단순했다 — subject-gate(리프 정밀화) 최상위 페르소나 38개의 라이브 라우팅 커버리지가 얇으니(특히 professor 157개 리프 중 6개만 테스트됨) 시나리오를 보태자는 요청이었다. 그런데 그 시나리오를 실제로 돌리자마자 기존에 있던, 예전에 통과 이력이 있었던 시나리오까지 포함해서 거의 전량이 실패했다. "우리가 새로 쓴 시나리오가 나쁜가"로 시작한 의심이 "테스트 하네스가 잘못됐나" → "네트워크가 막혔나" → "결국 프로덕션 코드 자체의 결함이었다"로 이어졌다.

이 문서를 읽어야 하는 상황
DeepSeek(또는 다른 reasoning 계열 모델) 호출에서 HTTP는 200인데 content가 빈 문자열로 오는 버그를 만났을 때 / max_tokens를 아주 작게(60~240) 고정해둔 짧은 분류· 태깅용 프롬프트를 새로 만들거나 건드릴 때 / 라이브 스모크테스트 워크플로가 "이유 없이" 실패할 때 / 여러 세션·사람이 동시에 같은 결과 브랜치·워크플로를 건드리고 있을 때.
① Symptom
38건 중 37건이 "JSON 파싱 실패, raw: (빈 문자열)"

새로 작성한 gapfill 시나리오 38건(accountant 5·patent-attorney 6·professor 27)을 subject_gate_live_smoketest.py로 돌리자 37건이 실패했다. 처음엔 시나리오 자체를 의심했다 — 직군명이 발화에 그대로 들어가 있진 않은지(④ 참고), 존재하지 않는 리프 id를 쓰지 않았는지 재검증했지만 전부 정상이었다.

결정적 단서는 기존에 이미 있던, 과거 통과 이력이 있는 검증된 시나리오 파일(scenarios_subject_gate_stage2_20260808.json, scenarios_leaf_routing_phys_law_patent_acct_20260808.json)로 같은 테스트를 다시 돌렸을 때 나왔다 — 이것도 각각 18/18, 33/33 전부 같은 패턴으로 실패했다. 우리 시나리오 파일과 완전히 무관한, 날짜도 다른 두 파일이 똑같은 방식으로 100% 실패한다는 건 시나리오 콘텐츠 문제가 아니라는 뜻이었다.

판별 신호
"새로 만든 시나리오가 잘 안 된다"는 신호가 뜨면, 먼저 과거에 통과 이력이 있던 기존 시나리오로 같은 하네스를 다시 돌려 "통제군"을 만든다. 통제군도 똑같이 깨지면 범인은 새 시나리오가 아니라 하네스·프로덕션 코드·외부 API 쪽이다.
② Root Cause
reasoning_content가 먼저, content는 나중

subject_gate_live_smoketest.py의 call_deepseek()는 HTTP 상태코드가 200이 아니거나 예외가 나야만 재시도하고, 200이면 content가 비어 있어도 그대로 성공 취급했다:

if resp.status_code == 200: data = resp.json() text = data["choices"][0]["message"]["content"] # ← reasoning_content는 안 봄 return text, data.get("usage", {}), None

deepseek-v4-flash는 reasoning 계열 모델이라 응답을 reasoning_content(사고 과정)와 content (최종 답변) 두 필드로 나눠서 준다. max_tokens가 작으면 사고 과정만으로 예산을 다 쓰고 최종 답변을 한 글자도 못 낸 채 끝날 수 있다 — 이때도 API는 정상 200을 주고 finish_reason: "length"를 함께 준다. 코드가 content만 읽고 finish_reason도 reasoning_content도 확인 안 하니, "정상 실패"와 "구조적 결함"을 구분 못 하고 전부 "JSON 파싱 실패"로만 보였다.

확진 — 디버그 로깅 한 줄로 실사 확인

content가 비었을 때만 finish_reason· reasoning_content 길이·usage를 찍는 로그를 추가하고 재실행하자 바로 잡혔다:

[DEBUG-EMPTY] finish_reason=length reasoning_content_len=1846 usage={'completion_tokens': 500, 'completion_tokens_details': {'reasoning_tokens': 500}, ...}

completion_tokens가 정확히 상한(500)만큼 소진됐고, reasoning_tokens가 그 전부를 차지했다 — 사고 과정이 1846자였는데 500토큰 예산 안에서 다 못 끝낸 것이다.

일반화 가능한 교훈
reasoning 계열 모델을 짧은 분류·태깅 프롬프트(JSON 한 줄만 기대하는 것)에 쓸 땐, max_tokens를 "출력 텍스트 길이"가 아니라 "사고 과정 + 출력"의 합으로 잡아야 한다. 응답의 content만 읽고 비어 있으면 그냥 실패로 넘기지 말고, finish_reason과 reasoning_content 존재 여부를 최소 로그로라도 남겨야 이런 결함이 "가끔 애매하게 실패하는 시나리오"가 아니라 "구조적으로 거의 항상 실패하는 설정값"이라는 걸 빨리 알 수 있다.
③ Fix
max_tokens 60/200/240 → 1000 (그리고 그걸로도 부족한 경우)

같은 모델(deepseek-v4-flash)·같은 "짧은 JSON만 기대" 패턴·같은 data.choices[0].message.content만 읽는 코드가 세 파일에 있었다. 전부 60~240 사이의 작은 값으로 고정돼 있어 같은 결함에 노출돼 있었다 — 전부 1000으로 올렸다.

재검증 결과 로컬(무료) 스크리닝은 원래도 문제없었고(트리거 리터럴 매칭이라 네트워크 자체가 필요 없음), 실제 네트워크 호출이 필요한 계층에서 기존 검증 파일 18/18 PASS, gapfill 38건 중 35/38 → (재상향 후) 37/38 PASS로 회복됐다.

"충분히 큰 고정값"은 없다
1000으로도 부족한 케이스가 실제로 나왔다(사고 과정 1846자· 1738자 시나리오 2건, finish_reason: length로 500 전량 소진 확인 후 1000으로 재상향해서야 통과). 발화가 복잡하거나 후보 메뉴가 클수록(professor는 157개 리프) 사고 과정이 더 길어질 수 있다 — 고정 상한을 올려서 지금 통과하는 게 "영구히 안전"을 뜻하지 않는다. 근본적으로는 reasoning을 억제하는 모델 파라미터가 있는지, 또는 후보 메뉴를 더 작게 쪼개는 쪽(현재도 리프가 2개 이하면 게이트 자체를 안 타긴 함)이 더 견고한 방향일 수 있다 — 다음 세션 판단 필요.
④ Scenario Design
직군명을 발화에 그대로 넣으면 안 되는 이유

gapfill 38건 초안에는 "변리사와 출원하고 싶어요", "역사학 교수님과 1:1로 배우고 싶어요"처럼 직군명(회계사·변리사· 교수)이나 루트 트리거 문구(1:1·과외)가 발화에 그대로 박혀 있었다. subject-gate 2단계는 이미 root(예: professor)가 정해진 뒤 리프만 고르는 단계라 이게 리프 자체를 알려주진 않지만, "발화만 보고 상황을 추론하는 능력"이 아니라 "직군명을 그대로 읽고 반응하는 능력"만 검증하는 셈이라 지적받아 19건을 다시 썼다 — 상황·분야 설명만 남기고 직군명은 뺐다.

교차검증됨 — 다른 세션도 독립적으로 같은 함정에 빠졌다
같은 날(2026-08-09) 별도 세션이 kgov/kregionalgov 라우팅 시나리오 58건을 전부 기관명을 명시해서 만들었다가, "기관명을 그대로 읽는 능력만 검증했다"는 걸 뒤늦게 깨닫고 기관명 없는 버전으로 다시 만드는 과정을 거쳤다(scenarios_jeju_unnamed_20260809.json 계열). 서로 다른 두 세션이 독립적으로 같은 실수를 저질렀다는 건 이게 우연이 아니라 시나리오를 만들 때 기본적으로 빠지기 쉬운 함정이라는 뜻이다 — 앞으로 라우팅·분류 시나리오를 새로 쓸 땐 "발화에서 정답 라벨(직군명·기관명·서비스명)을 문자 그대로 뺐는가"를 항상 먼저 점검할 것.
⑤ CI Blind Spot
실패한 실행은 결과가 어디에도 안 남는다

.github/workflows/subject-gate-live-smoketest.yml의 "Commit results to results branch"·"Upload artifact (backup)" 두 스텝 다 if: always()가 없다. GitHub Actions 기본 동작상, 앞 스텝(python3 subject_gate_live_smoketest.py)이 FAIL/ERROR가 하나라도 있으면 exit 1을 내도록 스크립트가 짜여 있는데, 그러면 뒤 두 스텝은 아예 실행되지 않고 건너뛴다.

결과 — 제일 필요한 순간에 사라진다
상세 결과가 제일 필요한 건 "뭔가 실패했을 때 뭐가 왜 틀렸는지 보고 싶을 때"인데, 정확히 그 순간(FAIL 존재)에 결과가 브랜치에도 아티팩트에도 저장되지 않는다. 전부 통과할 때만 결과가 남는데, 그때는 애초에 상세 결과가 안 궁금하다. 이번 세션에서 과거 8/8·8/9의 실패한 실행들이 결과 브랜치에 한 번도 안 보였던 이유가 이것이었다 — 실패해서 커밋 스텝 자체가 안 돌았던 것.

현재는 GitHub API로 워크플로 실행 상태(conclusion)까지는 확인할 수 있지만, 실패 실행의 원문 로그는 API 응답이 Azure Blob Storage로 리다이렉트되는 방식이라(⑧ 참고) 사람이 브라우저에서 직접 열어 복사하는 것 외엔 방법이 없었다. 두 스텝에 if: always()를 추가하면 실패한 실행도 결과가 남아, 최소한 gh api나 아티팩트 다운로드로 접근 가능해진다 — 아직 미착수, 다음 세션 후보 작업.

⑥ Race Condition
결과 브랜치 force-push가 다른 세션 결과를 지운다

결과 커밋 스텝은 매 실행마다 이렇게 한다:

git checkout -B results/live-smoketest git add -f results/ git commit -m "..." git push --force origin HEAD:results/live-smoketest

체크아웃을 main에서 새로 뜨고, 그 실행 하나가 만든 results/ 폴더만 커밋한 뒤 --force로 브랜치 전체를 덮어쓴다 — 누적이 아니라 "마지막으로 push한 실행이 이긴다" 구조다. 여러 라이브 스모크 테스트 워크플로(live-smoketest.yml· subject-gate-live-smoketest.yml· live-smoketest-expert-persona.yml· live-smoketest-profile-assistant.yml)가 각자 독립적으로 이 패턴을 쓰고, 여러 사람·세션이 동시에 돌릴 수 있어서, 우리 subject-gate 결과가 성공적으로 커밋된 직후 다른 세션의 kgov 관련 실행이 push하면서 통째로 지워지는 걸 실사로 확인했다.

일반화 가능한 교훈
공유 브랜치에 force-push로 "이번 실행 결과만" 쓰는 패턴은 동시 실행이 하나뿐일 때만 안전하다. 여러 워크플로· 여러 사람이 병렬로 같은 인프라를 쓰는 지금 단계에서는, 실행별로 경로를 분리하거나(예: results/<workflow>/<run_id>/) force 대신 병합 방식으로 바꾸는 게 맞다 — 이것도 다음 세션 후보 작업으로 남긴다.
⑦ Naming Collision
이름이 비슷한 워크플로 두 개 — 스키마가 다르면 100% 확정적으로 죽는다

Live Smoketest (DeepSeek, 300 scenarios) (live-smoketest.yml, live_smoketest.py 호출, {no, expected_id} 스키마)와 Subject Gate Live Smoketest (DeepSeek, 2단계 과목 게이트)(subject-gate-live-smoketest.yml, subject_gate_live_smoketest.py 호출, {id, root_id, expected_leaf_id} 스키마)가 GitHub Actions 사이드바에 나란히 있다. 실행 화면에서 사람이 반복해서 잘못된 쪽을 눌렀고(브라우저 뒤로가기·탭 전환 중 섞임), 매번 정확히 같은 에러가 났다:

KeyError: 'no' todo = [s for s in scenarios if s["no"] not in done]

이건 우연이나 세션 플레이크니스가 아니라 100% 확정적 결과다 — subject-gate 스키마 파일에는애초에 "no" 키가 없으니, live_smoketest.py에 넣으면 항상 이 줄에서 죽는다. 반대로 실제로 성공한 다른 실행("다른 세션은 성공한다")도 로그를 보면 live_smoketest.py + {no,...} 스키마 파일 조합이었을 뿐, 같은 스크립트가 우연히 잘 되거나 안 되고 한 게 아니었다.

판별 신호
워크플로를 잘못 골랐는지 헷갈리면 로그 첫 줄의 실제 호출된 파이썬 스크립트명(live_smoketest.py vs subject_gate_live_smoketest.py)과 --system-prompt 인자 존재 여부(전자만 있음)를 본다. workflow_dispatch 입력창을 열 때는 scenarios_file 위 회색 안내 문구(기본값 파일명)가 어느 스크립트 것인지부터 확인 — 이름이 비슷한 워크플로가 여럿일수록 URL을 직접 열어(사이드바 클릭 대신) 들어가는 게 더 안전하다.
⑧ Agent Sandbox Limits
샌드박스 에이전트의 네트워크 한계 — Azure Blob은 못 읽는다

이 규명 과정 상당 부분을 AI 에이전트(Claude)가 GitHub REST API로 워크플로를 직접 트리거·폴링하며 진행했다. api.github.com은 접근 가능해 워크플로 트리거·실행 상태(status/conclusion) 확인은 됐지만, 실패한 실행의 원문 로그(/actions/jobs/{id}/logs)와 아티팩트 다운로드(/actions/artifacts/{id}/zip)는 둘 다 GitHub이 아니라 productionresultssa*.blob.core.windows.net (Azure Blob Storage)로 302 리다이렉트되는데, 이 도메인이 샌드박스 네트워크 화이트리스트 밖이라 못 받아왔다. 결국 실패한 실행의 상세 로그는 사람이 브라우저로 열어 복사해주는 수밖에 없었다.

다음 세션(특히 AI 에이전트)을 위한 메모
GitHub Actions 로그·아티팩트를 자동화 스크립트나 에이전트로 받으려 할 때, api.github.com에 접근 가능하다고 로그 본문까지 받을 수 있다고 가정하지 말 것 — 실제 파일은 별도 스토리지 도메인에 있다. 상태 확인(성공/실패)까지는 API로 충분하지만, 실패 원인의 상세 텍스트가 필요하면 사람에게 로그를 요청하거나, 워크플로 자체가 로그 내용을 다른 방식으로 (예: PR 코멘트, 별도 텍스트 파일 커밋) 노출하도록 바꿔야 한다.
⑨ Known Issue
professor-gap-15는 토큰과 무관한 flaky 케이스 — 의도적으로 안 고침

실행finish_reasonreasoning_content_lencompletion_tokens

의도적 결정 — 왜 더 안 팠는가
38건 중 1건(2.6%)이고, 재현이 불안정한 flaky 케이스에 더 엔지니어링을 들이는 것보다 알려진 이슈로 문서화하는 쪽을 택했다. 같은 날 다른 세션도 34건의 경로 판단 중 진짜 오배정은 2건뿐이라고 판단하고 넘어간 선례가 있다 — 완벽한 100%를 추구하기보다, 소수의 불안정한 케이스는 기록해두고 구조적 결함(①~③)에 집중하는 게 이번 세션들의 일관된 판단 기준이었다. 나중에 이 리프 주변에서 반복적으로 문제가 보고되면 그때 재조사할 것.
