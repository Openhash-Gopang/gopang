이번 세션에서 gov-router.js를 열세 번 고쳤다(BUG-023~035, DECISION-01). 그중 최소 넷은 직전 작업의 부산물이었다 — 잘못된 자매 테이블에 키워드를 넣거나, 위험한 일반화 규칙을 제안했다가 스트레스 테스트로 기각당하거나(DECISION-01), 구조적 수정 하나가 다른 코드의 암묵적 전제를 깨뜨려 새 회귀를 낳거나(BUG-034→035), 라이브 테스트 워크플로 자체를 경쟁 상태로 설계해 결과를 유실시켰다. 다음 세션이 같은 함정을 안 밟도록, 무엇을 몰라서 실수했는지와 그걸 어떻게 알아챘는지를 정직하게 남긴다.

대상 저장소 Openhash-Gopang/gopang 관련 이슈 BUG-023~035, DECISION-01 작성 2026-08-23
Overview
이 문서가 왜 있는가

개별 기능 사용법이 아니라, gov-router.js 매칭 함수를 다시 건드릴 때 / 키워드 사전에 항목을 추가할 때 / 안전 게이트를 고칠 때 / 라이브 스모크테스트 인프라를 만들 때 밟게 될 함정 모음이다. 전부 이번 세션에서 실제로 밟았고, 상당수는 사용자가 재차 지적한 뒤에야 제대로 고쳐졌다.

이 문서를 읽어야 하는 상황
라우팅에 새 계층을 추가할 때 / 키워드를 추가하다가 "이거 다른 단어랑 겹치지 않을까" 싶을 때 / 자꾸 제네릭 폴백으로 떨어질 때 / 안전 코드에서 화이트리스트를 일반화하고 싶을 때 / 라이브 테스트가 로컬과 다른 결과를 낼 때.
① Core Principle
핵심 원리 — 모든 계층은 대칭이어야 한다

_matchCity()는 "발화 자체 매칭 vs 위치 힌트만 매칭"을 _matchedViaTextItself로 구분해서, 힌트로만 매칭되면 즉시 확정 대신 뒤 단계에 기회를 주는 패턴 (cityOnlyFallback)이 2026-07-24부터 있었다. 그런데 _matchCityDept 계층엔 이 패턴이 아예 없었고 (2026-08-23 BUG-028에서야 _resolveCityDeptMatch로 신설), _matchEmd 계층에도 없었다(2026-08-23 BUG-034에서야 emdMatchedViaTextItself· emdFallback으로 신설).

계층구분 유무(도입 전)보류 그릇신설 시점
시청(City)있음cityOnlyFallback2026-07-24
시청국(CityDept)없었음_resolveCityDeptMatch2026-08-23(BUG-028)
읍면동(Emd)없었음emdFallback2026-08-23(BUG-034)

실제 AC는 GPS·프로필로 항상 정확한 위치를 알기 때문에, 이 빠진 패턴이 예외가 아니라 주 경로였다는 게 라이브 테스트로 드러났다.

실전 규칙
새 계층을 만들 때 "이미 있는 다른 계층의 안전장치가 여기 없는 이유가 뭐지"를 항상 먼저 물어라.
② Root Primitive
부분 문자열 충돌 — 매칭 원시함수 자체를 의심하라

"문화재"⊃"화재"(응급감지 오탐)·"여권"⊃"여권진위확인"(관할 오분류)·"비자"⊂"소비자"·"입영"⊂"수입영수증"(둘 다 국가기관 오분류) — 전부 짧은 키워드가 우연히 더 긴 무관한 단어에 삼켜지는 같은 클래스의 버그다. 처음 세 번(BUG-025/026/030)은 발견될 때마다 그 단어 하나만 화이트리스트·복합어로 고쳤다. 네 번째(BUG-031)에서야 패턴 자체를 고쳤다.

수정 방식 — _kwMatch 신설

function _kwMatch(text, k) { if (!text || !k) return false; let idx = text.indexOf(k); while (idx !== -1) { const before = idx > 0 ? text[idx - 1] : ''; if (!/[가-힣]/.test(before)) return true; idx = text.indexOf(k, idx + 1); } return false; }

매칭 지점 바로 앞 글자가 한글 음절이면 그 위치의 매칭을 무시한다(뒤쪽은 조사가 자연스럽게 붙으므로 검사하지 않는다). 이 파일 전역 12개 text.includes(k) 호출 지점을 전부 교체했다. BUG-031의 개별 복합어 치환을 전부 폐기하고 bare 키워드로 원복해도 정상 작동함을 확인했다 — 이게 "진짜 근본 수정"이라는 증거다.

실전 규칙
같은 클래스 버그가 2번 이상 재발하면 3번째 사례를 개별 패치하기 전에 매칭 메커니즘 자체를 의심하라. 단, 응급감지 (EMERGENCY_RE)는 예외다(⑤ 참고).
③ False Assumption
"예외 지점"이라는 착각

BUG-028 때 EMD 확정 직전 "규칙 F 우회 검사" 지점을 "예외 감지라 위험 비대칭적"이라며 LLM 구제망 적용 대상에서 일부러 뺐다. 코드 구조만 보면 합리적이었다. 그런데 정부24 전수취합 코퍼스를 전체 주소(읍면동 명시)로 라이브 재실행하니, 그 "예외 지점"이 350건 중 다수를 처리하는 주 경로였다 — 실제 AC는 항상 정확한 위치를 알기 때문이다.

코드 구조상 "드물게 보이는 것"과 "실사용에서 드문 것"은 다르다.

실전 규칙
"이 지점은 예외라서 안전망 없어도 된다"고 판단할 때는 실제 호출 조건을 반영한 시나리오로 그 판단을 검증하라.
④ Blast Radius
구조적 수정은 반드시 파급효과를 남긴다 — BUG-034→BUG-035

BUG-034(EMD 비대칭 제거)는 "1단계는 성공했지만 확정을 보류하고 뒤 단계에 기회를 준다"는 새로운 상태를 만들었다. 문제는 2026-08-22에 이미 있던 다른 코드(5단계 SP-EMD-LAZY 재질문 로직)가 "이 지점 도달 = 1단계가 이미 실패했다는 뜻"이라는 전제로 짜여 있었다는 것이다. BUG-034가 그 전제를 깨뜨리면서, 이미 위치를 확보해둔 진짜 EMD 사무(주민등록표 등본 등)까지 전부 다시 "어느 읍면동이세요?"라고 되묻는 회귀가 생겼다.

이번엔 코드 리뷰가 아니라 라이브 스모크테스트 재실행으로 잡았다 — 로컬 사고실험(제한된 목)으로는 이 조합을 재현하기 어려웠다.

점검 절차

  1. 구조적 수정
  2. 로컬 회귀 테스트(최소 기준일 뿐)
  3. 가능하면 라이브 재검증
  4. 이전에 정상이던 게 이상해지면 "이 수정이 새로 만든 상태를 몰랐던 다른 코드"부터 찾기(날짜 주석 "이 지점 도달=X가 실패" 검색하면 빠름)
실전 규칙
큰 구조적 리팩터링을 할 때는 "이 변경이 만드는 새로운 상태 (또는 없애는 상태)를 전제로 짜인 다른 코드가 또 있는가"를 코드베이스 전체에서 검색하라.
⑤ Decision — DECISION-01
언제 일반화하고 언제 화이트리스트를 유지할 것인가

"개별 해법을 무한 반복할 수 없다" 원칙은 맞지만 모든 코드에 똑같이 적용하면 안 된다. 응급감지 부분문자열 오탐도 _kwMatch류로 일반화하자는 제안이 나왔는데, 실제 반영 전 적대적 시나리오로 스트레스 테스트했다.

규칙내용스트레스 테스트 결과
근접기반 일반화응급 키워드 앞뒤 15자에 서류마커면 예외 처리위험 — 12건 중 4건이 진짜 응급을 비응급으로 오판
보수적(화이트리스트 유지)긴급강조어 있으면 무조건 응급 유지11/12 통과, 유일 실패도 안전 방향

결론: 화이트리스트 유지.

판단기준라우팅응급감지
오분류 비용낮음비대칭적으로 큼
방향구조적 일반화화이트리스트 유지(순수 추가 전용, 회귀 위험 없음)
실전 규칙
안전 관련 코드를 고칠 때 "일반화하면 편해진다"는 유혹이 들면 먼저 적대적 시나리오 5개 이상으로 스트레스 테스트하라. 위음성 1건이라도 나오면 화이트리스트 유지가 맞다.
⑥ Methodology
검증 방법론 — 사고실험과 라이브 테스트의 역할 분담

혼디 라우팅은 문자매칭(빠른 경로)+의미검색(LLM classifyFn, 느린 경로)의 하이브리드다. 로컬 사고실험(목 classifyFn)은 "메커니즘이 작동하는가"는 증명하지만 "실제로 정확한가"는 증명 못한다 — 이 착시를 세 번 겪었다.

착시 사례실제 원인알아챈 방법
"어린이집"이 도서관으로 감 → 새 버그로 의심실제로는 2026-08-21에 이미 고친 계층 충돌인데 목이 그 판단을 못 흉내냄division-tables.js 주석·커밋 이력 확인
"1372 소비자상담센터"가 출입국으로 감 → 처음엔 목 오류로 추정실제로는 진짜 코드버그(bare 비자⊂소비자)classifyFn=null로 고정해 순수 키워드 경로만 격리 재현
350건 라이브에서 EMD 무차별 확정 확인 → 즉시 새 원인으로 판단실제 코드버그(BUG-034 필요성 확인, 이번엔 착시 아니라 진짜)trace의 "규칙 F 일반화" 문구 유무로 즉시확정 vs 폴백 구분
결정적 도구
"이상해 보이는 결과"를 볼 때마다 classifyFn을 진짜 null(함수가 아니라 값 자체가 null)로 고정해 같은 발화를 다시 돌려봐라 — 결과가 그대로면 순수 키워드 매칭 단계의 진짜 코드버그, 결과가 사라지면(제네릭으로 떨어지면) 목의 한계이거나 실제 LLM 판단력에 의존하는 부분이다.

라이브 테스트 인프라 자체도 버그를 가질 수 있다는 걸 잊지 마라 — 이번 세션에서 Origin 헤더 누락(403)과 결과 브랜치 경쟁 상태(동시 실행 시 데이터 유실) 두 건을 인프라 자체에서 발견했다. "라이브 결과가 이상하다"고 바로 코드를 의심하기 전에 테스트 스크립트·워크플로 자체가 의도한 조건을 정확히 재현하는지도 확인하라.

⑦ Post-Mortem
이번 세션에서 실제로 저지른 실수 목록
작업자 본인 실수

아래는 작업을 수행한 AI 비서(Claude) 본인이 저지른 실수를 시간 순으로 정리한 것이다. 다음 세션이 같은 실수를 반복하지 않도록 숨기지 않고 전부 남긴다.

  1. 디렉터리 복사 실수를 두 번 반복 — cp -r src/gopang 대상/src/gopang을 대상이 이미 있는 상태에서 실행해 대상/src/gopang/gopang/...로 중첩 복사되는 사고를 두 번 냈다. 그때마다 방금 수정한 코드가 아니라 오래된 코드로 테스트를 돌리고 있었다. 이후 rm -rf로 대상을 먼저 지우고 복사하는 걸 원칙으로 삼았다.
  2. 목이 만든 착시를 새 버그로 성급하게 단정할 뻔함 — "어린이집→도서관" 사례에서 코드 주석·커밋 이력을 먼저 확인 안 했으면 이미 고쳐진 문제를 다시 고치려 들 뻔했다.
  3. 키워드를 잘못된 자매 테이블에 넣음 — '취업지원 대상자' 키워드를 _guessNatAgencyDomainFromText용 테이블(비제주 전용)에 넣었다가, 재검증 과정에서 효과 없는 걸 보고서야 JEJU_NATIONAL_TABLE(실제 제주가 쓰는 표)로 옮겼다 — BUG-022가 경고했던 "자매 테이블 반영 누락" 함정에 스스로 빠졌다가 잡은 사례다.
  4. 위험한 일반화 규칙을 먼저 제안함 — 응급감지 화이트리스트를 근접기반 일반화 규칙으로 대체하자고 먼저 제안했는데, 스트레스 테스트 결과 진짜 응급 상황 4건을 비응급으로 오판하는 위험한 규칙이었다. 실제 코드 반영 전 검증한 게 다행이었다.
  5. EMD "규칙 F" 지점을 "예외라서 안전"이라고 잘못 판단 — BUG-028 당시 이 지점을 LLM 구제망 적용 대상에서 뺐는데, 이후 라이브 테스트로 그 지점이 실사용에서 주 경로였다는 게 드러났다(별도 재수정 BUG-034 필요).
  6. 구조적 수정(BUG-034)이 다른 코드의 전제를 깨뜨림 — 리팩터링 직후 "이 변경이 새로 만든 상태에 의존하는 다른 코드가 있는가"를 미리 점검 안 해서, 진짜 EMD 사무가 불필요하게 재질문하는 회귀(BUG-035)를 만들었다 — 사용자의 라이브 재실행으로 발견됐다.
  7. 라이브 스모크테스트 워크플로를 경쟁 상태로 설계 — 배치 7개를 동시 실행할 수 있게 만들면서도 결과를 커밋하는 브랜치를 배치 구분 없이 하나로 뒀다. 동시 실행 시 나중에 끝난 실행이 먼저 끝난 실행들의 결과를 --force 푸시로 덮어써서, 처음 7개 배치를 돌렸을 때 6개의 결과가 유실됐다. "배치별로 나눠 여러 번 돌린다"는 설계 목적 자체가 동시 실행을 전제하고 있었는데 그걸 놓쳤다.
  8. 메모리에서 데이터를 재구성하다 한 배치를 통째로 잃어버림 — 정부24 사고실험 시나리오 8개 배치(총 400건)를 라이브 테스트용으로 취합하는 과정에서 원본 스크립트 파일 중 하나가 이미 다른 작업으로 덮어써진 상태였다. 기억만으로 재구성하려다 한 배치를 다른 배치와 중복 입력해서 결국 7개 배치(350건)만 신뢰성 있게 복구, 나머지 1개는 "허위로 지어내지 않겠다"며 사용자에게 정직하게 누락을 알리고 원본을 다시 요청했다.
공통점
8개 실수 중 6개는 "검증하지 않고 넘어간 가정"에서 비롯됐다 — 복사가 제대로 됐다는 가정, 자매 테이블 이름이 맞다는 가정, 예외 지점이 실제로도 드물다는 가정, 구조적 수정이 다른 코드에 영향 없다는 가정, 워크플로가 동시 실행을 잘 처리한다는 가정, 저장소에 이미 해법이 없다는 가정. 전부 "확인 한 번이면 잡을 수 있었던" 것들이다.
