Overview
이 문서가 왜 있는가

하루 세션치고 변경 범위가 넓다 — 리프 신설 배치 두 번, 라우팅 아키텍처 리팩터 한 번, 실사 인프라 신설, 그리고 완전히 다른 주제(PDV 기록 원칙)의 조사·수정 두 건이 이어졌다. 다음에 이 영역을 다시 건드릴 사람(사람이든 다른 세션이든)이 "무엇이 바뀌었고 왜"를 처음부터 다시 추적하지 않도록, 산출물이 아니라 판단 근거 위주로 정리한다.

① Catalog & Audit
professor 전수 카탈로그·표준분류체계 감사

작업 지시는 "161개 리프를 사람이 읽기 좋게 정리"였다. dump_leaves.mjs·EXPERT_REGISTRY를 직접 import해(재구현 아님) 28개 중계열 그룹별 표로 정리하고, 이어서 근거 문서가 인용하는 「한국대학교육협의회 대학 학과 정보」 표준분류체계와의 대조 감사, K-12 대응 목적으로 신설된 4개 리프(교양음악·한문학·교양기술가정·진로교육)가 나머지 157개와 분류 기준이 다르다는 정합성 이슈까지 정리했다.

② International Standard
ISCED-F 2013 국제표준 대조

"대학은 국가·학교마다 과목명이 제각각인데 글로벌 표준은 있는가"라는 질문에 UNESCO ISCED-F 2013(11개 대분야·29개 중분야·80개 세부분야)을 확인. 이어서 "한국 표준분류체계가 글로벌 표준을 포괄하는가"라는 후속 질문에는 아니다로 결론 — 한국 체계는 의약·예체능을 ISCED-F보다 세밀하게 나누는 반면, ISCED-F가 독립 대분야로 두는 "10 Services"(치안·숙박업 등)는 한국 체계에 전용 자리가 없고, 실제로 161개 리프에도 경찰행정학·호텔경영학 같은 틈이 그대로 남아있음을 실제 카탈로그 대조로 확인했다.

③ Tier 1 Expansion
15개 대분야 세분화 + subject-gate 계층형 리팩터

법학·경제학처럼 "표준적으로 널리 알려진 하위분야가 있는데 지금은 리프 하나로 뭉쳐 있는" 대분야를 전수조사해 15개를 Tier 1로 확정(법학·경제학·물리학·생명과학·심리학·수학· 컴퓨터공학·철학·화학·사회학·정치외교학·기계공학·경영학· 역사학·전기공학) — 표준 하위분야 93개를 신규 리프로 등록.

발견한 구조적 위험 — flat 게이트가 254개 후보를 한 프롬프트에

93개를 그대로 추가하면 subject-gate.js의 refineToLeaf()가 161→254개 리프 전체를 단일 호출로 분류하게 된다는 걸 착수 전에 발견 — 이미 162개 시점에서도 max_tokens 1000→1500 재상향이 필요했던 이력이 있어 토큰 소진·정확도 저하가 사실상 확정적이었다. 리프를 추가하기 전에 refineToLeaf()를 flat 단일호출에서 재귀형 계층 게이트로 먼저 리팩터(직계 자식만 단계별로, 자식이 2개 이상일 때만 호출)한 뒤 리프를 얹었다 — 그 결과 리프가 161→254개로 늘어도 루트 게이트 후보 수는 29개로 그대로였다(기존 15개 대분야가 flat 형제로 추가된 게 아니라, 기존 리프 자리에 새 중계열이 "승격"돼 같은 슬롯을 차지했기 때문).

⑥ PDV Recording
UNIVERSAL-common §U0-1(모든 SP의 PDV 기록 의무) 4대 요건 완성

§U0-1(이 문서의 제1원칙)은 대화 종료 시 ①기록 ②6하원칙 요약 ③분류 ④즉시조회 4가지를 요구한다. 교수 포함 EXPERT 페르소나 61개가 공유하는 expert-chat.html 경로를 코드 레벨로 조사한 결과 ①②는 되고 있었으나, why 필드가 호출부에서 null로 하드코딩돼 있었고 (라이브러리 결함 아님, 호출부만의 문제), ④(즉시조회)는 엔드포인트 자체가 존재하지 않았다.

해결 — DB 마이그레이션 없이

기존 스키마에 필요한 필드가 이미 다 있었다. 신규 /owner-pdv/self-history 엔드포인트(같은 기관이 같은 사용자의 과거 기록을 자기가 보는 것 — 기관 간 교차가 없어 U8의 동의 기반 프로토콜과 무관하게 훨씬 가벼운 전용 경로로 설계)와 클라이언트 함수 queryOwnerPdvSelfHistory()를 신설, 세션 시작 시 인사말을 만들기 전에 자동 조회하도록 배선했다. why는 세션 첫 사용자 발화로 채운다(별도 요약용 LLM 호출 추가 없이 저비용 개선).

⑦ Correction
AGY_VAULT_STORE 재조사 — 잘못된 판단 정정 + 실제 구멍 수정

국가기관 SP 경로도 같은 방식으로 손보려다가, "실행기가 아예 없다"는 이전 판단(UNIVERSAL-common 문서 서술만 믿고 코드를 직접 안 본 데서 나온 오류)이 틀렸음을 발견했다. worker.js의 handleGovRelay에는 2026-07-23부터 이미 [AGY_VAULT_STORE] 인터셉트·저장 로직이 있었고, 342개 국가기관 공용 진입점이라 절대다수 케이스를 이미 커버하고 있었다.

실제 남아있던 구멍
위임(SP_CALL)이 실제로 발동해 새 LLM 응답을 받는 4개 지점(거부 재합성·서브호출 실패·위임 성공 합성·안전문구 대체)은 이 인터셉트를 거치지 않고 있었다 — 기록 누락뿐 아니라 태그 원문이 사용자 화면에 그대로 노출될 수 있는 더 심각한 문제였다. 인라인 로직을 _interceptAgyVaultStore() 헬퍼로 추출해 4개 지점 전부에 배선, 결제·라우팅 로직은 건드리지 않았다.
Lesson
문서 서술이 아니라 코드를 본다

이 세션 전체에서 반복된 하나의 원칙: "구현됐는가"를 판단할 때 문서의 정직 고지 문단조차 그대로 믿지 않고, 항상 코드를 직접 grep해서 확인한다. ⑦에서 그 원칙을 어긴 대가(잘못된 계획 제시)를 직접 겪었고, 바로 정정했다. UNIVERSAL-common의 "현재 구현 상태" 절도 이번에 산문에서 SP 카테고리별 표로 바꿨다 — 다음 세션이 "교수는 됐으니 이제 다 됐나?"라고 착각하지 않도록.
