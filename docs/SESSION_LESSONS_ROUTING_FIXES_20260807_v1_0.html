SITE MANUAL — 2026-08-07 세션 발견 정리

고친 것보다 왜 고쳤는지가 더 오래 남는다

2026-08-06 HANDOFF를 이어받아 5분기(K-서비스·전문가AI·중앙정부· 지방정부·시장) 라이브 스모크테스트를 새로 설계·실행하고, 거기서 나온 FAIL들을 하나씩 원인 규명해 3건을 고친 하루였다. 그 과정에서 처음 내린 진단("조용한 실패")이 코드를 직접 보고 나서 뒤집힌 사례, 같은 자리를 세 번째로 고치면서 접근 자체를 바꾼 사례, 인프라 자체의 숨은 함정을 우연히 밟은 사례가 나왔다 — 이 문서는 그 원리와 실패 패턴을 정리한 것이다.

대상 저장소 Openhash-Gopang/gopang 관련 PR #258~#262 작성 2026-08-07
Overview
이 문서가 왜 있는가

이 문서는 2026-08-06 세션의 직접적 후속편이다. 그날 만든 5분기 스모크테스트 배치(48건)를 실제로 라이브 실행하고, 거기서 나온 FAIL들을 재현성 확인(§0-2 방식, 15~45회 반복) → 원인 규명 → 수정 → 재실행 검증까지 끝까지 밟은 세 사이클을 기록한다. 전부 이번 세션에서 실제로 밟은 함정이고, 세 건 모두 라이브 재실행으로 "고쳐졌다"를 직접 확인했다.

이 문서를 읽어야 하는 상황
라이브 스모크테스트 결과를 보고 "버그인지 시나리오 설계 오류인지" 가릴 때 / call-ai.js의 fire-and-forget 재귀 호출 구조를 건드릴 때 / §CORE의 R1 판정축이나 §INFO의 "직접 답변 허용" 경로를 고칠 때 / results 브랜치가 원하는 실행 결과를 안 보여줄 때.
① Root-Cause Discipline
"조용한 실패"라는 자기진단이 틀렸던 이유

§TAGS 문서의 kestate/ktelecom 예외 경고문("존재하지 않는 탭을 열려다 조용히 실패한다")을 그대로 읽고, 40/40 라이브 재현 결과를 붙여 "실사용자 화면에서 조용히 실패하는 실제 장애"라고 진단했다. 이 진단은 틀렸다. call-ai.js를 직접 열어보니 2026-08-01에 이미 자동복구 안전망 (_forwardSwitchSP)이 들어가 있었고, 잘못된 문법을 감지하면 조용히 올바른 SP로 전환하고 있었다 — §TAGS의 경고문 자체가 그 안전망이 생기기 전 서술 그대로 낡아 있었을 뿐이다.

진짜 문제는 따로 있었다: 그 안전망이 fire-and-forget으로 callAI()를 재귀 호출하는데, 바깥쪽 callAI()의 finally가 조건 없이 _currentAbort = null을 실행해서, 안쪽 호출이 방금 세팅한 AbortController를 지워버릴 수 있는 경쟁조건이었다. 이건 코드 자체의 주석에 "미검증 잔여 리스크"로 이미 남겨져 있었다 — 프롬프트 문서만 읽고 멈췄다면 발견 못 했을 문제다.

교훈
프롬프트 문서(SP)에 적힌 "이렇게 실패한다"는 서술은 그 문서가 마지막으로 갱신된 시점의 진실일 뿐이다. 실제 코드가 그 뒤에 바뀌었을 수 있다 — 심각도를 판단하기 전에 항상 관련 코드를 직접 열어봐야 한다. 라이브 재현으로 "버그가 있다"는 확정할 수 있어도, "그 버그의 실사용자 영향이 얼마나 되는지"는 코드를 봐야만 안다.

수정 방식 — compare-and-clear

AbortController를 callAI() 지역변수(myAbort)로 스냅샷해두고, finally에서 _currentAbort === myAbort일 때만 정리하도록 바꿨다. 다른 callAI() 실행이 이미 자기 것으로 갱신했으면 그대로 둔다 — 표준적인 "내가 만든 것만 내가 치운다" 패턴이다.

② Pattern Over Example
개별 예시보다 일반 규칙이 이긴다

§CORE의 klaw R1 예시 문단은 이미 같은 하루(2026-08-06)에 한 번 재정정된 이력이 있는 자리다 — "관세 통관"을 예시로 들었다가 klogistics·customs-broker와 충돌해서 "감정평가"로 바꿨다. 이번 세션에서 세율(ktax)·해고 통지 기준(kbusiness)·교통 벌금 (ktransport) 3개 도메인이 전부 klaw로 흡수되는 걸 45/45 완전 결정론적으로 재현했는데, 처음 든 생각은 "또 다른 개별 예시를 추가해서 막자"였다.

그 대신 일반 원칙을 추가했다: "전용 GWP가 있는 영역은 '법적으로' 표현이 들어가도 그 GWP가 우선한다." 개별 단어를 나열하는 대신 판단 순서 자체를 명시한 것이다.

접근이번 세션 이전 이력이번 결과
개별 예시 나열특허→변리사 충돌, 관세→klogistics 충돌 (2회 실패)—
일반 규칙(신규 시도)3개 도메인 45/45 한 번에 해결, 새 충돌 없음
교훈
같은 자리에서 같은 종류의 충돌이 반복된다면, 그건 "예시가 하나 더 필요하다"는 신호가 아니라 "예시로는 이 문제의 형태를 못 담는다"는 신호일 수 있다. 개별 사례를 계속 추가하는 건 매번 새로운 충돌 표면을 만드는 것과 같다 — 원칙 하나로 여러 사례를 동시에 커버할 수 있는지 먼저 물어봐야 한다.
③ Conflicting Instructions
§INFO와 §CORE가 경합하고 있었다

§1에 이미 "당신은 개체를 대신해 직접 답하지 않습니다"라는 명시적 원칙이 있었는데도, klogistics·ksecurity 등에서 태그 없이 정보성 텍스트만 주고 끝나는 회귀가 17/25건 나왔다. 문구를 더 세게 쓰는 접근(kestate/ktelecom에서 이미 안 먹혔던 방식) 대신, 경합하는 다른 지침이 있는지를 먼저 찾아봤다.

찾았다 — §INFO("정보 해결 3경로")가 "§CATALOG에 답이 없다는 게 안내를 줄 수 없다는 뜻은 아니다, 웹검색 등으로 직접 답하라"고 하는데, 이 "답이 없다"가 (a) 그 주제를 다루는 GWP 자체가 없다는 뜻인지 (b) GWP는 있지만 구체적 수치가 표 텍스트에 안 적혀 있다는 뜻인지 구분돼 있지 않았다. 실패 사례는 전부 (b)였는데 모델이 이걸 (a)로 오인해 §INFO의 "직접 답변 허용" 경로로 새고 있었다.

§INFO 서두에 적용 범위를 명확히 하는 문단을 추가했다 — "§CATALOG에 담당 GWP가 있으면 이 경로로 가지 않는다." 재실행 결과, 핵심 20건(klogistics 10·ksecurity 10)이 전부 해결됐다.

완전히는 안 풀렸다
같은 재실행에서 kedu 1건은 klaw로, kinsurance 1건은 kgov로 여전히 샜다 — 둘 다 "태그 누락"이 아니라 각각 다른 새 갈래 (klaw 과잉흡수의 4번째 사례, §GOV_MATCH 경계 문제)로 보인다. 한 번의 수정이 원래 겨냥한 문제(태그 누락)는 확실히 잡았지만, 비슷해 보이던 인접 사례까지 전부 해결하지는 못했다 — 다음 세션 과제로 남긴다(⑥ 참고).
④ Methodology
재현 배치는 고쳐도 재사용한다

세 수정 전부 "수정 전 FAIL을 확정한 바로 그 시나리오 파일"을 수정 후에도 그대로 재실행했다 — 새 시나리오 파일을 만들지 않았다. klaw 과잉흡수는 45/45 FAIL → 45/45 PASS로 완전히 뒤집혔고, §INFO 수정은 같은 배치 안에서 도메인별로 결과가 갈렸다(klogistics/ksecurity는 완전 해결, kedu/kinsurance는 그대로).

같은 배치를 재사용했기 때문에 이 도메인별 차이가 선명하게 보였다 — 만약 매번 새 시나리오를 만들었다면 "부분적으로만 고쳐졌다"는 걸 놓치고 "고쳐졌다"고 성급히 결론 냈을 수 있다.

교훈
수정의 효과를 재는 자(尺)는 수정 전과 똑같아야 한다. 재현 배치를 "이번에 고칠 것"뿐 아니라 "다음에 또 쓸 회귀 테스트"로 설계해두면, 전후 비교뿐 아니라 인접 영역이 실수로 깨지지 않았는지도 같은 실행에서 같이 확인된다.
⑤ Infra Gotcha
결과 브랜치는 비누적식이다

results/live-smoketest 브랜치에서 이전 실행 결과를 다시 찾으려다가 두 번 헛걸음했다. 첫 번째는 이미 다음 실행이 같은 경로를 덮어써서 사라진 경우, 두 번째는 패치 머지 직후 자동으로 트리거된 check-routing-regression.yml (회귀 게이트)이 수동 live-smoketest.yml 실행 바로 뒤에 같은 브랜치에 커밋하면서 그 결과를 덮어쓴 경우였다.

이 브랜치는 실행별로 쌓이는 게 아니라, 실행할 때마다 그 시점의 결과로 덮어써진다 — 두 워크플로가 서로 다른 시나리오를 테스트해도 같은 하위 경로 구조를 공유하면 나중에 커밋한 쪽이 이긴다. GitHub Actions 아티팩트(gh run download)는 워크플로 실행마다 독립적으로 보존되므로, 브랜치보다 아티팩트가 더 신뢰할 수 있는 기록이다.

아직 안 고친 것
두 워크플로가 결과를 쓰는 경로를 분리하거나(예: 수동 실행은 results/manual/, 자동 게이트는 results/gate/), 최소한 관례로 "패치 머지 직후엔 곧바로 라이브 재실행하지 말고 자동 게이트가 끝난 뒤에 하기"를 정해두는 게 다음 개선 후보다.
⑥ Handoff
아직 남은 두 갈래

§INFO 수정(③) 재실행에서 새로 드러난 것 두 건은 이번 세션에서 손대지 않았다 — 다음 세션 우선 과제로 남긴다.

  • kedu vs klaw: "학교폭력을 신고하면 법적으로 어떤 절차로 처리되나요"가 [GWP: klaw]로 감. ②의 klaw 과잉흡수 일반 규칙이 ktax/kbusiness/ktransport 3개만 명시적으로 예시를 들어서, kedu까지는 완전히 안 퍼진 것으로 보인다 — 규칙 자체의 적용 범위인지, 아니면 별도 원인인지 아직 미규명.
  • kinsurance vs kgov: "실업급여는 최소 며칠 일해야 받을 수 있게 정해져 있나요"가 [GWP: kgov]로 뭉뚱그려짐. §GOV_MATCH 절 자체가 이미 "실업급여→고용센터/ 고용보험은 GWP_REGISTRY_SEARCH 대상"이라고 명시하고 있는데도 안 지켜지고 있다 — ②·③과는 다른, §GOV_MATCH 경계선 자체의 문제로 보인다.
