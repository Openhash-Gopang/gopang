SITE MANUAL — 2026-08-05 저녁 세션 발견 정리

응답이 "안 온다"는 증상 하나에도 최소 세 가지 서로 다른 원인이 겹쳐 있을 수 있다

이날 저녁 세션은 K-Compose STEP 1의 status:draft 처리 수정(같은 날 오전 커밋)을 라이브에서 검증하려던 것으로 시작했다. hondi.net에서 "안심상속" 시나리오를 여러 번 입력했는데 응답이 5분 이상 지연되거나 아예 안 오는 현상을 만났고, 그 원인을 추적하며 여러 번 잘못된 가설을 세웠다가 스스로 정정했다. 최종적으로는 검증하려던 버그와 전혀 무관한, 훨씬 근본적인 두 가지 문제(빈 응답· 순차 지연)를 발견했다. 이 문서는 그 추적 과정에서 실제로 밟은 디버깅 함정을 정리한 것이다.

Overview
이 문서가 왜 있는가

이 문서는 응답 지연·빈 응답 버그 자체의 수정 방법을 다루지 않는다(그건 HANDOFF_2026-08-05_live-smoketest-latency-and-empty-content.md가 다룬다). hondi.net처럼 사용자가 실제로 쓰는 시스템에서 "왜 응답이 안 오지?"를 라이브로 디버깅할 때 또 밟게 될 게 뻔한 함정들을 모아뒀다. 전부 오늘 세션에서 실제로 겪은 시행착오이고, 몇 개는 스스로 세운 가설을 스크린샷 몇 장 뒤에 스스로 정정한 사례다.

이 문서를 읽어야 하는 상황
라이브 시스템에서 "응답이 안 온다/느리다"를 디버깅할 때 / wrangler tail·브라우저 DevTools를 같이 쓸 때 / SSE 스트리밍 응답을 분석해야 할 때 / "정상 종료됐는데 결과가 이상하다"는 버그를 마주쳤을 때 / 여러 단계로 이어지는 오케스트레이션·에이전트 체인의 지연 원인을 찾을 때.
Goal
오늘 세션의 목표와 흐름
  1. 검증 목표 — 그날 오전 커밋한 K-Compose STEP 1 status:draft 처리 수정이 라이브에서 실제로 동작하는지 확인.
  2. 1차 관찰 — hondi.net에 "안심상속" 관련 발화를 입력, 응답이 5분+ 지연되거나 다른 메시지("안녕")에 뒤늦게 붙어서 나오는 현상 관찰.
  3. 1차(틀린) 가설 — GDC 지갑 잔액 0으로 인한 과금 실패(AI_CHARGE_FAILED)가 원인이라고 짐작 → worker.js의 _chargeGdcForAiUsage() 주석을 코드로 직접 확인한 결과 응답 자체는 막지 않는다는 게 드러나 정정.
  4. 2차(틀린) 가설 — "수천 번 deepseek 호출"로 폭주 중이라고 우려 → wrangler tail과 Network 패널을 대조한 결과 SSE 스트리밍 청크 수를 호출 횟수로 착각한 것으로 확인·정정(§1 참고).
  5. 결정적 증거 — 브라우저 Console에 fetch 가로채기 스크립트를 심어 응답의 reasoning_content와 content를 분리해서 확인 → content가 완전히 비어있는데 finish_reason:"stop"으로 정상 종료된 것을 확인(§4 참고).
  6. 근본 원인 확정 — 코드 감사로 (a) thinking 모드가 completion 예산을 잠식하는 기존에 알려진 버그의 재발, (b) 오케스트레이션 체인의 모든 홉이 순차·동일 모델로 실행되는 구조적 지연, 두 가지를 확정.
01 · Streaming
SSE 청크 수를 호출 횟수로 착각하지 마라
"1000여 줄이 찍혔다" = 폭주가 아니라 토큰 하나당 한 줄일 뿐

DevTools Network 패널에서 deepseek 요청의 Response를 열었을 때, 왼쪽 파일 목록에 같은 이름의 요청이 여러 개(792, 793, 795, 797...) 있는 것처럼 보여서 "deepseek 5건이 각기 1000여 건씩 출력"이라고 순간적으로 판단했다. 실제로는 SSE (Server-Sent Events) 스트리밍은 토큰 하나(또는 몇 글자)마다 별도의 data: {...} 줄을 찍기 때문에, 답변 하나가 조금만 길어도 수백~수천 줄이 되는 게 정상이다. 마지막 줄의 data: [DONE]이 "이 응답 하나가 정상 종료됐다"는 표준 신호다.

줄 번호로 보인 것실제 의미
같은 요청 안의 1567~1592번 줄토큰 스트리밍 청크 26개(응답 하나)
wrangler tail의 POST /deepseek 횟수실제 API 호출 횟수(이 시간대엔 3회뿐이었음)
일반화된 교훈
실제 호출 횟수는 서버 진입점 로그(예: wrangler tail의 POST 라인 수)로 세는 게 정확하다. 클라이언트 Network 패널에 보이는 줄 수는 스트리밍 프로토콜의 청크 단위일 뿐, 호출 단위가 아니다.
02 · Client vs. server
서버 로그와 브라우저 콘솔은 완전히 다른 프로세스다
wrangler tail에서 클라이언트 전용 로그를 찾다가 여러 턴을 낭비함

_handleOrchestrationTags()(call-ai.js)의 console.log('[Orchestration] PROCEDURE_MAP_LOOKUP 감지...')는 브라우저에서 실행되는 클라이언트 코드다. 이걸 Cloudflare Workers의 wrangler tail(서버 진입점 로그)로 찾으려고 몇 번을 살펴봤는데 당연히 안 나온다 — 애초에 다른 프로세스, 다른 머신에서 실행되는 로그다.

일반화된 교훈
코드를 뒤지기 전에 그 로그가 어디서 실행되는 코드에 있는지부터 확인하라 — 프론트엔드(src/gopang/ai/ call-ai.js, 브라우저 Console) vs 백엔드 (worker.js, wrangler tail)는 겹치지 않는 두 세계다. 파일 경로만 봐도 대개 구분된다.
03 · DevTools 사용법
Network URL 필터로 콘솔 로그·응답 본문을 찾을 수 없다
"Orchestration"으로 필터링해도 항상 0건 — 애초에 URL에 그 문자열이 없기 때문

Network 탭 상단의 필터 입력창은 요청 이름(URL)만 걸러낸다. 응답 본문 안의 텍스트나 콘솔 로그 문구를 찾는 용도가 아니다 — Orchestration으로 필터링하면 그 문자열이 URL에 없는 한 항상 0건이 나온다. 이걸로 몇 턴을 허비한 뒤에야 제대로 된 방법으로 바꿨다:

제대로 된 방법 — Console에서 fetch 가로채기

(function(){
  const orig = window.fetch;
  window.fetch = async function(...args) {
    const res = await orig.apply(this, args);
    if (String(args[0]).includes('deepseek')) {
      const clone = res.clone();
      clone.text().then(t => {
        const lines = t.split('\n').filter(l => l.startsWith('data: ') && !l.includes('[DONE]'));
        let reasoning = '', content = '';
        for (const line of lines) {
          try {
            const j = JSON.parse(line.slice(6));
            const d = j.choices?.[0]?.delta;
            if (d?.reasoning_content) reasoning += d.reasoning_content;
            if (d?.content) content += d.content;
          } catch(e) {}
        }
        console.log('=== REASONING ===\n' + reasoning);
        console.log('=== FINAL CONTENT ===\n' + content);
      });
    }
    return res;
  };
})();

이 방법이 이번 세션에서 실제로 결정적 증거를 냈다(§4 참고) — SSE 청크를 한 줄씩 눈으로 읽거나 URL 필터로 헤매는 것보다 훨씬 빠르다.

04 · Silent failure
finish_reason:"stop"은 성공을 보장하지 않는다
reasoning이 completion 예산을 다 먹으면 content가 빈 채로 "정상 종료"된다

fetch 가로채기로 확인한 실제 사례 — 사용자가 "안심상속 확인해줘"를 재차 보냈을 때, 모델의 reasoning_content는 "재요청해야 하나, status-check용 표준 태그가 없는데..."를 장문으로 고민했고, content(사용자에게 실제로 보일 답)는 완전히 빈 문자열이었다. 그런데도 응답은 finish_reason:"stop"으로, 즉 API 관점에서는 정상 종료됐다.

근본 원인(코드로 확인됨)
src/gopang/core/token-policy.js에 이미 한 번 발견되고 부분 완화된 동일 클래스 버그가 기록돼 있었다(#180). hondi-pro는 thinking: enabled가 기본값이라 최종 답 전에 reasoning에 토큰을 먼저 쓴다. CHAT_REPLY_PRO를 800→4000으로 이미 한 번 올려 완화했지만, 이번처럼 reasoning이 그보다 길어지면 4000 예산 전체를 reasoning이 잠식하고 content가 0으로 남는다.
일반화된 교훈
reasoning/thinking 모드가 있는 모델을 쓸 때, API가 보고하는 종료 사유(finish_reason)와 실제 유용한 출력이 생성됐는지는 별개다. content가 비어있는지를 reasoning과 별도로 검사하지 않으면, 시스템은 이 실패를 영원히 "정상"으로 취급한다.
05 · Latency
순차 다단계 LLM 재주입 구조가 지연을 곱한다
태그 하나 감지될 때마다 새 hondi-pro 호출 — 5단계면 지연이 5번 곱해짐

_handleOrchestrationTags는 PROCEDURE_MAP_LOOKUP 같은 태그를 감지할 때마다 sendFn(기본값 callAI)으로 새 deepseek 호출을 만든다. 이 재호출에 모델을 지정하는 override가 없어서, 오케스트레이션 체인의 모든 홉(AC 판단 → K-Intent → 태그 재주입 → K-Compose → K-Execute → K-Deliver)이 전부 hondi-pro(thinking 켜짐)로, 그것도 순차(sequential)로 실행된다. 무거운 호출 하나가 수십 초 걸리는데 그게 4~6단계 이어지면 수 분이 걸리는 게 당연하다.

일반화된 교훈
다단계 에이전트/오케스트레이션 체인을 설계할 때, 모든 홉이 같은 무게의 모델을 쓸 필요는 없다. "결과를 받아서 다음 단계로 넘기기만 하는" 기계적 홉과 "진짜 판단이 필요한" 홉을 구분하지 않으면 지연이 홉 수만큼 곱해진다. (구체적인 해법은 HANDOFF_2026-08-05_live-smoketest-latency-and-empty-content.md §4에 정리돼 있다 — 진행상황 표시 의무화 → 홉별 모델 분리 → 기계적 분기의 LLM 호출 자체 제거, 3단계 순서로 진행 예정.)
Checklist
다음에 라이브 디버깅할 때

"응답이 안 온다/느리다"를 처음 마주쳤을 때

  • 먼저 아주 단순한 메시지("안녕")로 기준선을 확인했는가 — 이 시나리오만 문제인지, 시스템 전체가 막혔는지 구분
  • 서버 로그(wrangler tail)와 클라이언트 로그(브라우저 Console)를 둘 다 확인했는가, 그리고 각각 어느 코드가 찍는 건지 파일 경로로 먼저 확인했는가

Network 패널을 읽을 때

  • 같은 이름의 요청이 여러 줄 보이면, 그게 별도 호출인지 하나의 스트리밍 응답의 청크인지(data: [DONE] 유무로) 확인했는가
  • 응답 본문 안의 특정 문자열을 찾아야 한다면 URL 필터가 아니라 fetch 가로채기나 응답 본문 검색 기능을 썼는가

reasoning/thinking 모드가 있는 모델을 쓸 때

  • finish_reason:"stop"만 보고 성공으로 단정하지 않고, content가 실제로 비어있지 않은지 별도로 확인했는가
  • 다단계 체인이라면 각 홉이 정말 무거운 모델(thinking 켜짐)이 필요한 홉인지, 아니면 결과만 넘기는 기계적 홉인지 구분했는가
