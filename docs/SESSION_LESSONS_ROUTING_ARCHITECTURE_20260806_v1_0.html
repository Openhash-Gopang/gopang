SITE MANUAL — 2026-08-06 세션 발견 정리

라우팅은 순서가 아니라 습관이다

2026-08-06 세션은 AC의 죽은 코드 정리에서 시작해, EXPERT 페르소나 오배치 방어, GWP↔EXPERT 편향 방지책 4종, R1(GWP vs EXPERT)· R2(GWP vs GWP) 판정축 신설, 도메인 키워드 충돌 검사기 제작까지 이어진 긴 하루였다. 그 과정에서 같은 종류의 실수(의미론적 판단만 하고 문자열로 검증 안 함)를 두 번 반복하고서야 진짜 교훈을 얻었다 — 이 문서는 그 원리와 실패 패턴을 정리한 것이다.

대상 저장소 Openhash-Gopang/gopang 관련 PR #233~#249 작성 2026-08-06
Overview
이 문서가 왜 있는가

이 문서는 개별 기능의 사용법 매뉴얼이 아니다. AC-PRO-CORE의 §CORE 라우팅 로직, gwp-registry.js·expert-registry.js 의 trigger 표, R1/R2 판정축을 다시 건드릴 때 또 밟게 될 게 뻔한 함정들을 모아뒀다. 전부 이번 세션에서 실제로 밟은 함정이고, 그중 둘(klaw/klogistics·klaw/appraiser 충돌)은 라이브 스모크테스트로 20회 반복 재현까지 해서 확정한 것이다.

이 문서를 읽어야 하는 상황
AC-PRO-CORE의 R1/R2 판정축이나 §CATALOG "분야" 서술을 고칠 때 / gwp-registry.js·expert-registry.js의 trigger 배열을 추가·수정할 때 / "왜 이 발화가 엉뚱한 서비스로 갔지"를 디버깅할 때 / 새 라우팅 회귀 테스트를 설계할 때.
① Core Insight
라우팅은 순차 탐색 알고리즘이 아니라 프롬프트 안의 우선순위 서술이다

처음엔 "K시리즈 → 정부기관 → EXPERT → 비즈니스맥락 → 개인·사물" 5단계를 순차 탐색 알고리즘(코드가 하나씩 확인 하다 먼저 매칭되면 멈추는 방식)으로 이해했다. 실제로는 §CATALOG·§CATALOG-EXPERT 전체가 한 프롬프트 안에 동시에 존재하고, LLM이 한 번의 판단으로 전체를 놓고 고른다 — "①이 ②③보다 먼저 검색된다"는 문자 그대로의 순차 탐색이 아니라, 모델에게 준 우선순위 지침이다.

왜 이게 중요한가
"왜 선순위가 후순위를 밀어내는가"라는 질문의 답이 "코드가 일찍 멈춰서"가 아니라 "모델이 더 일반적이고 눈에 익은 후보로 자동 수렴하는 습관 때문"이다(AC-PRO-CORE 자체 진단: "판단력 부족이 아니라 습관"). 이건 순서를 아무리 바꿔도 안 없어지는, 모델 자체의 행동 편향이다 — 300건 라이브 테스트 진짜 FAIL 39건 중 23건(59%)이 정확히 이 패턴이었다.
② Structure
§CORE 4단계와 그 안에 중첩된 판정축들

전체 구조

R0응급 — 모든 것에 우선하는 예외, §CORE 4단계 전체를 건너뜀
§CORE-1의도 파악 — 확신도 기반 되묻기 규칙 포함
§CORE-2최적 주체 결정 — 주체 5단계 + R1 + R2 + §GOV_MATCH + "표 안/밖" 이분법이 전부 이 안에 중첩
§CORE-3대응 SP 검색 — 정확한 id, 철자 추측 금지
§CORE-4호출 또는 생성
§INFO위 라우팅과 직교 — 웹검색→PDV 과거대화→핸드셰이크

이번 세션에서 검증·수정된 것

  • R1(GWP vs EXPERT 축, 2026-08-01 기존): 위임의도 문구 있어도 GWP trigger 표에 해당 단어가 없으면 흔들리는 걸 발견 → "trigger 매칭이 아니라 '분야' 개념 매칭"으로 보강
  • R2(GWP vs GWP 축, 2026-08-06 신설): ktax↔klogistics의 "관세", ktax↔kbusiness의 "부가세"처럼 GWP끼리 충돌할 때 더 구체적인 trigger가 이겨야 한다는 원칙이 지금까지 없었음
③ Root Cause
도메인 소유권이 세 곳에 흩어져 있고, 서로 검증 안 된다

오늘 낸 버그 3개(klaw/klogistics 통관 충돌, klaw/appraiser 감정평가 충돌, 그리고 처음부터 있던 ktax/klogistics·ktax/kbusiness 충돌)가 전부 같은 구조적 원인에서 나왔다.

계층파일성격
GWP 키워드 색인gwp-registry.js triggers[]클라이언트 문자열 매칭용
GWP 개념 서술AC-PRO-CORE_v1_1.txt §CATALOG "분야" 칸LLM의 의미론적 참조용
EXPERT 키워드 색인expert-registry.js triggers[]클라이언트 문자열 매칭용

이 세 곳이 서로 교차검증되지 않는다. 한 곳에서 "이 단어는 A 서비스 것"이라고 정하면, 다른 곳에서 같은 단어를 B 서비스 것으로 이미 써놨는지 아무도 자동으로 확인 안 해준다. 이걸 메우는 check_domain_keyword_collision.py를 만들었는데, 이것도 처음엔 §CATALOG 다음 텍스트만 보고 §CATALOG 앞쪽(실제 사고 지점)은 놓쳤고, 그 다음엔 한글 조사 때문에 정규식 단어경계(\b)가 깨져서 또 놓쳤다.

핵심 교훈
검사 도구를 만드는 것 자체도 검증이 필요하다 — 실제 버그 재현 텍스트에 돌려보기 전까진 도구가 제 역할을 하는지 알 수 없다.
④ Core Insight
"하이브리드"라는 말의 진짜 의미

"의미 검색과 문자열 검색의 하이브리드 아닌가"라는 질문이 이번 세션에서 가장 뼈아팠던 지점이었다. R1 조항에 "관세 통관도 klaw 영역"이라는 예시를 추가할 때, 순수하게 의미론적으로만 판단하고 문자열로 실제 충돌을 검색해보지 않았다. 결과: 그 예시 문구 자체가 이미 다른 GWP(klogistics)가 등록해둔 문자열과 충돌해서, 명확한 위임의도 발화가 오케스트레이션([CALL_KINTENT:]) 으로 새는 회귀를 만들었다(temperature=0에서 20/20 완전 재현).

교훈
"의미로 판단하라"는 지침을 쓸 때조차, 그 지침에 넣는 구체적 예시 단어는 반드시 문자열 검색으로 기존 등록 현황과 대조해야 한다. 의미론과 문자열 검색은 경쟁 관계가 아니라, 후자가 전자의 전제조건이다.
⑤ Design Principle
오류 자체보다 "후속 조치의 유무"가 실사용자 영향을 가른다

같은 종류의 태그 문법 오류인데 결과가 다른 두 사례를 비교하며 배운 것이다.

  • kestate/ktelecom: 모델이 [GWP: kestate]라는 구식 문법을 가끔 쓴다(프롬프트 경고에도 불구하고). 하지만 call-ai.js에 이미 코드 레벨 자동복구(_forwardSwitchSP)가 있어서, 잘못된 문법을 감지하면 조용히 올바른 SP로 전환한다. 단위테스트로 "복구 분기 진입"까지는 확인했지만, "복구가 끝까지 완주해 정상 응답이 나오는지"는 아직 실배포에서 검증된 적 없다.
  • EXPERT가 GWP를 잘못 채가는 경우: 되돌림 메커니즘 자체가 설계에 없었다. 한번 잘못된 탭이 열리면 사용자가 직접 알아채고 돌아가는 수밖에 없었다. SUGGEST_SERVICE_REDIRECT 태그를 만들어 이 공백을 메웠다(강제 전환이 아니라 사용자 동의 기반 제안 배너로).
교훈
확률적 시스템(LLM)에서 오류를 100% 없애는 건 불가능하다. 그래서 "오류가 일어날 수 있다는 전제 하에 후속 조치가 있는가" 가 "오류가 아예 없는가"보다 더 중요한 설계 질문이다.
⑥ Methodology
스모크테스트를 만드는 방법론에서 배운 것
  • trigger 문자열을 그대로 쓴 테스트는 거의 동어반복이다. 첫 배치(35건)가 34/35로 "너무 잘 나와서" 의심스러웠는데, 까보니 20개 중 17개가 등록된 trigger 단어를 발화에 그대로 박아넣고 있었다. "모델이 상황을 이해하는가"가 아니라 "정규식이 문자열을 잘 찾는가"를 시험한 셈이었다.
  • 재현성 검증이 필수다. temperature=0이어도 완벽히 결정적이지 않을 수 있다는 우려가 있었는데, 실제로 동일 발화 20회 반복 결과 19건이 문자 그대로 동일했다 — 이 사실 자체가, 관측된 실패가 "일회성 변동"이 아니라 "체계적 버그"라는 걸 확정하는 근거가 됐다.
  • static_verdict: WARN 관례가 유용했다 — 확신 없는 정답을 PASS로 위장하지 않고 정직하게 낮은 확신도로 표시해두면, 나중에 그 정답 자체가 틀렸다는 게 밝혀져도(실제로 여러 번 그랬다) 수정이 빠르다.
⑦ Details
발견하지 못했다면 몰랐을 세부 구조
  • EXPERT 페르소나 세션(expert-chat.html)은 부모 창과 postMessage로 통신하지 않고, 단순 URL 이동(location.href = RETURN)으로만 돌아간다 — 생각보다 단순한 구조.
  • gwp-registry.js는 ES 모듈이 아니라 고전적 <script> 전역 로드 방식(window.GWP_REGISTRY)이라, <script type="module">인 expert-chat.html에서 직접 import가 안 된다.
  • prompts/AC-PRO-CORE_v1_1.txt 하나가 5개의 서로 다른 CI 워크플로를 동시에 감시하고 있다(정적 정합성 검사 4개 + 행동적 정확도 게이트 1개, 2026-08-06 신설) — 이 파일을 자주 고치는 작업 패턴 자체가 GitHub Actions 러너 자원을 상당히 쓴다.
  • 라우팅의 "행동적 정확도"(실제로 맞게 라우팅하는가)를 검증하는 자동 게이트가 이번 세션 이전엔 전혀 없었다 — 구조적 정합성(표 동기화, 참조 유효성)은 이미 push마다 자동 검사되고 있었는데, 그 사이에 검증 수준의 공백이 있었다.
⑧ Meta Observation
이 조직의 반복되는 패턴

오늘 새로 발견한 게 아니라, 오늘의 사건들이 재확인해준 이 코드베이스의 오래된 습성이다.

  • 문서·코드 어긋남이 반복된다. 7월 12일 작성된 라우팅 분류 문서가 8월 5일에야 뒤늦게 git에 커밋되면서 내용은 그대로 낡아 있었던 것, civil(K-Civil)이 폐기됐는데 §CATALOG-EXPERT 표엔 아직 남아있는 것 — 같은 유형의 드리프트다.
  • "있는데 못 찾는" 실패가 "아예 없는" 실패보다 흔하다. kbusiness의 "부가세 신고" trigger가 정확히 등록돼 있는데도 매번 ktax로 흡수되는 것, kestate/ktelecom의 라우팅 판단은 맞는데 태그 문법만 틀리는 것 — 전부 존재하는 기능을 못 찾거나 못 지키는 유형이지, 기능 자체가 없는 유형이 아니다.
  • 이 조직은 문제를 발견하면 날짜가 박힌 주석으로 프롬프트 안에 경위를 남기는 관례가 있다 — 좋은 습관이지만, 그 주석이 계속 쌓이기만 하고 실제 지침 문장은 여전히 틀린 채로 남는 경우가 있다(예: 이번 감정평가 사고에서 이미 한 번 "재정정" 주석을 달고도 같은 사고를 또 냄).
