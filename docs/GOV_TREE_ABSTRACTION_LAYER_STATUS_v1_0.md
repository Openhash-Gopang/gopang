# GOV_TREE_ABSTRACTION_LAYER_STATUS_v1_0.md
## gov-tree 추상화(템플릿) 계층 현황 — 전국 확대 전 필독

작성일: 2026-08-04 | 작성자: 주피터 지시, Claude 작성

## 0. 이 문서의 목적

"부산·서울·광주 등이 제주 모형의 인스턴스로 구현되려면, 먼저 추상적 자치단체·
기관·부서가 작성돼 있어야 한다"는 지시에 따라 2026-08-04 세션에서 gov-tree
전 계층을 **전수 검증**한 결과를 기록한다. 검증 과정에서 같은 세션 안에서도
여러 차례 잘못된 결론을 냈다가 정정한 이력이 있으므로, **다음 세션은 이 문서의
최종 결론(§2)만 신뢰하고, 과거 세션 로그에 있는 "~건 완료/미완료" 같은
중간 판단은 재검증 없이 인용하지 말 것.**

## 1. 검증 중 반복됐던 실수 — 같은 실수를 반복하지 않기 위한 기록

이번 세션에서 do-agency/org 템플릿 커버리지를 **세 번** 잘못 판단했다:

1. 브랜치 실수로 `main`에서 분기해 작업하다가, `local-batch1` 브랜치에만
   있던 도메인 템플릿(SP-AGY-LIBRARY-TEMPLATE 등) 자체가 안 보이는 상태에서
   "템플릿이 거의 없다"고 오판.
2. do-agency/org 인스턴스가 템플릿을 참조하는지 확인할 때 `"클래스 템플릿"`
   문자열로만 검색해서, do-dept 계층이 실제로는 **`"클래스 상속"`이라는
   다른 표현**을 쓴다는 걸 놓치고 "do-dept 0/22 참조"라고 오판(실제로는
   14/22 이미 완료돼 있었음).
3. `PROVINCE_TABLES.busan`의 `file: null` 스텁만 보고 "부산 do-dept 콘텐츠
   전무"라고 오판 — 실제 렌더링 경로는 `do-dept-master-data.json`이었고
   부산은 이미 16개 레코드가 있었다.

**교훈**: gov-tree는 "인스턴스 파일에 직접 콘텐츠를 쓰는 방식"과
"템플릿+마스터데이터 JSON으로 데이터만 채우는 방식" **두 가지가 계층마다
다르게 섞여 있다.** 커버리지를 판단할 때는 반드시 (a) 해당 계층의 실제
렌더링 함수(`gov-router.js`)를 먼저 확인하고, (b) 그 계층이 실제로 쓰는
참조 문구·필드명을 정확히 확인한 뒤 검색해야 한다. "템플릿 디렉터리에
파일이 몇 개 있는가"만으로 판단하면 틀린다.

### 요약

- **제주 267개 기관·부서 중, 추상 템플릿이 필요한 계층(do-dept·do-agency·org)은
  전부(22+10+26=58건) 이미 클래스 템플릿으로 추상화 완료**되어 있다.
- 01-do·04-city·05-emd는애초에 인스턴스 파일 방식이 아니라 데이터(JSON)
  기반이라 "추상화"라는 개념 자체가 다르게 적용된다 — 이미 도별 데이터를
  추가하는 구조로 설계돼 있다.
- **진짜 남은 공백은 "추상화가 안 된 것"이 아니라 "타 도의 실제 데이터가
  없는 것"**이다: 04-city-dept(부산 jachi 16/16 완료, 그 외 도메인은
  해운대구 등 일부만), 05-emd(제주 외 0건 — 스키마·라우팅 코드는
  2026-08-05 기준 전국 일반화 완료), division 레벨 전체(전 도 0건).

**추상 클래스 정교화(2026-08-04 완료)**: `SP-EMD-TEMPLATE`을 v1.3으로 전면 개정 — 제주 행정시(제주시/서귀포시) 이원구조 하드코딩을 제거하고 `{상위기관구분}` enum(행정시\|자치구\|자치군\|일반시\|일반군)으로 일반화. `gov-router.js`의 렌더링 함수(`_renderEmdTemplate`)·파일 참조까지 함께 갱신, 기존 제주 43개 레코드도 신규 스키마로 소급 반영 완료. `SP-CITY-TEMPLATE`·`SP-CITYDEPT-*-TEMPLATE`(16개)·division 템플릿(2개)은 점검 결과 이미 전국 공통으로 잘 설계돼 있어 추가 수정 불필요.

**추상 라우팅 코드 일반화(2026-08-05 완료)**: 위 v1.3 템플릿·스키마 작업 당시에도 `gov-router.js`의 directCode 해석부('emd'/'team' tier)와 `_findCityByName(emdEntry.행정시명)` 호출부에는 `_currentResolvedProvinceCode = 'jeju'` 하드코딩이 그대로 남아있었다(당시엔 "스키마에 도코드가 없어서 못 고친다"고 판단했으나, 실제로는 스키마는 이미 소급 반영돼 있었고 라우팅 코드만 안 고쳐진 상태였음 — §1의 "중간 판단 재검증 없이 인용 금지" 교훈이 그대로 재현된 사례). l2/city/agency/org가 쓰는 `_findEntryAcrossProvinces` 패턴의 EMD 전용 버전(`_findEmdEntryAcrossProvinces`, 비동기 로더 기반)을 신설해 도 하드코딩을 제거했고, `_matchEmd`·`_loadEmdNameToProvinceIndex`도 구 필드(`관할리목록`)뿐 아니라 신규 필드(`관할구역목록`)를 우선 인식하도록 폴백을 추가했다. **이제 부산 등 신규 도의 EMD 레코드를 실사해 `EMD_PATHS`에 키만 추가하면, 코드를 다시 고치지 않아도 directCode·자연어 매칭 양쪽 모두 정상 작동한다** — 다음 세션의 "읍면동 인스턴스" 작업은 이제 순수하게 데이터 실사·입력 작업만 남았다.
