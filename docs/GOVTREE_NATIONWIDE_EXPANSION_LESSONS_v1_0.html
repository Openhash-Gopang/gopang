①
추상 클래스의 목적과 구현 상태

왜 추상 클래스가 필요한가

혼디의 전국 확장 원칙은 "제주 모형 완결 → 추상 템플릿 도출 → 각 지역 구체 인스턴스 생성" 3단계다. 제주 267개 기관·부서 SP를 도마다 새로 쓰면 17개 광역단체 × 267건에 가까운 중복 작업이 되므로, 도 공통 부분(근거 법령·업무 절차·응답 스키마)을 템플릿으로, 도별로 다른 부분(기관명·연락처·조직 구성)을 데이터로 분리한다.

두 가지 서로 다른 구현 방식이 공존한다

이번 세션 최대 교훈이다. gov-tree는 계층마다 완전히 다른 두 메커니즘을 쓴다.

방식적용 계층동작
A. 인스턴스 파일 + 클래스 역참조02-do-dept, 03-do-agency, 07-org도별로 실제 .md 파일이 존재하고, §LEGAL-BASIS에 클래스 템플릿 상속 참조 문구가 박혀 있다.
B. 템플릿 + 마스터데이터 JSON01-do, 04-city, 04-city-dept, 05-emd.md 템플릿 하나만 있고 실제 값은 JSON 레코드로 존재한다. gov-router.js가 요청마다 렌더링한다.

함정: A방식 계층에서 클래스 참조 여부를 확인하려면 정확한 참조 문구를 검색해야 하는데, 계층마다 그 문구 자체가 다르다. do-agency·org는 "클래스 템플릿", do-dept는 "클래스 상속" 이라는 다른 문구를 쓴다. 이번 세션에서 "클래스 템플릿"으로만 검색해 "do-dept는 0/22 참조"라고 잘못 결론 냈다가, 정확한 문구로 재검색하니 22개 중 14개가 이미 완료돼 있었다. 세 번째 오판은 B방식(라우팅 테이블의 file: null만 보고 "콘텐츠 전무"라 단정)에서 나왔다 — 실제 렌더링 경로인 do-dept-master-data.json엔 부산 16개 레코드가 이미 실사 완료돼 있었다.

일반화된 교훈: 템플릿 디렉터리 파일 개수나 특정 문자열 포함 여부만으로 커버리지를 판단하지 마라. 반드시 (a) 실제 렌더링 함수(gov-router.js)를 먼저 확인하고, (b) 그 계층이 실제로 쓰는 참조 문구·필드명을 정확히 확인한 뒤 검색해야 한다. 이건 SESSION_LESSONS_VECTORIZE_GOVTREE §④("SP 파일과 코드는 다를 수 있다")의 재발이다 — 교훈을 알고도 같은 유형의 실수를 반복했다.

SP-EMD-TEMPLATE — 유일하게 실제로 고쳐야 했던 추상 클래스

B방식 템플릿 중 SP-EMD-TEMPLATE(읍면동)만 제주에 구조적으로 결합돼 있었다. 제주는 "행정시"(법인격 없음·임명제 시장) 특수 구조라 {행정시명}을 enum(제주시|서귀포시)로 고정해뒀는데, 부산의 자치구·자치군은 법인격 있는 민선 기초자치단체라 이 enum이 안 맞았다.

v1.3 개정 핵심:

  • {행정시명} enum → {상위기관명}(자유 텍스트) + {상위기관구분} enum(행정시|자치구|자치군|일반시|일반군)으로 분리
  • 상수도 소관 하드코딩 → {상수도소관기관} 단일 변수
  • "제주콜센터 064-120" 고정 텍스트 → {통합콜센터명}/{통합콜센터번호} 변수
  • 문서만 고치고 코드는 안 고치는 실수 방지: gov-router.js의 _renderEmdTemplate()과 파일명 참조 3곳까지 함께 갱신, 기존 제주 42개 레코드도 즉시 소급 반영

반면 SP-CITY-TEMPLATE(이미 유형1/유형2 분기 내장), SP-CITYDEPT-*-TEMPLATE(16개), division 템플릿은 점검 결과 수정 불필요였다 — 모든 템플릿이 문제였던 게 아니라 "제주가 유일한 사례였을 때 작성된" 템플릿 하나만 문제였다.

04-city 실사 중 발견한 실제 계층 위계 차이

제주(도청→행정시[비자치]→읍면동)와 부산(광역시청→자치구/군[자치]→동)은 중간 계층의 자치권 유무가 다르다. 자치구는 자체 조례·예산으로 자기만의 조직 편제를 가질 수 있다 — 실제로 해운대구는 같은 "경제" 기능도 도청 단위와 달리 "문화관광경제국" 하나로 통합돼 있었다. 즉 16개 구·군이 전부 다른 조직 구조를 가질 수 있어 "표준 구청 조직도"를 가정하면 안 된다. 또한 CATALOG_ONLY의 안내 문구가 "제주 지역 사무소"로 하드코딩된 실제 결함도 발견했다.

하이브리드 검색/라우팅 — 세 갈래 경로와 각자의 관할

이 절의 결론은 초안 작성 이후 저장소 갱신(jejuro, 커밋 287bfcb)으로 한 번 크게 정정됐다. 처음엔 "K-Search가 LIKE 기반이라 자연어에 취약하니 의미검색으로 보완해야 한다"는 2갈래 구도로 판단했는데, 실제로는 gov-tree 전용 SP가 있는 기관은 애초에 K-Search 관할이 아니라는 제3의 경로가 이미 있었다.

SP-18 RULE-07 [7-D] — 근거 문서를 먼저 읽었어야 했다

prompts/SP-18_ksearch_v1.4.txt에 이미 명시돼 있었다:

대상이 정부기관·부서면서 이미 해당 부서를 다루는 전용 SP가 있으면, K-Search가 별도로 그 조직의 프로필을 다시 만들지 않는다 — "해당 기관은 이미 전용 창구가 있다"고 안내하고 [KSEARCH_HANDOFF_BACK: reason=institution-govtask]로 되돌린다.

실제로 밟았던 함정: 부산 파일럿(부산교통공사) 세션에서, 이미 전용 SP(SP-ORG-BUSANTRANSIT)가 있는 기관을 "K-Search가 찾을 수 있는지" 검증한다며 PocketBase에 별도 프로필을 등록하고 색인 검증까지 시도했다. 전부 불필요했다 — 경로 A (_resolveInstitutionMatch)가 BUSAN_ORG_TABLE의 kw 배열만으로 이미 정상 작동했다. "부산교통공사 민원은 어디로 문의하나요"는 물론, 별칭 "휴메트로 분실물센터 전화번호 알려줘"까지 매칭됐다 — directCode조차 없이, 순수 발화 텍스트만으로.

일반화된 교훈: 코드를 추적해서 아키텍처를 짐작하기 전에, 그 시스템의 1차 정의 문서(SP 자신의 System Prompt 본문)를 먼저 읽어라. gov-tree처럼 "이미 자기 완결적인 라우팅 체계를 가진 도메인"에 "모든 개체는 DB에 등록하고 검색으로 찾는다"는 대원칙을 습관적으로 적용하지 마라 — RULE-07 [7-D]가 명시적 예외다.

원래 논의(LIKE vs 의미검색)는 어디에 적용되는가 — 정정된 범위

"K-Search가 자연어에 취약하다"는 관찰 자체는 사실이지만, 적용 범위가 좁아졌다 — 경로 B/C(K-Search·의미검색)의 관할, 즉 gov-tree 전용 SP가 없는 기관·조직에만 유효하다.

29건 파일럿의 재해석: LIKE가 0%였다는 실측 자체는 유효하지만, 그 대상(도청 실·국)이 애초에 gov-tree 전용 SP가 있는 기관이었다는 점에서 "K-Search 취약점"이 아니라 "K-Search가 애초에 관여하지 말았어야 할 대상에 관여시켜본 결과"에 가깝다. 진짜 검증했어야 할 것은 경로 A가 자연어에 통하는가였고, 이건 부산 파일럿에서 별도로 검증돼 통과했다.

정리: 경로 A는 진짜 자연어 이해가 아니라 "기관별로 큐레이션된 별칭 목록과의 문자열 대조"다 — kw 목록에 없는 표현이면 여전히 실패한다. 경로 B/C 영역에서는 원래 논의(LIKE 0% 취약점, 의미검색 전환 필요성, SP-18 프로토콜 재설계 부담)가 그대로 유효하다.

남은 실전 함의

  • gov-tree 신규 기관 추가 시 PocketBase 등록·K-Search 색인은 필요 없다 — kw 배열에 실제 별칭까지 등록하고, 발화 텍스트 매칭 테스트(네트워크 불필요)로 검증하면 끝이다.
  • K-Search/의미검색 하이브리드 설계(정확매칭·자연어탐색·구조화후처리 3분기, RULE-01 점수 기반 재정의 등)는 gov-tree 밖의 대상에 한해서만 진행한다 — gov-tree 기관까지 끌어들이면 안 된다.

[2026-08-04 추가 검증·수정] 경로 A의 완전 매칭 실패 구제 경로 신설

위 함의까지는 "kw 배열만 잘 큐레이션하면 된다"고 정리했는데, 실측으로 확인하니 부족했다. "지하철 타다가 물건 놓고 내렸는데 어디다 물어봐요"(kw 리터럴 불포함 패러프레이즈)로 코드를 추적한 결과: _resolveInstitutionMatch는 topScore === 0이면 즉시 null을 반환했고, 함수 내부 LLM 폴백은 "동점 후보 중 고르기" 전용이라 완전 매칭 실패는 구제하지 않았다. do-dept용 별도 LLM 폴백도 후보 목록에 SP-ORG-*/SP-AGY-* 코드가 아예 없어 무력했다. 즉 org/agency 계층 전체가 kw 목록에 없는 표현이면 완전히 새는 사각지대였다.

수정: topScore === 0 분기에서 즉시 포기하는 대신, table 전체(이미 desc 필드 보유)를 후보로 _classifyDivisionFallback을 재사용해 한 번 더 시도하도록 고쳤다 — 새 헬퍼 없이 기존 함수 재사용으로 해결됐다. 검증: 목(mock) classifyFn 주입 케이스와 미주입 대조군 케이스를 테스트에 추가해 10/10 통과 확인.

일반화된 교훈: 실측 결과가 "우려가 맞았다"로 나오면 새 방비책을 미루지 말고 바로 만들어야 한다 — 다만 새 코드를 늘리기 전에, 이미 있는 폴백 메커니즘이 재사용 가능한지부터 확인하는 습관이 여기서도 유효했다.

추상화 커버리지를 판단할 때

  • 이 계층이 A방식(인스턴스+역참조)인지 B방식(템플릿+데이터)인지 먼저 gov-router.js에서 확인했는가
  • A방식이면, 정확한 참조 문구를 확인하고 검색했는가("클래스 템플릿" ≠ "클래스 상속")
  • B방식이면, file: null 같은 스텁만 보고 "콘텐츠 없음"이라 단정하지 않고 실제 마스터데이터 JSON까지 확인했는가

검색/라우팅 코드를 만지거나 판단할 때

  • 매칭 순서가 이상해 보이면 하위 함수가 도 코드에 의존하는지부터 확인했는가 — "버그" 단정 전에 설계 의도 추적
  • 임베딩 검색을 새로 붙일 때 메타데이터 인덱스·guid 조회·description 기본 공개 여부를 재확인했는가
  • LIKE와 임베딩을 섞을 때, 벡터 topK를 먼저 뽑고 그 안에서만 후처리하는 순서를 지켰는가

타 도 확장 시

  • 그 도의 기초자치단체가 자치권이 있는지(자치구/자치군) 없는지(행정시) 먼저 확인했는가
  • 하드코딩된 지역명·전화번호가 남아있지 않은지 grep으로 전수 확인했는가
