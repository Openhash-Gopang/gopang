## 1. 추상 클래스의 목적과 구현 상태

### 1-1. 왜 추상 클래스가 필요한가

혼디의 전국 확장 원칙은 **"제주 모형 완결 → 추상 템플릿 도출 → 각 지역 구체
인스턴스 생성"** 3단계다. 제주 267개 기관·부서 SP를 도마다 새로 쓰면 17개
광역단체 × 267건에 가까운 중복 작업이 되므로, "이 기관이 어느 도에 있든 공통인
부분"(근거 법령, 업무 절차, 응답 스키마)과 "도마다 다른 부분"(기관명·연락처·
조직 구성)을 분리해 전자를 템플릿(클래스)으로, 후자를 데이터로 관리한다.

### 1-2. 두 가지 서로 다른 구현 방식이 공존한다 — 이걸 모르면 커버리지를 오판한다

이번 세션 최대 교훈이다. gov-tree는 계층마다 **완전히 다른 두 메커니즘**을 쓴다.

| 방식 | 적용 계층 | 동작 |
|---|---|---|
| **A. 인스턴스 파일 + 클래스 역참조** | 02-do-dept, 03-do-agency, 07-org | 도별로 실제 `.md` 파일이 존재하고, 그 안의 `§LEGAL-BASIS`에 "이 클래스 템플릿을 상속한다"는 참조 문구가 박혀 있다. |
| **B. 템플릿 + 마스터데이터 JSON (인스턴스 파일 없음)** | 01-do, 04-city, 04-city-dept, 05-emd | `.md` 템플릿 **하나**만 있고, 실제 도별 값은 JSON 배열의 레코드로만 존재한다. `gov-router.js`가 요청마다 템플릿에 데이터를 꽂아 렌더링한다 — 도가 100개로 늘어도 새 `.md` 파일이 생기지 않는다. |

**함정**: A방식 계층에서 "이 인스턴스가 클래스를 상속하는가"를 확인하려면 실제로
박혀 있는 참조 문구를 정확히 검색해야 하는데, **계층마다 그 문구 자체가 다르다.**

- do-agency·org: `"클래스 템플릿"` 이라는 문구 사용
- do-dept: `"클래스 상속"` 이라는 **다른** 문구 사용

이번 세션에서 `"클래스 템플릿"`으로만 검색해 "do-dept는 0/22 참조 — 전부
미완결"이라고 **잘못** 결론 내렸다. 실제로 정확한 문구(`"클래스 상속"`)로
재검색하니 22개 중 **14개가 이미 완료**돼 있었다. 세 번째 오판은 B방식
계층(do-dept의 도별 데이터)에서 나왔다 — `PROVINCE_TABLES.busan`의 라우팅
테이블 항목이 `file: null`인 것만 보고 "부산 콘텐츠 전무"라고 판단했는데, 실제
렌더링 경로는 `do-dept-master-data.json`이었고 거기엔 부산 16개 레코드가 이미
실사 완료돼 있었다.

> **일반화된 교훈**: "템플릿 디렉터리에 파일이 몇 개 있는가", "인스턴스가 특정
> 문자열을 포함하는가"만으로 커버리지를 판단하지 마라. 반드시 (a) 그 계층의
> 실제 렌더링 함수(`gov-router.js`)를 먼저 열어서 데이터가 어디서 오는지
> 확인하고, (b) 그 계층이 실제로 쓰는 참조 문구·필드명을 정확히 확인한 뒤
> 검색해야 한다. 이건 `SESSION_LESSONS_VECTORIZE_GOVTREE_v1_0.md` §④("SP 파일에
> 적힌 것과 코드가 실제로 하는 것은 다를 수 있다")의 재발이다 — 교훈을 알고도
> 같은 유형의 실수를 반복했다는 뜻이므로, 다음 세션은 **작업 시작 전에 반드시
> 렌더링 코드부터 읽을 것**.

`33b5f15`)도 이 사이 수정됐다 — 전국 확대를 실제로 막고 있던 코드 버그였다.

### 1-4. SP-EMD-TEMPLATE — 유일하게 실제로 고쳐야 했던 추상 클래스

B방식 템플릿 중 `SP-EMD-TEMPLATE`(읍면동)만 실제로 제주에 구조적으로
결합돼 있었다. 원인: 제주는 "행정시"(제주시·서귀포시, 법인격 없음·도지사
임명 시장)라는 특수 구조라 `{행정시명}` 변수를 `enum(제주시|서귀포시)`로
고정해뒀는데, 부산의 자치구·자치군은 법인격 있는 민선 기초자치단체라 이
enum 자체가 안 맞았다.

**v1.3 개정 핵심**:
- `{행정시명}` enum(제주시\|서귀포시) → `{상위기관명}`(자유 텍스트) +
  `{상위기관구분}` enum(행정시\|자치구\|자치군\|일반시\|일반군)으로 분리
- 상수도 소관(제주만 시별로 분기하던 하드코딩) → `{상수도소관기관}` 단일 변수
- "제주콜센터 064-120" 고정 텍스트 → `{통합콜센터명}`/`{통합콜센터번호}` 변수
- **문서만 고치고 코드는 안 고치는 실수 방지**: `gov-router.js`의
  `_renderEmdTemplate()`과 템플릿 파일명 참조 3곳(v1.2→v1.3)까지 함께 갱신.
  구 필드(`행정시명`·`관할리목록`)도 폴백으로 남겨 하위호환 유지.
- 기존 제주 42개 레코드도 새 스키마로 즉시 소급 반영(안 하면 새 템플릿이
  제주에도 못 쓰이는 회귀가 생긴다).

반면 `SP-CITY-TEMPLATE`(이미 유형1 자치구/유형2 행정시 분기 내장),
`SP-CITYDEPT-*-TEMPLATE`(16개), division 템플릿(2개)은 점검 결과 이미 전국
공통으로 설계돼 있어 **수정 불필요**였다 — 모든 템플릿이 문제였던 게 아니라,
"제주가 유일한 사례였을 때 작성된" 템플릿 하나만 문제였다는 뜻이다.

### 1-5. 04-city/04-city-dept 실사 중 발견한 실제 계층 위계 차이

제주(도청→행정시[비자치]→읍면동)와 부산(광역시청→자치구/군[자치]→동)은
**중간 계층의 자치권 유무가 다르다**. 이게 실무에 주는 영향:

- 자치구는 자체 조례·예산으로 **자기만의 조직 편제**를 가질 수 있다 — 실제로
  해운대구 실사 결과, 같은 "경제" 기능도 도청 단위(부산시)는 econ/tourism이
  분리돼 있는데 구청 단위(해운대구)는 "문화관광경제국" 하나로 통합돼 있었다.
  즉 **16개 구·군이 전부 다른 조직 구조를 가질 수 있다** — 하나의 "표준
  구청 조직도"를 가정하면 안 된다.
- `CATALOG_ONLY`(아직 미완결 중앙기관 폴백)의 안내 문구가 "제주 지역
  사무소"로 하드코딩돼 있는 걸 발견 — 타 지역 확장 시 반드시 도별
  파라미터화가 필요한 실제 결함으로 별도 기록해뒀다.

## 2. 하이브리드 검색/라우팅 — 세 갈래 경로와 각자의 관할

**이 절의 결론은 초안 작성 이후 저장소 갱신(jejuro, 2026-08-04 20시경 커밋
`287bfcb`)으로 한 번 크게 정정됐다.** 처음엔 "K-Search가 LIKE 기반이라
자연어에 취약하니 의미검색으로 보완해야 한다"는 2갈래 구도로 썼는데, 실제로는
**gov-tree 전용 SP가 있는 기관은 애초에 K-Search 관할이 아니라는 제3의 경로가
이미 있었다.** 이 절은 그 정정 경위 그대로 서술한다 — 처음 판단이 왜 틀렸는지도
교훈이기 때문이다.

### 2-1. 세 갈래 경로

| 경로 | 대상 | 매칭 방식 | 비고 |
|---|---|---|---|
| **A. gov-router.js 정적 키워드 테이블** | gov-tree 전용 SP가 이미 있는 기관(도청·시청·직속기관·출자출연기관 인스턴스) | 기관별로 큐레이션된 `kw`(키워드·별칭) 배열과 발화 텍스트를 대조(`_resolveInstitutionMatch`) | **K-Search/PocketBase 전혀 관여 안 함** — SP-18 RULE-07 [7-D]가 명시적으로 규정한 경계 |
| **B. K-Search LIKE(`_l1SearchEntities`)** | gov-tree 전용 SP가 **없는** 기관·조직, 사람, 일반 사업체 | PocketBase `~` 연산자 부분 문자열 일치 | 구조화된 필드 + 수동 동의어표 필요 |
| **C. entity-semantic-search(임베딩)** | B와 동일 대상(대체재) | bge-m3 임베딩 + Vectorize 유사도 | 배포됐지만 `call-ai.js`엔 아직 미연결 |

### 2-2. SP-18 RULE-07 [7-D] — 근거 문서를 먼저 읽었어야 했다

`prompts/SP-18_ksearch_v1.4.txt`에 이미 명시돼 있었다:

> 대상이 정부기관·부서(조직 단위)면서 **이미 해당 부서를 다루는 전용 SP가
> 있으면**(제주 행정처럼 SP-DO-*/SP-EMD-* 계층이 이미 자체 데이터를 연동
> 중인 경우), K-Search가 별도로 그 조직의 프로필을 다시 만들지 않는다 —
> "해당 기관은 이미 전용 창구가 있다"고 안내하고
> `[KSEARCH_HANDOFF_BACK: reason=institution-govtask]`로 되돌린다.

즉 gov-tree에 이미 인스턴스화된 기관은 PocketBase profiles/K-Search의 관할이
**아니다.** 이건 버그가 아니라 SP-18이 명시적으로 규정한 경계다. K-Search는
"전용 SP가 없는" 기관·조직에 한해서만 개입하며, 그 경우에도
`status=external_info_only`만 반환하고 **정식 profile로 등록하지 않는다.**

**실제로 밟았던 함정**: 2026-08-04 부산 파일럿(부산교통공사) 세션에서,
`SP-ORG-BUSANTRANSIT`(전용 gov-tree SP가 이미 있음)를 "K-Search가 찾을 수
있는지" 검증한다며 PocketBase에 별도 프로필을 등록하고, `entity-semantic-search`·
`POST /search` 양쪽으로 색인 여부까지 검증하려 했던 시도가 있었다. 전부
불필요했다 — `gov-router.js`의 A경로(`_resolveInstitutionMatch(text,
_orgTable(), ...)`)가 `BUSAN_ORG_TABLE`의 `kw` 배열만으로 이미 정상
작동하고 있었다. "부산교통공사 민원은 어디로 문의하나요"는 물론, 별칭
"휴메트로 분실물센터 전화번호 알려줘"까지 `kw: ['부산교통공사', ...,
'휴메트로', ...]`로 매칭됐다 — **directCode(K-Search가 프로필을 이미 확정한
경우의 지름길)조차 없이, 순수 발화 텍스트만으로.**

> **일반화된 교훈**: 코드를 추적해서 아키텍처를 짐작하기 전에, 그 시스템의
> 1차 정의 문서(이 경우 SP 자신의 System Prompt 본문, `SP-18_ksearch_v1.4.txt`)를
> 먼저 읽어라. `gov-router.js`만 읽고 판단했다면 애초에 K-Search 검증
> 자체를 시도하지 않았을 것이다. gov-tree처럼 "이미 자기 완결적인 라우팅
> 체계를 가진 도메인"에 "모든 개체는 DB에 등록하고 검색으로 찾는다"는
> 대원칙을 습관적으로 적용하지 마라 — RULE-07 [7-D]가 명시적 예외다.

### 2-3. 그럼 §2 원래 논의(LIKE vs 의미검색)는 어디에 적용되는가 — 정정된 범위

**"K-Search가 자연어에 취약하다"는 관찰 자체는 사실이지만, 적용 범위가
좁아졌다.** 이 논의는 **경로 B/C(K-Search·의미검색)의 관할**, 즉 **gov-tree
전용 SP가 없는 기관·조직에만** 유효하다 — 도청·시청·직속기관·출자출연기관처럼
이미 gov-tree화된 기관에는 애초에 해당 사항이 없다.

**29건 파일럿(§③)의 재해석**: `jeju_29_genuine_task_queries.json`으로
LIKE가 0%였다는 실측 자체는 유효하지만, 그 대상(도청 실·국)이 애초에
gov-tree 전용 SP가 있는 기관이었다는 점에서 "K-Search 취약점"이 아니라
"K-Search가 애초에 관여하지 말았어야 할 대상에 관여시켜본 결과"에 가깝다.
**진짜 검증했어야 할 것은 경로 A(정적 키워드 매칭)가 자연어에 통하는가**였고,
이건 부산 파일럿에서 별도로 검증돼 **통과했다**(§2-2의 부산교통공사 사례,
`directCode-province-resolution.test.mjs` 케이스 7·8).

정리하면:

- **경로 A(정적 키워드 매칭)**: 진짜 자연어 이해가 아니라 "기관별로 큐레이션된
  별칭 목록과의 문자열 대조"다 — LIKE와 근본 메커니즘은 같지만, 사전에 "휴메트로"
  같은 실제 별칭을 사람이 등록해두면 그 표현으로는 성공한다. **kw 목록에 없는
  표현이면 여전히 실패한다** — 완전한 자연어 이해는 아니다.
- **경로 B/C(K-Search)**: gov-tree 밖의 일반 개체(사람·식당·미등재 기관)
  대상이며, 이 영역에서는 §2-1의 원래 논의(LIKE 0% 취약점, 의미검색으로의
  전환 필요성, SP-18 프로토콜 재설계 부담)가 그대로 유효하다.

### 2-4. 남은 실전 함의

- gov-tree 신규 기관을 추가할 때, PocketBase 등록·K-Search 색인은 **필요
  없다.** 검증 순서는 (1) `kw` 배열에 실제 사용자가 쓸 법한 별칭까지
  등록했는지 (2) 발화 텍스트 매칭 테스트(`node src/tests/*.test.mjs`,
  네트워크 불필요)로 확인 — 이걸로 끝이다.
- 반대로 K-Search/의미검색 하이브리드 설계(§2-1 원래 제안: 3-A 정확매칭·
  3-B 자연어탐색·3-C 구조화후처리, RULE-01 점수 기반 재정의 등)는 **gov-tree
  밖의 대상에 한해서만** 진행하면 된다 — gov-tree 기관까지 이 설계에 끌어들이면
  안 된다.

## 3. 다음에 비슷한 작업을 할 때 — 체크리스트

**추상화 커버리지를 판단할 때**
- [ ] 이 계층이 A방식(인스턴스+역참조)인지 B방식(템플릿+데이터)인지 먼저
      `gov-router.js`에서 실제 렌더링 함수를 찾아 확인했는가
- [ ] A방식이면, 이 계층이 실제로 쓰는 참조 문구를 정확한 텍스트로 확인하고
      검색했는가("클래스 템플릿" ≠ "클래스 상속")
- [ ] B방식이면, 라우팅 테이블의 `file: null` 같은 스텁만 보고 "콘텐츠
      없음"이라 단정하지 않고 실제 마스터데이터 JSON까지 확인했는가

**검색/라우팅 코드를 만지거나 판단할 때**
- [ ] 매칭 순서가 이상해 보이면, 그 분기가 참조하는 하위 함수(예:
      `_nationalTable()`)가 도 코드에 의존하는지부터 확인했는가 — "버그"로
      단정하기 전에 설계 의도를 끝까지 추적
- [ ] 임베딩 검색을 새로 붙일 때 메타데이터 인덱스·guid 조회 방식·
      description 기본 공개 여부를 재확인했는가(§2-3 함정 3가지)
- [ ] LIKE와 임베딩을 섞을 때, 벡터 topK를 먼저 뽑고 그 안에서만 후처리
      (거리·정렬)하는 순서를 지켰는가

**gov-tree 신규 기관을 추가·검증할 때**
- [ ] 그 기관이 이미 gov-tree 전용 SP를 갖는지부터 확인했는가 — 그렇다면
      PocketBase 등록·K-Search 색인은 **하지 않는다**(SP-18 RULE-07 [7-D],
      §2-2 참조)
- [ ] `kw` 배열에 사용자가 실제로 쓸 법한 별칭까지 등록했는가(예:
      "부산교통공사" 외에 "휴메트로"도 등록)
- [ ] 검증은 발화 텍스트 매칭 테스트(`node src/tests/*.test.mjs`, 네트워크
      불필요)로 충분한가 — PocketBase profile 등록·API 호출 검증을
      "당연한 단계"로 가정하지 않았는가
- [ ] 아키텍처를 코드 추적만으로 짐작하기 전에, 그 시스템의 1차 정의
      문서(SP 자신의 System Prompt 본문, 여기선 SP-18)부터 읽었는가

**타 도 확장 시**
- [ ] 그 도의 기초자치단체가 자치권이 있는지(자치구/자치군) 없는지(행정시)
      먼저 확인했는가 — 조직 구조 다양성·§LEGAL-BASIS 근거법이 달라짐
- [ ] 하드코딩된 지역명·전화번호(콜센터 등)가 남아있지 않은지 grep으로
      전수 확인했는가
