Overview
이 문서가 왜 있는가

이 문서는 gov-tree 지연 인스턴스화 기능 자체의 사용법 매뉴얼이 아니다(그건 GOV_TREE_LAZY_INSTANCING_DESIGN_v1_0.md 가 다룬다). 새 PocketBase 컬렉션을 만들거나, 클라이언트↔워커 사이에 새 엔드포인트를 붙이거나, 로컬 검증 스크립트로 실서버에 데이터를 넣거나, Windows 환경에서 Node 스크립트를 돌릴 때 또 밟게 될 게 뻔한 함정들을 모아뒀다. 전부 오늘 세션에서 실제로 밟은 함정이고, 원인을 확인하는 데 각각 여러 번의 왕복(패치 전달→적용→진단→재수정)이 필요했다.

이 문서를 읽어야 하는 상황

01 · Convention
새 스키마를 만들기 전에 기존 관례부터 뒤져라
PocketBase 필드명을 한글로 설계했다가 재작업

새 PocketBase 컬렉션(sp_gov_tree_instance_realtime)의 필드명을 도코드·시코드·국코드· 읍면동명처럼 애플리케이션 코드(gov-router.js ↔worker.js 사이의 govTreeKey 객체)와 똑같이 한글로 설계했다. 코드 자체는 잘 동작했겠지만, pb_migrations/*.js 145개 파일을 전수 확인해보니 이 저장소의 다른 모든 PocketBase 컬렉션은 예외 없이 영어(ASCII) 필드명을 쓰고 있었다 — 관리자 UI에서 다른 컬렉션과 나란히 보일 때만 이상해 보이는 게 아니라, K-Search 엔티티 식별자 (entity_subtype)도 관례가 이미 "{tier}:{code}"(예: city-dept:jejusi-jachi, emd:애월읍) 형식으로 확립돼 있었는데 처음엔 이걸 놓치고 완전히 다른 형식(gov-tree-instance:{tier}:{instance_key}) 으로 설계했다 — 검색은 되지만 클릭 시 라우팅이 깨지는 상태였을 것이다.

일반화된 교훈
새 컬렉션·새 엔티티 식별자 형식을 설계하기 전에, 같은 목적을 이미 하고 있는 자매 컬렉션(named-institution용 sp_gov_draft_realtime, 기존 시딩 스크립트 seed_gov_tree_citydept_natagency.py/ seed_gov_tree_emd_team.py)이 있는지 먼저 찾아라. 설계 문서를 아무리 꼼꼼히 써도, 실제 저장소에 이미 있는 관례를 확인하지 않으면 "말이 되는 새 설계"를 만들어서 기존 것과 어긋나게 된다. 애플리케이션 레벨 키(한글)와 저장소 레벨 필드명 (영어)이 다를 수 있다는 것 자체는 문제가 아니다 — 그 경계에서 번역 계층 하나만 두면 된다(_govTreeKeyToPbFields()).
02 · Architecture principle
"라우팅이 된다"와 "이 개체가 혼디의 사용자로 존재한다"는 다르다
정적 키워드 매칭은 잘 됐지만 K-Search 등록이 통째로 빠져 있었음

부산 43개 동·jachi 16개 구·군은 정적 JSON 파일과 gov-router.js의 키워드 매칭만으로도 "우1동 등본 발급" 같은 발화에 정상적으로 응답했다. 그래서 라우팅이 되니까 이 작업이 끝났다고 판단하기 쉬웠다 — 하지만 "혼디의 모든 개체는 profiles에 등록된 독립적 사용자(SP)여야 한다"는 대원칙(§1)은 완전히 별개의 요구사항이었다. 감사해보니 기존 profiles 시딩은 제주에만 적용돼 있었고, 그 이후의 모든 부산 파일럿 산출물(이번 세션 포함)이 애초에 K-Search 대상이 아니었다.

일반화된 교훈
"발화 하나에 잘 응답한다"는 확인만으로 새 도메인/계층 작업이 끝났다고 판단하지 마라. gov-tree처럼 정적 라우팅과 동적 검색(K-Search/profiles)이 서로 다른 코드 경로인 시스템에서는, 라우팅 테스트를 통과해도 검색·등록 쪽이 통째로 빠져 있을 수 있다. 새 엔티티 계층을 만들 때는 "이 계층이 이미 profiles에 등록되는 기존 시딩 스크립트의 대상인가"를 먼저 확인해야 한다.
03 · Git workflow
git am이 "이미 있다"고 하면 진짜로 이미 있는지부터 확인
여러 차례 반복된 "patch does not apply" / "already exists in index"

이 세션은 Claude가 별도 샌드박스에서 패치를 만들어 전달하고, 사람이 git am으로 적용하는 방식으로 진행됐다. 이 과정에서 같은 패턴의 혼란이 여러 번 반복됐다 — git am 이 "patch failed"·"already exists in index" 를 동시에 내는 경우가 있었는데, 원인은 Claude의 샌드박스 커밋과 사용자가 이미 적용한 커밋이 내용은 완전히 같은데 커밋 해시만 다른 경우였다(같은 diff를 다른 시점에 커밋하면 해시가 달라진다). 실패를 보고 "다시 시도"만 반복하면 안 되고, git log origin/main --oneline과 git diff origin/main <로컬브랜치>로 내용 자체가 이미 일치하는지부터 확인해야 했다.

또 한 번은 git checkout -b가 "브랜치가 이미 있다"는 이유로 실패했는데 이걸 무시하고 넘어가서, 의도와 다르게 main 브랜치에서 git am을 시도하다 충돌이 났다. 이후 git push origin <그 브랜치명>을 실행하니 로컬에 이미 존재하던(내용을 알 수 없는) 그 브랜치가 그대로 푸시되어 새 PR이 생겼고, 확인해보니 실제로는 이전 시도에서 이미 성공적으로 병합된 내용과 똑같아서 그 PR은 그냥 중복이었다.

증상실제 원인확인 방법
am: patch does not apply
am: already exists in index		 내용은 이미 origin에 있음(해시만 다름) git diff origin/main <브랜치> -- <파일>로 diff 없음(빈 결과) 확인
checkout -b 실패 후 무시하고 진행 의도와 다른 브랜치(main)에서 작업 중 git status·git branch로 현재 브랜치 재확인 후 진행
새 PR을 만들었는데 "No commits between" 에러 그 브랜치가 이미 main과 내용이 동일(과거에 병합됨) git diff origin/main origin/<브랜치>가 빈 결과인지 확인 → 중복이면 그냥 close
일반화된 교훈
패치 적용이 이상하게 실패하면, "다시 만들어서 다시 보내기" 전에 먼저 origin과 diff 없음(=이미 반영됨)인지 확인하는 습관을 들여라. worker.js처럼 브랜치 보호가 걸린 파일은 직접 push가 막혀 있으므로(브랜치→PR→auto-merge 필요), 실패 메시지가 "권한 문제"인지 "내용이 이미 같아서"인지부터 구분해야 헛수고를 피할 수 있다.
04 · Platform gotcha
Windows 환경 특유의 함정 3가지
이 세션의 로컬 검증은 전부 리눅스 샌드박스에서만 했던 게 원인

1. 동적 import()에 Windows 절대경로를 그대로 넘기면 안 된다

path.join(SRC_ROOT, 'gov-router.js')의 결과가 Windows에서는 C:\Users\...\gov-router.js(드라이브 문자+역슬래시) 형태인데, 이 문자열을 import()에 직접 넘기면 Node의 ESM 로더가 c:를 알 수 없는 프로토콜 스킴으로 해석해 ERR_UNSUPPORTED_ESM_URL_SCHEME로 거부한다. 리눅스에서는 경로가 /로 시작해 우연히 문제가 안 됐을 뿐, 애초에 이식성 있는 코드가 아니었다.

// 틀림 — Windows에서 터짐 await import(path.join(SRC_ROOT, 'gov-router.js')); // 맞음 — file:// URL로 변환 import { pathToFileURL } from 'node:url'; await import(pathToFileURL(path.join(SRC_ROOT, 'gov-router.js')));

2. PowerShell Out-File -Encoding은 버전마다 지원값이 다르다

utf8NoBOM이 최신 PowerShell(7+)에는 있지만, 이 세션에서 쓴 PowerShell 버전의 ValidateSet에는 없어서(unicode,utf8,ascii 등만 허용) 파라미터 검증 단계에서 바로 실패했다. utf8 로 바꾸면 BOM이 붙지만 Node는 BOM 붙은 UTF-8 파일도 문제없이 읽는다 — 굳이 utf8NoBOM을 고집할 이유가 없었다.

3. Invoke-WebRequest는 한글을 깨뜨릴 수 있다 — 진단할 땐 네이티브 fetch를 써라

PowerShell의 ConvertTo-Json → Invoke-WebRequest 조합으로 API를 테스트했더니, 서버가 받은 페이로드의 한글 필드명· 값이 전부 ?로 깨져 있었다(콘솔·요청 인코딩이 UTF-8이 아니었던 것으로 추정). 이게 실제 버그와 뒤섞여서 원인 파악을 어렵게 했다 — 실제 운영 코드(Node 스크립트)가 쓰는 것과 똑같은 방식(네이티브 fetch)으로 진단 스크립트를 짜는 게, 다른 도구(PowerShell HTTP 클라이언트)로 진단해서 새로운 변수를 추가하는 것보다 훨씬 빠르고 정확했다.

일반화된 교훈
이 프로젝트의 개발·테스트는 리눅스 샌드박스에서, 실사용은 Windows PowerShell에서 이뤄진다. "내 환경에서 됐다"는 이식성을 보장하지 않는다 — 특히 파일 경로·인코딩 관련 코드는 Windows에서 최종 확인 전까지 완료로 치지 마라.
05 · Bug pattern (critical)
mock으로 덮어쓴 전역 함수를 "복원"한다고 착각한 코드가 실전송까지 삼켰다
--apply를 여러 번 실행해도 항상 "생성 0/스킵 0/실패 0" — 에러 없이 조용히 아무 일도 안 일어남

부트스트랩 시딩 스크립트는 assembleGovSystemPrompt()를 그대로 재사용해 로컬 JSON/템플릿 파일로부터 실제 렌더링 결과를 얻는다. 이를 위해 globalThis.fetch를 로컬 파일을 읽는 모의(mock) 함수로 덮어썼다(테스트 파일들과 동일한 패턴). 문제는, 그 뒤 실제 PocketBase로 데이터를 전송하는 단계(main()의 /gov-tree-instance/seed POST)에서도 같은 fetch 식별자를 그대로 호출했다는 것 — "원래 네이티브 fetch로 복원한다"는 코드(globalThis.fetch = fetch;)가 있었지만, 이 시점에는 fetch라는 식별자 자체가 이미 globalThis.fetch(=모의 함수)를 가리키고 있었다 — 즉 모의 함수를 자기 자신에게 재대입하는 무의미한 코드 였다. 원본 네이티브 fetch에 대한 참조를 애초에 별도 변수로 저장해두지 않았던 게 근본 원인.

// 틀림 — "복원"이 실제로는 아무 효과 없음 globalThis.fetch = async (url) => { /* 로컬 파일 읽기 mock */ }; // ... 나중에 ... globalThis.fetch = fetch; // fetch는 이미 mock을 가리킴 — 자기 자신 재대입 const res = await fetch(WORKER_URL, {...}); // 여전히 mock 호출! // 맞음 — 원본을 별도 이름으로 먼저 저장 const _nativeFetch = globalThis.fetch; globalThis.fetch = async (url) => { /* 로컬 파일 읽기 mock */ }; // ... 나중에 ... const res = await _nativeFetch(WORKER_URL, {...}); // 진짜 네트워크 요청

모의 함수는 알 수 없는 URL에 대해 { ok: true, json: async () => ({}) }를 돌려주도록 짜여 있었다 — 그래서 실전송 호출도 res.ok === true로 "성공"한 것처럼 보이면서 빈 객체만 받아, 결과 집계 로직 (data.created || [] 등)이 전부 빈 배열로 계산됐다. 에러 로그가 전혀 안 남고, HTTP 상태 코드 확인 분기도 정상 통과하며, 스크립트는 끝까지 완주해서 "완료" 메시지를 출력했다 — 겉보기엔 정상 실행이었다.

어떻게 잡았는가
"생성/스킵/실패가 전부 0"이라는 출력 자체가 이상하다고 판단해, 모킹 없는 별도 진단 스크립트로 단일 레코드를 네이티브 fetch로 직접 보내봤다 — 그건 정상 작동했다 (200 OK, 실제 생성됨). 그 다음 실제 배치 스크립트에 걸린 시간(ms)을 찍는 코드를 추가해보니 "0ms"가 나왔다 — 진짜 네트워크 요청이라면 있을 수 없는 값이라 여기서 mock 재사용을 확신했다.
일반화된 교훈
전역 함수(fetch·console.log 등)를 로컬 테스트/수집 목적으로 모킹해야 한다면, 원본을 반드시 별도 이름의 변수에 먼저 저장하고, 실제 외부 효과가 필요한 지점에서는 그 변수를 명시적으로 써라 — "나중에 복원"은 같은 전역 이름에 재대입하는 방식으로는 작동하지 않는다(자기 자신을 가리키는 참조를 다시 대입할 뿐이다). 그리고 "에러 없이 완료됐다"는 로그를 무조건 신뢰하지 말고, 숫자가 전부 0이거나 실행 시간이 비정상적으로 짧다면 그 자체를 이상 신호로 취급해라 — mock이 조용히 성공을 가장하는 경우 이런 신호가 유일한 단서일 때가 많다.
06 · Platform limit
Cloudflare Workers "하위요청 수" 한도는 애플리케이션 레벨 rate limit과 별개다
배치 10건 중 뒷부분에서만 "Too many subrequests" 실패가 재현됨

mock 버그(⑤)를 고친 뒤 실제로 전송이 되자, 이번엔 54건 중 6건이 "Too many subrequests by single Worker invocation" 으로 실패했다. 원인은 레코드 1건을 처리하는 데 PocketBase 왕복이 최대 4번(인스턴스 조회+생성, 프로필 조회+등록) 필요한데, 배치 10건을 한 HTTP 요청에 묶어 보내면 한 Worker 실행 안에서 최대 40개의 하위요청이 발생한다는 것 — Cloudflare 플랫폼 자체가 요청 1건당 걸어둔 하위요청 수 상한에 배치 뒷부분 (8~9번째 레코드 근방)에서 걸렸다.

일반화된 교훈
이 프로젝트는 이미 "시간당 몇 번 실시간 생성을 트리거하는가"(_checkGovTreeInstanceRateLimit, KV 카운터)라는 자체 비용 상한을 설계해뒀었다 — 그런데 이건 "한 HTTP 요청 안에서 하위요청을 몇 개까지 낼 수 있는가"라는 완전히 다른 제약이었다. 하나를 설계했다고 다른 하나도 저절로 해결되는 게 아니다. 여러 건을 한 요청에 배치로 묶어 외부 API(특히 서버리스 플랫폼)를 호출할 때는, 레코드 1건당 발생하는 하위 네트워크 호출 수 × 배치 크기가 그 플랫폼의 요청당 상한을 넘지 않는지 미리 계산해야 한다. 실패한 레코드는 재실행 시 멱등(이미 있으면 건너뜀)하게 설계해뒀던 덕분에 배치 크기만 줄여서 재시도하는 것으로 안전하게 복구됐다 — 배치 처리 스크립트는 부분 실패를 전제로 멱등하게 설계하라.
07 · Deployment map
이 저장소의 실제 배포 파이프라인 지도
PocketBase 스키마도 git push로 배포된다 — GUI Import는 최후 수단

이번 세션에서 처음으로 PocketBase 컬렉션을 새로 만들 일이 생겼는데, PocketBase 관리자 UI의 "Import collections"로 바로 만들 수도 있었지만, 이 저장소는 이미 git 기반 마이그레이션 파이프라인을 갖추고 있었다. GUI로 임시로 만들었다면 다른 서버(l1-hanlim 외 다른 L1 노드들)와 스키마가 어긋나고, 변경 이력도 안 남았을 것이다.

구성 요소역할
pb_migrations/*.jsPocketBase 0.22 migrate((db)=>{...},(db)=>{...}) 문법. 컬렉션 생성은 new Collection({...}); Dao(db).saveCollection(collection); 형태 — sp_gov_draft_realtime 생성 마이그레이션이 정확한 참고 예시.
ops/apply-pb-migrations.shGitHub Actions가 SSH forced-command로 트리거. SSH_ORIGINAL_COMMAND로 넘어온 파일명만 GitHub raw에서 개별 다운로드·검증 후 migrate up 실행 → 서비스 재시작 → 헬스체크.
.github/workflows/deploy-worker.ymlworker.js·wrangler.toml이 main에 push되면 wrangler-action으로 Cloudflare Workers에 자동 배포. gh run list --workflow=deploy-worker.yml로 배포 성공 여부 확인 가능.

실제 서버에서 SSH로 상태를 볼 때도 함정이 하나 있었다 — PocketBase 데이터 디렉토리 구조를 --dir=pb/hanlim이면 그 안에 pb_data/data.db가 있을 거라 가정했는데, 실제로는 pb/hanlim/ 바로 밑에 data.db가 있고 pb_data라는 폴더는 별도로(비어있는 채로) 존재했다. sqlite3로 잘못된 경로를 계속 조회하면서 "테이블이 없다"고 오판할 뻔했다 — ls -la로 실제 파일이 어디 있는지 먼저 확인하지 않고 관례적인 경로를 가정한 게 원인이었다.

일반화된 교훈
새로운 종류의 인프라 변경(오늘은 "PocketBase 컬렉션 생성")을 처음 할 때는, GUI로 바로 하기 전에 이 저장소가 이미 그걸 위한 파이프라인을 갖추고 있는지부터 확인해라 (pb_migrations/, .github/workflows/). 그리고 원격 서버를 SSH로 조사할 때 파일 경로를 관례로 가정하지 말고 ls -la·find로 실제 위치를 먼저 확인해라 — "여기 있을 것"이라는 가정이 틀리면 그 다음 모든 진단이 헛수고가 된다.
Checklist
다음에 비슷한 작업을 할 때

새 PocketBase 컬렉션·엔티티 식별자를 설계할 때

  • pb_migrations/*.js에서 비슷한 목적의 자매 컬렉션을 먼저 찾아 필드명 관례(영어 ASCII)를 확인했는가
  • K-Search 엔티티 식별자(entity_subtype)가 기존 시딩 스크립트가 이미 쓰고 있는 형식과 정확히 일치하는가(다르면 검색은 돼도 라우팅이 깨짐)
  • GUI로 바로 만들기 전에 이 저장소의 git 기반 마이그레이션 파이프라인(pb_migrations/+apply-pb-migrations.sh)부터 확인했는가

새 엔티티 계층/도메인 작업이 "끝났다"고 판단하기 전에

  • 발화 하나에 정상 응답한다는 것만으로 끝났다고 판단하지 않았는가 — 정적 라우팅과 K-Search/profiles 등록은 별개 경로일 수 있다
  • 이 계층이 이미 profiles에 등록되는 기존 시딩 스크립트의 대상 범위에 포함되는지 확인했는가

패치 적용이 실패하거나 이상하게 동작할 때

  • git am 실패 시 재시도 전에 git diff origin/main <브랜치>로 이미 반영됐는지부터 확인했는가
  • 지금 어느 브랜치에 있는지(git status) 명령 실행 전에 재확인했는가
  • PR을 만들었는데 "no commits" 에러가 나면 그 브랜치가 이미 main과 동일한지 확인했는가(중복이면 그냥 close)

Windows 실사용 환경에서 Node 스크립트를 돌릴 때

  • 동적 import()에 절대경로를 넘길 때 pathToFileURL()로 감쌌는가
  • PowerShell로 파일을 만들 때 Out-File -Encoding 값이 그 PowerShell 버전에서 지원되는지 확인했는가(안전하게는 utf8)
  • API 진단은 Invoke-WebRequest가 아니라 실제 운영 코드와 동일한 방식(네이티브 fetch)으로 했는가

로컬 테스트용으로 전역 함수(fetch 등)를 모킹할 때

  • 원본을 덮어쓰기 전에 별도 변수에 저장해뒀는가(const _native = globalThis.fetch;)
  • 실제 외부 효과가 필요한 지점에서 그 저장해둔 원본 변수를 명시적으로 쓰고 있는가(같은 전역 이름 재대입은 복원이 아니다)
  • "완료됐다"는 출력의 숫자가 전부 0이거나 실행 시간이 비정상적으로 짧으면, 성공이 아니라 이상 신호로 의심했는가

여러 건을 배치로 묶어 외부 API(특히 서버리스 플랫폼)를 호출할 때

  • 레코드 1건당 발생하는 하위 네트워크 호출 수 × 배치 크기가 그 플랫폼의 요청당 하위요청 상한을 넘지 않는지 계산했는가
  • 배치 처리 스크립트가 부분 실패를 전제로 멱등하게 설계됐는가(재실행 시 이미 성공한 건 건너뛰는가)
