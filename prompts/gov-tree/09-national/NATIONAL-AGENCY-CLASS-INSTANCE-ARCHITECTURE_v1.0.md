## 0. 배경 — 주피터 지시 원문 요약

> "모든 기관들의 원형 클래스를 구성한 뒤, 처음 호출되는 시점에 인스턴스를
> 생성한다. 인스턴스는 클래스를 복제한 뒤 점진적으로 지역 특성에 맞게
> customization된다. 중앙정부기관(국세청, 통계청 등)은 인스턴스가
> 하나뿐인 싱글턴이지만, 원리는 동일하다."

이 문서는 이 원칙을 09-national 트리에 명시적으로 적용한다.

## 1. 지역 행정기관과 국가기관의 클래스-인스턴스 대응관계

| 개념 | 지역 행정기관(도청/시청) | 국가기관(중앙행정기관) |
|---|---|---|
| 클래스(원형) | `SP-DEPT-{DOMAIN}-TEMPLATE`, `SP-CITYDEPT-{DOMAIN}-TEMPLATE` | `SP-NAT-{DOMAIN}-TEMPLATE` |
| 인스턴스 카디널리티 | **지역(도코드/시코드)마다 1개** — 부산시청 jachi ≠ 제주시청 jachi | **전국에 정확히 1개(싱글턴)** — 국세청은 어디서 물어도 같은 국세청 |
| 인스턴스를 구분하는 축 | 지역(어느 도/시/구인가) | 없음 — 도메인(어느 기관·업무인가)만으로 완전히 식별됨 |
| "실사 데이터"의 역할 | 그 지역 인스턴스 자체의 정체성(국이름·산하과 등) | 인스턴스 정체성과 무관 — **지사 디렉터리**(아래 §2)일 뿐 |
| 마스터데이터 파일 | `city-dept-master-data.json`(레코드=인스턴스) | `national-agency-master-data.json`(레코드=지사 디렉터리 항목, 인스턴스 아님) |

**핵심 차이를 한 문장으로**: 지역 행정기관은 "어느 지역이냐"가 인스턴스를
가르는 축이지만, 국가기관은 그 축이 아예 없다 — "세무서가 어디 있는지"는
인스턴스가 여러 개라서가 아니라, **단 하나뿐인 국세청 SP가 사용자 위치에
맞는 지사를 찾아주는 부가 기능**일 뿐이다.

## 2. `national-agency-master-data.json`의 올바른 해석 — "지사 디렉터리", 인스턴스 목록이 아님

2026-07-24 이전에는 이 파일의 레코드(예: `{domain: 'police', 도코드: 'busan', 지사명: '부산경찰청'}`)를
"부산의 police 인스턴스"처럼 다뤄왔다 — 지역 행정기관 패턴을 그대로
따라한 것인데, 오늘 주피터 지시로 보니 정확한 모델이 아니다.

**올바른 모델**: `SP-NAT-POLICE-TEMPLATE`가 유일한 인스턴스(싱글턴)다.
`national-agency-master-data.json`의 47개 레코드는 이 싱글턴이 §7
PDV_REQUEST 흐름(사용자 위치 확인 후 관할 안내)에서 참조하는 **조회용
디렉터리 데이터**다 — 지역 행정기관의 "국(局) 인스턴스"와는 존재론적으로
다르다. 비유하자면, 실제 국세청 웹사이트가 하나이면서 "가까운 세무서
찾기" 페이지에 전국 세무서 주소록을 갖고 있는 것과 같다 — 주소록이
여러 개라고 국세청 웹사이트가 여러 개가 되는 게 아니다.

**이 재해석이 바꾸는 것**:
- (구) "police는 13개 도에 인스턴스화됨, 21개 도는 미인스턴스화" — 틀린
  프레임. **police 싱글턴은 처음부터 전국에 이미 완전히 존재한다**
  (`SP-NAT-POLICE-TEMPLATE`가 존재하는 순간 인스턴스화 완료). 47개
  레코드는 "디렉터리가 몇 개 지사까지 채워졌는가"일 뿐, 인스턴스
  완성도가 아니다.
- (구) "나머지 20개 도메인은 정적 확대가 필요하다" — 이것도 재해석하면
  **인스턴스는 이미 34개 전부 완성돼 있다**(SP-NAT-*-TEMPLATE 34개
  전부 존재하므로). 남은 일은 "디렉터리를 얼마나 채우느냐"뿐이며, §3에서
  보듯 그마저도 정적으로 미리 채울 필요가 점점 줄어든다(동적 조회로
  대체 가능).

## 3. 지사 디렉터리를 채우는 두 가지 방법 — 정적 사전등록 vs 동적 실시간조회

싱글턴 SP가 "이 사용자는 어느 지사로 가야 하는가"를 알아내는 방법은
두 가지이고, 서로 배타적이지 않다:

1. **정적 사전등록**(`national-agency-master-data.json`에 미리 레코드 추가)
   — 관할이 도 경계와 깔끔히 일치하고(§7-1 참고) 이미 검증된 경우에만
   쓴다(2026-07-24 police 13개 도 사례). 장점: 빠른 응답, 실사 검증
   가능. 단점: 관할이 안 맞으면 위험(§7-1 이미 확인).
2. **동적 실시간조회**(§7 PDV_REQUEST + `SP-NATIONAL-LAZY`) — 사전등록이
   없어도, 사용자 위치를 물어서 그 순간 관할을 찾아준다. 장점: 관할
   복잡성(세무서·법원·병무청 등 도 경계와 안 맞는 기관)에도 안전하게
   대응. 단점: 매 호출 검색 비용, 결과가 매번 검증되지 않음.

**원칙**: 관할이 깔끔한 소수(현재 police)만 1번 방식을 쓰고, **나머지는
전부 2번 방식이 기본값**이다 — 이게 "처음 호출 시점에 인스턴스화"의
국가기관 버전이다: 사전에 아무것도 안 채워놔도, 첫 호출에서 PDV_REQUEST로
그 자리에서 관할을 찾아 답하고, 그 결과를 지금은 저장하지 않지만(§4
한계 참고) 필요하면 다음 호출도 똑같이 잘 작동한다(같은 절차를 다시
타므로 "인스턴스화가 덜 됐다"는 의미의 실패가 아니다).

## 4. 아직 없는 조각 — 실시간조회 결과의 영속화(persist)

지역 행정기관 논의에서도 나온 것과 동일한 한계다: 지금 PDV_REQUEST
흐름은 매 호출 계산만 하고 **저장하지 않는다**. "서울 사는 사람이 관할
법원을 물어봤다 → 답해줬다"는 사실이 다음 호출을 위해 캐싱되거나
디렉터리에 반영되지 않는다. 이를 개선하려면 hondi-proxy Worker가
PDV_REQUEST 조회 결과를 `national-agency-master-data.json` 상당의 실제
저장소(PocketBase 등)에 기록하는 쓰기 경로가 필요하다 — 이건 09-national
프롬프트 콘텐츠 작업의 범위를 넘어서는 인프라 작업이라 이번 문서에서는
설계만 남기고 구현하지 않는다(지역 행정기관 세션과 겹칠 수 있는 영역이라
더더욱 별도 조율이 필요 — §5 참고).

## 5. 지역 행정기관 세션과의 조율 — 충돌 방지

- 이 세션은 `09-national/` 트리와 `gov-router.js`의 국가기관 관련 함수
  (`_matchNational`, `_fetchNatText`, `_renderNatTemplate`,
  `_guessNatAgencyDomainFromText`, `_NAT_AGENCY_DOMAIN_KEYWORDS`,
  `POLICE_PROVINCES`/`_makePoliceEntry`, `PROVINCE_TABLES[*].national`)만
  다룬다.
- `02-do-dept/`, `04-city/`, `05-emd/`, `city-dept-master-data.json`,
  `do-dept-master-data.json`, `PROVINCE_TABLES[*].l2`/`.city`/`.citydept`는
  건드리지 않는다 — 다른 세션이 작업 중이다.
- §4의 영속화(persist) 인프라는 두 세션 모두에 필요한 **공유 인프라**다
  — 어느 한쪽이 먼저 설계하면 그 스키마를 그대로 재사용해야 한다(예:
  지역 행정기관 쪽이 PocketBase 컬렉션을 먼저 설계하면, 국가기관 지사
  디렉터리도 같은 컬렉션 패턴을 따른다). 이번 세션에서는 설계를
  제안하지 않고, 지역 행정기관 세션의 설계가 나오면 그걸 따라간다.
- 커밋 전 항상 `git pull origin main --rebase`(또는 상황에 따라
  브랜치+PR) — 오늘 세션에서 반복 확인한 표준 절차 그대로.
