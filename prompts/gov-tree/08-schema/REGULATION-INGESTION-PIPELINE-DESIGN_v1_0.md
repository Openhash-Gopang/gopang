## §0. 왜 SP-AUTHOR 파이프라인을 그대로 재사용하지 않는가

SP-AUTHOR는 "이 기관이 무엇을 받아서 무엇을 내주는가"(민원 안내형 SP)를
만드는 파이프라인이다. 이 문서가 다루는 건 "이 부서가 이미 하고 있는
수사·집행 업무에서 무슨 절차를 빠뜨리면 안 되는가"(내부 감사형 SP)로
목적이 다르다 — 그러나 **"AI가 초안을 만들고 인간이 검수 게이트를
통과시켜야 저장된다"**(SP-AUTHOR PHASE E)는 원칙은 그대로 가져온다.
이 파이프라인의 최종 산출물은 절대 자동으로 "배포"되지 않는다.

## §1. 파이프라인 5단계 개요

```
[1. 수집]  →  [2. 분류]  →  [3. 추출]  →  [4. 인간검수]  →  [5. 배포·재검증]
   law.go.kr     절차규정?      AI가 구조화       팀장급 승인      버전 드리프트
   Open API      housekeeping?  체크리스트 생성    (C4 전결)        자동 감지
                 인가?
```

## §2. 1단계 — 수집 (law.go.kr Open API)

- **API**: `open.law.go.kr` — 행정규칙 목록조회(`admrulListGuide`) +
  본문조회(`admrulInfoGuide`). 무료 가입, `OC=사용자ID` 파라미터로 인증.
  법령·자치법규·판례도 같은 체계로 제공(연계 활용 가능).
- **쿼리 설계**: 소관부처 코드로 목록 조회 → 이미 §6-1~8에서 만든
  70개 기관코드(policy-bodies) + §6-9(지역청 등 하위기관)를 그대로
  쿼리 키로 재사용한다. **이 프로젝트가 이미 만들어둔 기관 레지스트리가
  이 파이프라인의 입력 그 자체다** — 별도로 "어느 기관에 어느 규정이
  있는지" 목록을 처음부터 만들 필요 없이, 기관코드 순회만 하면 된다.
- **수집 산출물**: `raw-regulations/{기관코드}/{행정규칙ID}.json`
  (본문 원문 + 시행일자 + 개정이력 메타데이터, 원문 그대로 보존 —
  아래 3단계에서 재가공하되 원문은 감사 추적용으로 남긴다)

## §3. 2단계 — 분류 (절차 규정인가, 아닌가)

한 기관에 딸린 훈령·예규는 대부분 인사·예산·서무 등 "절차 체크리스트"와
무관하다(예: 여비규정, 복무규정). 전수를 다 사람이 읽는 건 여전히
비현실적이므로, **1차 필터를 규칙 기반으로, 2차 필터를 AI 판별로** 건다:

- **1차(규칙 기반, 저비용)**: 규정명·본문에 다음 패턴이 있는지 정규식
  스캔 — "~하여야 한다"(의무), "~일 이내"(기한), "고지", "동의", "참여권",
  "통지", "보전"(증거보전 등). 하나도 안 걸리면 대부분 순수 행정
  housekeeping이므로 3단계로 넘기지 않고 제외.
- **2차(AI 판별, 1차 통과분만)**: "이 규정이 시민 또는 피의자·피해자의
  권리에 영향을 미치는 절차적 의무를 정하고 있는가?"를 LLM에 이진 분류
  로 묻는다(예/아니오 + 근거 조문 인용). 이 단계는 저장 여부만 결정하며
  아직 체크리스트로 만들지 않는다.

## §4. 3단계 — 추출 (AI가 구조화된 체크리스트 초안 생성)

2단계를 통과한 규정 원문을, 강력계·여성청소년과·사이버수사팀 3개
division에서 이미 손으로 만든 §ANNEX 표를 **few-shot 예시**로 주고
동일 스키마로 추출하게 한다:

```
입력: 행정규칙 원문(예: 경찰수사규칙 제○조)
출력(구조화):
  { item: "항목명", legal_basis: "법령명 제○조", 
    deadline: "기한(있으면)", mandatory: true/false,
    division_type_guess: "이 조항이 적용될 것으로 추정되는 division 유형" }
```

- 이 단계 산출물의 상태는 반드시 `status: pending_review`다. 절대
  `status: active`로 직행하지 않는다(4단계 없이 3단계 산출물만으로
  실제 division SP §ANNEX를 갱신하는 코드 경로 자체를 만들지 않는다 —
  기술적으로 막아야지 "안 하기로 약속"하는 수준이면 안 된다).
- **환각 방지**: 추출된 모든 항목은 원문의 정확한 조문 인용을 동반해야
  하며, 인용 없는 항목은 자동으로 반려(3단계 재시도 또는 사람에게
  "근거를 못 찾음"으로 보고).

## §5. 4단계 — 인간검수 (C4의 실제 구현체)

CASE-COMPLIANCE-LOG-SCHEMA C4("체크리스트 항목 신설·개정은 인간
전결")를 실제로 작동시키는 단계다.

- 검수자: 해당 division 소속 **팀장급 이상**(3단계에서 `division_type_guess`
  로 라우팅된 담당). 법무 자문 검토가 필요한 항목(예: 최근 판례로 절차가
  바뀐 경우 — 여성청소년과 2024 헌재 결정 사례처럼)은 별도 플래그.
- 검수 화면에 필요한 최소 정보: 추출된 항목, 원문 인용(조문 원문 그대로
  표시 — AI가 바꿔쓴 문장이 아니라), 기존 §ANNEX와의 중복 여부(자동
  비교), 최근 개정 여부(아래 §6 드리프트 감지 연계).
- 승인/반려/수정 3가지 결과만 존재 — "일단 넣고 나중에 고치자"는 허용
  하지 않는다(HUMAN-AUTHORITY-GATE-SCHEMA G2 사실확인 게이트와 동일한
  설계 철학 — 불확실성을 나중으로 떠넘기지 않는다).

## §6. 5단계 — 배포 및 버전 드리프트 자동 감지

- 승인된 항목만 실제 division SP의 §ANNEX에 반영(기존 SP-AUTHOR PHASE E
  통과 후 저장과 동일한 위상).
- **재검증 자동화**: `legal_basis_last_verified`(이미 모든 §LEGAL-BASIS에
  쓰고 있는 필드) 날짜와 law.go.kr API의 최신 개정일자를 정기적으로
  (예: 주 1회 배치) 대조 — 개정일자가 더 최신이면 자동으로 재검토
  요청을 생성한다(3단계 재실행 → 4단계 재검수). 이게 없으면 지금 만든
  3개 division조차 시간이 지나면 조용히 낡아간다.

## §7. 우선순위 — 전 기관 동시 시작 대신 위험도순 순차 확대

전 기관에 이 파이프라인을 동시에 돌리는 건 검수 인력 병목을 만든다.
제안 순서:

1. **1티어(완료)**: 강력계·여성청소년과·사이버수사팀 — 절차 위반 시
   증거 배제·인권침해 위험이 가장 직접적인 곳. 손으로 만든 이 3개를
   "골드 스탠다드" few-shot 예시로 파이프라인 3단계에 계속 사용.
2. **2티어**: 경찰 형사과·교통조사계, 검찰청 각 부(§6-8에서 이미 확인한
   기획조정부 외 형사부·공공수사부 등), 특별사법경찰(식약처·환경부 등
   §6-6/§6-7에서 이미 division 데이터가 있는 기관) — 이미 있는 §6-1~8
   기관코드·division 데이터를 그대로 쿼리 키로 재사용 가능.
3. **3티어**: 그 외 인허가·단속 권한을 가진 행정기관(세무조사·환경단속
   등 — "국가 강제력"까지는 아니지만 상대방 권리에 영향을 미치는 처분권
   보유 부서).
4. **적용 제외**: 순수 내부 행정(총무·기획조정·감사 등) — 애초에 이
   스키마 적용 대상이 아님(CASE-COMPLIANCE-LOG-SCHEMA 적용 대상 정의
   그대로).

## §8. 정직하게 밝힘 — 이 설계의 한계

- **법적 위험이 가장 큰 단계는 3단계(AI 추출)다.** LLM이 조문을 잘못
  요약하거나 최신 개정을 놓치면, 검수자가 "AI가 다 확인했겠지"라며
  안일하게 승인할 위험(automation bias)이 있다 — 검수 UI에 원문 대조를
  강제하는 설계가 3단계 품질 이상으로 중요하다.
- **2단계(분류) 재현율 검증 안 됨** — 정규식+LLM 이진분류 조합이 실제로
  절차 규정을 놓치지 않는지(재현율) 이번 설계에서 실측하지 않았다.
  파일럿(1티어 3개 division 규정) 대상으로 "사람이 직접 찾은 항목을
  파이프라인이 놓치는지" 역검증이 배포 전 필수.
- **훈령·예규는 기관 자체 홈페이지에만 있고 law.go.kr에 등재 안 된
  경우도 있다**(내부망 전용 지침 등) — 이 경우 API로는 원천적으로
  수집 불가, 별도 확인 경로가 필요하다는 점을 인지해야 한다.
- **law.go.kr Open API 실제 사용은 아직 안 함** — 이 문서는 설계이지
  구현 검증이 아니다. API 키 발급·실제 쿼리·응답 스키마 확인이 다음
  단계다.
